## 1. Приоритет P0 — блокеры, без которых остальное не имеет смысла

### P0.1. Диск агента — разгружен 05.11.2026, но исчерпание не решено
**Было:** `overlay 9.8G / 9.2G / 447M avail / 96%`. **Стало:** `739M avail / 93%`.
Следующий `npm install` требует ≥208 МБ — запас есть.
**Что сделано:** удалены `failed`-сессии через `openclaw sessions delete`, затем
свободные страницы возвращены ОС — `PRAGMA incremental_vacuum` (`auto_vacuum=2`;
полный `VACUUM` потребовал бы 884 МБ временного места, которых не было) и
`wal_checkpoint(TRUNCATE)`. База `884 → 619 МБ`, `freelist 0`, `integrity_check: ok`.
**Почему не закрыто:** транскрипты растут ~100–190 МБ/сутки — это отсрочка на
считанные дни, а не решение. Следствие, которое надо назвать вслух: удаление
через шлюз само по себе **не освобождает диск** (страницы уходят в `freelist`),
без `incremental_vacuum` `df` не сдвинется.
**Уточнение 05.11 (замер, а не оценка):** предпосылка «87 МБ в `failed`» **неверна** —
там 6,8 МБ. Разложение 332 МБ текста `transcript_events`: `custom:openclaw.cache-ttl`
(метаданные кэша) — **176,5 МБ = 53%**; `message` (переписка) — 147,8 МБ;
`compaction` — 6,8 МБ. Форки: 259 `done`-сессий целиком лежат внутри других
(31,7 МБ), 28 774 из 54 542 сообщений — дубли (49,6%). **Сессии хранятся цепочкой,
ветка содержит полную копию родителя.**
**Что делать дальше (по убыванию эффекта):**
1. Удалять `customType='openclaw.cache-ttl'` — до **176 МБ**, истории не касается,
   кэш пересоберётся. Это самый большой рычаг, и он не про сессии.
2. Удалять `done`-сессии, чьё содержимое целиком дублируется родителем (259 штук,
   **31,7 МБ**) — потерь ноль. Перед удалением прогонять
   `scripts/extract-session-summary.js`, чтобы суть осталась в `docs/PROJECT-MEMORY.md`.
3. `~/.npm/_cacache` — уже чистили, дал +241 МБ.
4. `doctor --session-sqlite compact` — **почти бесполезен** при здоровом `freelist`;
   работает только при остановленном gateway.
**Условие готовности:** `df -h /` → `avail ≥ 1G` **и** автоматическая ротация в строю.
**Чего НЕ делать:** не считать `/tmp` диском — это tmpfs, чистка `/tmp` освобождает RAM.

**Замер 05.11 15:56 — потолок изнутри контейнера.** `/tmp` — отдельный tmpfs
(2 ГБ, `findmnt`), поэтому удалённые 379 МБ кэша
`/tmp/openclaw/session-archive-read-cache` освободили RAM, а `df -h /`
не сдвинулся **ни на байт** — это подтверждено, а не предположено.
Внутри overlay видно `du -x -sh /` → **3.3 ГБ**, а `df -k /` →
**8.90 ГБ занято**: разница **5.8 ГБ** на корне лежит вне видимости
контейнера (нижние слои overlay и данные хоста).

**Следствие, которое надо назвать вслух:** цель «`avail ≥ 1G`» **недостижима
удалением файлов внутри контейнера** — там всего 3.3 ГБ, из которых 2.8 ГБ
это `/app` (зависимости рантайма), и трогать их нельзя. Все найденные
кандидаты в сумме дают ~200 МБ: база 604 МБ (из них `cache-ttl` 161 МБ,
удалять только через штатный механизм, 23 680 строк в 120 сессиях), WAL 51 МБ,
`.git` 34 МБ, логи 12 МБ. Это отсрочка, а не `≥1 ГБ`.
**Реальный рычаг — на хосте**, не в контейнере: `docker system prune`,
очистка старых образов/слоёв, либо том большего размера. Пока это не сделано,
`ENOSPC` при `npm ci` вернётся, и никакая уборка внутри его не отменит.

**Что реально сделано 05.11:** `incremental_vacuum` вернул **7054 страницы

### P0.8. WAL не усекается на проде — код готов, блокирует litestream (`2.22.0`)

На проде база `2256896` Б, а `tarnet.db-wal` — `675712` Б: треть размера базы жила в
журнале. Копия «одного файла `.db`» при таком раскладе теряет последние транзакции —
их видно только через WAL, и обнаружение происходит при восстановлении.

**Сделано в коде:** `PRAGMA wal_checkpoint(TRUNCATE)` сразу после открытия БД,
при `busy` только лог (журнал валиден, старт не падает). Замер на 4 МБ: `4120032 → 0` Б.
Раскатано на прод, `server.js:278`.

**Проверка на проде 05.11.2026 — чекпоинт НЕ выполнился:** в логе «checkpoint не
завершён (busy) — журнал 675712 Б остался». Причина не в коде: БД держит
`litestream-tarnet.service` (репликация в S3), 8 попыток `TRUNCATE` из отдельного
процесса — 8 раз `busy:1`. Доказано: `stop litestream` → `TRUNCATE` вернул `busy:0`
и `675712 → 0` Б; `start` → WAL `4152` Б, `quick_check: ok`, 45 таблиц, репликация
продолжилась. То есть противоречия «код верен, но не работает» здесь нет — мешает
обязательный читатель.

**Осталось:** не автоматизировать вслепую. Усечение требует `stop litestream` →
чекпоинт → `start`, и это осознанно ручная операция: останавливать репликацию
на время рестарта сервиса значит молча расширять окно без бэкапа. Решение — либо
явная команда обслуживания с уведомлением, либо отказ от усечения (журнал 675 КБ
при базе 2.2 МБ не проблема, проблема — копия «одного файла»).

**Ловушка:** `wal_checkpoint(TRUNCATE)` возвращает `log: 0` — счётчик обнуляется в самом
вызове. Отчитываться можно только замером файла до/после, иначе лог молчит всегда.

### P1.1. Второй узел вне localhost — **главный незакрытый пункт проекта**
**Проблема:** `registry.total: 0`, P2P на `127.0.0.1`, `active_workers: 0`.

**Почему P1:** всё остальное (экономика, криптография, леджер) уже проверяемо. Упирается
именно в это: протокол без второго участника — демонстрация, а не сеть.
**Что уже готово в коде:** `p2p-transport.js` умеет `wildcardBind` для `0.0.0.0`
(строка 157), приоритет `P2P_PUBLIC_URL → P2P_ADVERTISE_IP` (строки 220-225).

в systemd **заданы** (`p2p-bridge.service`: `P2P_HOST=0.0.0.0`, `P2P_PORT=4001`,

порт открыт в ufw (IPv4+IPv6). То есть возможность больше не «есть в коде, но не
включена» — она включена, и всё равно `registry.total: 0`: объявленный узел сети
не создаёт.
**Что делать:** поднять второй узел на отдельной машине, задать `P2P_PUBLIC_URL`,
проверить, что `framesIn > 0` — сейчас у всех трёх узлов нули.
**Условие готовности:** `GET /p2p/status` → `registry.has_public_nodes: true`,
`framesIn > 0` хотя бы на одном внешнем узле, `active_workers ≥ 1` в течение 10 минут
**без ручного запуска** воркера.

| Файл | Роль |
| :--- | :--- |
| `p2p-node/bridge.js` | Отдельный процесс. Unix-socket `/tmp/tarnet-p2p-bridge.sock`, права `0600`, JSON Lines. Команды: `announce`, `status`, `peers`, `ping` |
| `p2p-bridge-client.js` | Клиент на голом `net`, подключается из `server.js`. Никогда не бросает |
| `server.js:37` | `require('./p2p-bridge-client')` |
| `server.js:9268` | `announceOnStartup()` в колбэке `app.listen`, **без `await`** |

**Почему отдельный процесс, а не модуль в `server.js`.** libp2p тянет 105 МБ
зависимостей и свои таймеры. Импорт внутрь `server.js` означал бы, что ошибка
libp2p при старте роняет HTTP-сервер — тот, что обслуживает 1124 проверки и прод.
Мост изолирует: сервер живёт, даже когда p2p-узла нет вовсе.

**Почему `await` не поставлен.** С `await` при зависшем мосте сервис формально
запускается, но не обслуживает запросы, а systemd ставит `active` — деплой счёл
бы такую раскатку успешной. Объявление идёт в фоне.

**libp2p на момент этого шага НЕ поднимался** (`P2P_BRIDGE_LIBP2P=1` включает). Запуск
узла открывает порт 4001 наружу — это отдельное решение с правкой firewall, и
принимать его молча из-за деплоя нельзя. (Решение принято отдельным шагом — см. ниже.)

**Проверено:** мост поднимается, сокет `0600`, все четыре команды отвечают,
неизвестное действие → `UNKNOWN_ACTION` со списком известных, битый JSON →
`BAD_JSON`. Сквозной прогон: `server.js` на порту 3006 пишет
`🌐 p2p bridge: объявлен как backend-api@127.0.0.1:3006`, мост логирует
`announce: node=backend-api@127.0.0.1:3006`. `peerId` при этом был `unassigned` —
у backend-api **на тот момент** не было ключа узла; это было честное состояние,
а не успех discovery. Ключ и постоянный `peerId` появились следующим шагом, ниже.

**Чего мост НЕ делает (важно для приёмки):** не ищет пиров в Kademlia DHT,
не передаёт координацию и не снимает зависимость от единого `server.js`.
Объявленный `peerId` никому не сообщается — это первый шаг, а не discovery.
Условие готовности P1.1 **не закрыто** им.

**На проде мост ЗАПУЩЕН с 2026-11-05.** `p2p-bridge.service` установлен,
`active`, `enabled`, `NRestarts=0`. libp2p слушает `0.0.0.0:4001`,
порт открыт в ufw (IPv4 + IPv6). Живой ответ сокета:
`peerId 12D3KooWRjbDE4rzafznjsd4aDu3S4Z1exHcPKSw2MeH4WcVEZpy`,
`listen /dns4/v1107336.hosted-by-vdsina.com/tcp/4001/p2p/<peerId>`,
`peer_id_persistent: true`, `peer_key_path /var/lib/tarnet/p2p/peer-id.bin`.
`server.js` переобъявляется после рестарта моста автоматически
(`startAnnounceLoop`, интервал 60 с, лог только при смене состояния).

**`peerId` больше не `unassigned`.** Ключ узла генерируется один раз и лежит
на диске (`p2p-node/peer-id-store.js`, права `0600`); проверено двумя
рестартами сервиса — `12D3KooWRjbDE4rzafznjsd4aDu3S4Z1exHcPKSw2MeH4WcVEZpy`
не меняется, `peer_id_created_on_start: false` со второго старта.

**Чего это по-прежнему не даёт:** узел объявлен и доступен, но discovery
нет — peers в Kademlia DHT не ищутся (kad-dht в `clientMode`, запросов 0).
Условие готовности P1.1 (`has_public_nodes: true` + `framesIn > 0`) этим
шагом **не закрыто**: один узел в сети не создаёт трафик. Мост — предпосылка,
а не результат.

### P1.2. Эмиссия против спроса
**Проблема:** Block `116.75` против Fee `7.15` — 94.2% награды из эмиссии.
Условие «спрос > эмиссия» не выполнено. Это не дефект кода, а отсутствие спроса.
**Что делать:** не менять константы (запрет манифеста), а растить платящий спрос.
**Условие готовности:** `totalFeeRewardTar / totalRewardTar > 0.5` в `/summary`.
**Чего НЕ делать:** не подкручивать `E_0` или `κ`, чтобы «выглядело сбалансированно».

### P1.3. Операционный запас казны
**Проблема:** `0.19815 TAR` при OPEX `517 $/мес` → `reserveStatus: critical`.
**Условие готовности:** `reserveStatus` перестаёт быть `critical` **за счёт fee**,
а не за счёт допечатки.

## 3. Приоритет P2 — доверие и приватность

### P2.1. Комитет валидаторов
**Проблема:** 0 членов при `REQUIRED_COMMITTEE_SIZE = 5` и `VALIDATOR_STAKE_LOCK_TAR = 10`
(нужно 50 TAR стейка). Без комитета spot-check некому подтверждать.
**Почему P2:** пока узлов один, валидировать нечего — зависит от P1.1.
**Условие готовности:** 5 членов, `benchmark_runs` с реальными вердиктами.

### P2.2. ONNX NER — но не включать
**Проблема:** `pii_classifier.ready: false`. Модели на проде физически нет.
**Важно, и это легко упустить:** включение ONNX **не изменит гейт Tier 6**. Гейт
(`server.js:6169`) вызывает `LLM.piiCheck`, а тот читает **только** `STRUCTURED_PATTERNS`
(`llm-adapter.js:40-56`). `piiClassifier.classify` с NER вызывается в двух других местах —
`/distill/record` (4455) и внешняя ветка (6955). Гейт regex-only по устройству.
**Решение уже принято 22.10 (вариант B, `ebc461d`):** не включать. Причина — точность, не память:
`bert-base-NER` при пороге `0.95` размечает «Explain how TCP handshake works» как `B-ORG: T (0.94)`.
**Условие для пересмотра:** модель с F1 ≥ 0.95 на нашем наборе обычных вопросов.
**Чего НЕ делать:** не подавать Tier 6 как безопасный для произвольных промптов —
имена, адреса, паспортные данные в свободном тексте **не блокируются**.

### P2.3. Смарт-контракты `[SPEC / ROADMAP]`
**Проблема:** 0 файлов `.sol`, `onchain.simulated: true`, 17 settlement'ов синтетические.
**Условие готовности:** контракт в тестовой сети + один settlement, проверяемый по `txHash`
внешним эксплорером.
**Чего НЕ делать:** не писать «on-chain» при `simulated: true`.

## 5. Правило приоритета

1. **P0 — блокеры:** диск, контракт, мёртвая константа. Делать сразу, они дешёвые.
2. **P1.1 — второй узел.** Единственный пункт, который переводит проект из демонстрации
   в сеть. Всё остальное либо уже работает, либо ждёт этого.
3. **P1.2, P1.3** — не код, а спрос. Кодом не решаются.
4. **P2/P3** — после того, как есть второй участник.

**Приоритет никогда не повышается из-за того, что пункт «интересный».** Только из-за блокера.

## 6. Как этот файл обновляется

- При закрытии пункта — не удалять, а переносить в `PROJECT-HISTORY.md` с датой и доказательством.
