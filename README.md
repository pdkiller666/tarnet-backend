# TarNet / Synapse — dPoUW backend (`2.22.13`)

Демонстрационный стенд экономики **Deterministic Proof-of-Useful-Work**.
Каждая подтверждённая единица работы даёт точное, заранее вычислимое
начисление. Вероятностных выплат нет.

- Версия схемы: `2.1.0-dpouw`
- Подписи чеков: **Ed25519** (проверяются локально клиентом)
- Приватные ключи: **AES-256-GCM** at rest
- Начисления: **off-chain**, мгновенно. On-chain — только итоговый чек (симуляция)

> **Карта прогресса — [`MASTER-PLAN.md`](MASTER-PLAN.md):** 14 этапов от идеи до цели,
> что закрыто и что впереди. `README` — быстрый вход в проект, `MASTER-PLAN` — где мы на
> пути к продукту с платящим спросом.

> **Честный срез состояния — [`docs/REALITY-CHECK-v3.md`](docs/REALITY-CHECK-v3.md).**
> Что из обещаний Whitepaper v1.0 реализовано, что переделано, что отложено
> и что выброшено — с цифрами с боевого сервера, а не по памяти. Начинать

## Запуск

```bash
cd backend-api
npm install
node seed.js          # чистая база: ноды + служебные счёта
node server.js        # http://localhost:3001
```

Переменные окружения: `PORT`, `TARNET_DB`, `TARNET_SECRETS_DIR`,
`REWARD_MODE` (`bootstrap|demand|hybrid`), `TARNET_GENESIS_TS`.

Каталог `.secrets/` создаётся при старте и содержит `master.key` (0600).
Потеря `master.key` делает приватные ключи кошельков нечитаемыми — это
осознанно, резервная копия обязательна.

## Экономика

### Cognitive Work Unit

```
W_i = N_tokens × κ_tier × γ_verify
```

| Тир | κ | Назначение |
|---|---|---|
| `nano` | 0.1 | смартфон/планшет: relay + nano inference |
| `base` | 1.0 | домашний ПК, 0.5B–1.5B |
| `expert` | 4.0 | экспертный узел, 3B–7B + LoRA |

`γ_verify ∈ {0, 1}` — флаг качества (Blind Spot Check, 5% работ).
`γ=1` → начисление всегда. `γ=0` → начисления нет, причина в логе.

### Dual-Stream

```
Fee_Reward   = (W_i × P_USD / 1e6 / Rate_TAR) × (1 − φ)
Block_Reward = E_epoch × (W_i × ω_i) / Σ(W_k × ω_k)
E_epoch(t)   = E_0 × 2^(−t / T_halving)
ω_node       = √(Stake) × Reputation
```

`P_USD = $0.20`, `Rate_TAR = 20`, `φ = 5%`, `E_0 = 50 TAR`, эпоха = сутки.
`HALVING_PERIOD_EPOCHS = 365` — это **не ступенчатый халвинг**, а непрерывное
затухание: `E(epoch) = 50 × 2^(−epoch/365)` меняется каждую эпоху, а не скачком
раз в 365 (`economics.js:85`).

### Распределение φ = 5%

| Доля | Ставка | Получатель |
|---|---|---|
| Burn | 2.5% от fee | `0x…dead` (необратимо) |
| Treasury | 2.5% от fee | казна протокола |
| LoRA royalty | 5% от Fee_Reward | автор адаптера |
| Worker net | остаток | воркер |

Эмиссия не сжигается и не облагается комиссией: `burn`/`treasury`/`royalty`
берутся только из fee-потока.

> **Не путать при коммуникации:** 2.5% — это доля **от стоимости запроса** (`fee.gross`),
> а не от того, что получает воркер. На expert-тире выплата в ~3.3× больше fee, поэтому
> burn составляет лишь **0.76% от начисления**. Формулировка «сжигается 2.5% от каждого
> начисления» завышает дефляцию втрое и снята из публичных материалов (см. `MANIFEST.v3.4-UNIFIED.md`).

**Инвариант:** `burn + treasury + royalty + worker = feeGross + block`
проверяется в `/health` и `/summary` на каждой выборке.

### Защита эмиссии

Пул эпохи открывается линейно по времени (`released = E_epoch × elapsed/epoch`).
Выплата идёт только из открытой части, а одна выплата ограничена
`MAX_RECEIPT_SHARE_OF_EPOCH = 0.25` от `E_epoch`.

Без этого потолка первая работа эпохи имеет `denominator = собственный вклад`
(доля 100%) и забирает всю накопленную эмиссию — вознаграждение превращается
в гонку «кто первый». Сумма за эпоху всё равно не превышает `E_epoch`.

## PII-фильтр

Гибридный: **regex + ONNX NER**. Регулярки ловят структурный PII (телефон,
email, карта, IBAN), модель `Xenova/bert-base-NER` ловит имена. Итоговая
уверенность — минимум из двух веток.

**Почему гибрид, а не только модель.** У `bert-base-NER` девять меток
(`O, B/I-MISC, B/I-PER, B/I-ORG, B/I-LOC`). Классов «телефон», «email»,
«карта» в ней нет физически: на `+7 916 555 12 34` модель не находит
ничего. Замена regex на модель означала бы пропуск телефонов почты
во внешний API.

**ONNX выключен на текущем VPS.** Замер 30.10: модель держит пиковые 687 МБ RSS
(VmHWM) при 1642 МБ всего и 1165 МБ доступных — риск OOM при демо.
`/health.pii_classifier.enabled: false`, работает только regex-ветка.
Включение — только явным флагом `Environment=TARNET_PII_ONNX=1` в systemd unit.

**Авто-включения по объёму RAM нет.** Прежняя редакция этого раздела утверждала, что на сервере
с большим объёмом памяти модель поднимется сама — это было неверно: в коде единственное
условие — `process.env.TARNET_PII_ONNX === '1'` (`pii-classifier.js:48`).
`minFreeMb: 900` — лишь предохранитель (не грузить при нехватке памяти),
а не триггер загрузки. На сервере с любой RAM модель останется выключенной,
пока флаг не выставлен вручную.

Фильтр стоит только на ветке `external_api`. При `llm_mode =
deterministic_fallback` (текущий VPS) он не вызывается вовсе — проверять
классификатор надо напрямую, а не через `/inference`.

## Валидаторы и тиры узлов

`nodes.tier` — класс железа: `nano`, `base`, `expert`, `heavy`.
В комитет валидаторов (Benchmark Gate) попадают только `expert` и `heavy`.
Миграция ставит `DEFAULT 'base'`, затем backfill переводит в `expert` те
узлы, у которых есть ненулевой стейк и реальные `expert`-работы в
`work_receipts` — по факту, а не по заявлению клиента.

**`heavy` есть только как тир узла.** В `TIER_WEIGHTS` (κ для CWU) его нет:
это два разных смысла. `heavy`-машина способна быть валидатором, но
`POST /work` с `tier=heavy` по-прежнему отвечает 400.

Жребий комитета — детерминированный sha256-поток, **не VRF**: выбор
пересчитывается любым участником, но предсказуем заранее. ECVRF —
`[SPEC Phase 3]`.

## Накопительные чеки

Каждое начисление пишет запись в `work_receipts`:

```
seq, workerAddress, cwu, tier, feeGrossTar, feeRewardTar, blockRewardTar,
rewardTar, burnTar, treasuryTar, royaltyTar, cumulativeTotal, epoch,
omega, share, adapterId, actionId, timestamp, prevSignature, signature
```

- `seq` монотонен, `cumulativeTotal` — сумма всех начислений воркера включительно.
- `signature` — Ed25519 от канонической строки, `prevSignature` связывает чек с предыдущим.
- Клиент проверяет подпись по ключу из `/health`, не доверяя серверу.

## Идемпотентность `/work`

`actionId` в теле `POST /work` — **ключ идемпотентности**, а не подсказка для
аудита. Поведение проверяется приёмкой (раздел 8.11):

| Что пришло | Что происходит | Ответ |
|---|---|---|
| новый `actionId` | обычное начисление, id сохраняется в чеке | `201` |
| повтор того же `actionId` | второго начисления нет, возвращается существующий чек | `200 {duplicate:true, existing:'receipt'}` |
| повтор `actionId` короткой работы, чек ещё не выпущен | накопление не удваивается | `202 {duplicate:true, reason:'already_pending'}` |
| повтор работы, уже слитой в чек | возвращается тот чек, `batchedInto` = его `seq` | `200 {duplicate:true, batchedInto}` |
| тот же `actionId` на другого воркера | конфликт ключей, чек не отдаётся | `409` |
| `actionId` не передан | ключа нет: два одинаковых запроса — две работы | `201` ×2 |

Без `actionId` идентификатор выводится из содержимого (воркер, токены, тир,
адаптер, ответ) и служит **отпечатком для spot-check**, но не ключом: клиент
мог честно выполнить ту же работу дважды, и молчаливая «одна оплата» списала
бы его токены.

Практика: клиент, который может повторить запрос (сеть, таймаут), обязан
слать стабильный `actionId`. Тогда ретрай безопасен, а γ=0-отказ не «залипает»
навсегда — новый ключ даёт новое решение spot-check.

Проверка: `POST /receipt/verify` возвращает `signatureValid` и
`cumulativeValid` (арифметика нарастающего итога пересчитывается по БД).

## On-chain

Только итоговый чек, раз в `SETTLEMENT_INTERVAL_SEC` (86400) или по запросу.
Повторный `/settle` возвращает `alreadySettled: true` и не создаёт вторую
транзакцию. Одна запись на воркера в `/settlements`.

⚠️ Транзакция синтетическая: `txHash` — локальный идентификатор, реальной
сети нет. Это заглушка для аудита потока, а не боевой расчёт.

## Отличия от v1.3

Лотерейная модель удалена полностью: класс чека с множителем, розыгрыш по
HMAC, `drawProof`/`winThreshold`, эндпоинты `/lottery/*`, `/ticket*`, `/draw/*`,
поля `ticketsIssued`/`winRate` в сводке.

Причина: вероятностная выплата не даёт пользователю ответа «сколько я
заработаю за эту задачу» и делает баланс скачкообразным. dPoUW заменяет
множитель на формулу от объёма работы, а розыгрыш — на детерминированный
расчёт.

## Ограничения (честно)

1. **Нет реальной сети.** `settlementTxHash` — синтетика, смарт-контракта нет.
2. **TEE декларативен.** Флаг `isTeeAttested` ставится вручную, аттестации нет.
3. **Ollama может отсутствовать.** Тогда инференс эмулируется: токены
   выводятся из хеша промпта (воспроизводимо), ответ помечен `emulated: true`.
4. **`P_USD` — параметр, не рынок.** Курс `USD_PER_TAR` фиксирован (1 TAR = $20).
5. **`master.key` на том же диске.** Защита от утечки файла БД, не от
   компрометации хоста.
6. **Эмиссия с потолком на выплату.** Ранние работы эпохи получают больше
   поздних при равном вкладе — следствие мгновенности начислений.
7. **Доход на стенде мал по построению.** При цене `$0.20/1M` и доле эмиссии,
   делящейся на всю сеть, средний ПК даёт порядка `$2/мес`, RTX 4090 — `$31/мес`.
   Цифра `$330/мес` недостижима ни на одном классе устройств при этой цене.
   Подробный расчёт — `../TARNET_ARCHITECTURE.md` §8.2 (лежит на уровень выше, в корне workspace, вне этого репозитория).
