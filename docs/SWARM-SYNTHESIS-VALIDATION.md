# Валидация Swarm Synthesis

> **Версия:** 2.29.21-docs
> **Дата прогона:** 20.11.2026
> **Задач:** 25 · **Моделей в рое:** 3 · **Эталон:** 1 сильная
> **Вердикт: MOAT НЕ ПОДТВЕРЖДЁН.** Рой выиграл 0 из 25 задач (0%) при пороге 20%.

---

## 1. Зачем этот документ

Весь тезис проекта — «рой из нескольких слабых узлов даёт результат не хуже одной
сильной модели, поэтому офисный ПК имеет смысл». До этого прогона утверждение
**не измерялось ни разу**. `swarm-synthesis.js` умеет *выбирать* из двух ответов
(согласие по Дайсу, синтаксис кода, длина), но «выбрать» и «выиграть» — разные вещи.

Директива v2.29.20 требовала измерить это до Этапа 11, а не после того, как второй
seed уже поднят. Здесь — результат.

---

## 2. Как мерили

### 2.1 Задачи (25)

Детерминированный оракул вместо субъективной оценки 1–5. Пять категорий:

| Категория | Задач | Что проверяет | Тип проверки |
| :--- | ---: | :--- | :--- |
| `arith-*` | 5 | арифметика, проценты, скорость×время | число → допуск `1e-9` |
| `unit-*` | 3 | перевод единиц (кг, сек, KiB) | число → допуск `1e-9` |
| `logic-*` | 3 | силлогизмы, вывод по последнему слову | да/нет · число |
| `text-*` | 4 | реверс строки, счёт букв/слов, trim | точное совпадение |
| `json-*` | 4 | разбор JSON, извлечение полей, сумма | число · строка |
| `code-*` | 6 | JS-функции, запуск в `vm` с таймаутом 1000 мс | исполнение |

Оракул проверяет **результат**, а не форму ответа.

### 2.2 Модели

| Роль | Модель | Как |
| :--- | :--- | :--- |
| Рой №1 | `qwen/qwen3.5-9b` | OpenRouter |
| Рой №2 | `meta-llama/llama-3.1-8b-instruct` | OpenRouter |
| Рой №3 | `mistralai/mistral-small-3.2-24b-instruct` | OpenRouter |
| Эталон | `openai/gpt-5.6-terra` | OpenRouter |

**Честно о подмене.** Директива называла локальные `qwen2.5-coder:1.5b`, `qwen2.5:7b`,
`llama3.1:8b` через Ollama. Прогон шёл через OpenRouter на моделях того же класса
размера, потому что Ollama на машине прогона не поднята. **Числа этого прогона на
локальный рой не переносятся** — см. §6.

### 2.3 Три числа, а не одно

Разделение «качество моделей» и «качество выбора» — главное в методике:

- **swarm** — что реально отдал рой: два шага `synthesize()`, победитель фиксируется
  **до** оценки оракулом. Оракул не подсказывает рою.
- **oracle-best** — сколько дал бы **идеальный** выбор из тех же трёх ответов.
  Верхняя граница того, что `synthesize()` мог бы выжать.
- **single** — что ответила одна сильная модель.

Если рой меньше oracle-best — виноват **выбор**. Если oracle-best меньше single —
виноваты **модели**. Одно число этого не показывает.

## 3. Результат

```
рой 19/25 · oracle 24/25 · сильная 24/25
рой выиграл 0, сильная 5, ничьих 20 → 0% → NO-MOAT
стоимость: рой $0.001958 vs сильная $0.008758
```

| Метрика | Значение |
| :--- | ---: |
| Рой решил | **19 / 25** (76%) |
| Идеальный выбор из тех же ответов | **24 / 25** (96%) |
| Одна сильная модель | **24 / 25** (96%) |
| Эффективность выбора (рой / oracle) | **79.2%** |
| Задач, где рой победил сильную | **0** |
| Задач, где сильная победила рой | **5** |
| Ничьи | **20** |
| **Порог директивы** | **≥ 20%** |
| **Вердикт** | **NO-MOAT** |

Стоимость: рой в **4.5 раза дешевле** ($0.001958 против $0.008758) — это
единственное, где рой выигрывает.

---

## 4. Почему проиграл именно выбор

Потолок у роя **равен** сильной модели: 24/25 против 24/25. То есть три слабые
модели **вместе знают ответ** на все задачи, которые знает сильная. Потеря
происходит на одном шаге — когда `synthesize()` выбирает из трёх ответов.

| Правило `synthesize()` | Срабатываний | Из них потеряно |
| :--- | ---: | ---: |
| `agree` (сходство ≥ 0.8) | 15 | 1 |
| `longer` (более длинный) | 10 | **4** |
| `syntax` (код компилируется) | 0 | 0 |

**Правило `longer` потеряло 4 задачи из 5.** Все четыре — арифметика, где верный
ответ короткий, а неверный длиннее:

| Задача | Верный ответ был | Выбрано | Причина |
| :--- | :--- | :--- | :--- |
| `arith-1` | `410` (qwen) | `391.` / `400` | длиннее |
| `arith-5` | `200` (qwen, mistral) | `125.` | длиннее |
| `unit-2` | `2` (qwen, mistral) | `120` | длиннее |
| `logic-3` | `8` (qwen, mistral) | `10.` | длиннее |

Это не случайность, а системный дефект правила: **на задачах с коротким числовым
ответом «более длинный» означает «более подробно объяснил неверное»**. Правило
длины было выбрано как «более полный», но полнота и правильность расходятся
именно там, где ответ — одно число.

Пятая проигранная сильной моделью задача — `arith-4`: поезд 2 ч 45 мин × 80 км/ч.
Верного ответа (220) **не дала ни одна** модель роя, включая qwen. Здесь виноваты
модели, а не выбор.

### 4.1 Верхняя граница моата

Даже при **идеальном** выборе рой выиграл бы **1 задачу из 25** — те 5 проигрышей
сводятся к одному, где сильная модель ошиблась, а слабая оказалась права. Это
**4%** при пороге **20%**.

Вывод: проблема не в `synthesize()` и не в конкретных моделях. **Пять раз
меньше порога** — это не «подкрутить правило длины», это «механизма моата в
текущей формулировке нет».

## 5. Что это НЕ доказывает

Три ограничения, без которых результат был бы переоценён:

1. **Прокси вместо локального роя.** Модели того же класса, но не те. Локальные
   `qwen2.5:7b` на 4-битном квантовании слабее своих облачных версий — вероятно,
   хуже, но это **другое** измерение, и его нельзя вывести из этого прогона.
2. **25 задач — мало для узкого доверительного интервала.** 0/25 даёт верхнюю
   границу ~11% по правилу трёх при 95% уверенности. Это ниже 20%, но не ноль.
   Утверждение «моата нет» держится на **соотношении** (4% против 20%), а не на
   точности одной цифры.
3. **Один эталон.** GPT-5.6-terra — сильная модель, но не единственная. Рой мог бы
   выигрывать у модели слабее эталона. Директива требовала сравнения с «GPT-4/Claude»;
   взят один представитель этого класса.

---

## 6. Что делать

**Не менять позиционирование по одному числу.** Порядок:

1. **Повторить на локальном рое** (`--base ollama` на машине с Ollama) — это то,
   что действительно проверяет тезис про офисный ПК. Прокси-прогон отвечает на
   вопрос «может ли рой облачных моделей средней руки», а не «может ли рой на
   железе пользователя».
2. **Если локальный прогон тоже даст < 20%** — тезис про качество неверен, и
   экономику надо строить на **других** преимуществах: приватность (промпты не
   уходят с машины), стоимость (4.5× дешевле подтверждено), устойчивость
   (падение одного узла не роняет задачу). Все три — реальны и не требуют,
   чтобы рой был умнее.
3. **Правило `longer` нельзя оставлять как есть** независимо от исхода: оно
   систематически выбирает многословный неверный ответ на числовых задачах.
   Минимум — при равном синтаксисе и низком согласии предпочитать **короткий**
   ответ на задачах, где ожидается одно число. Это отдельная работа, не в 2.29.20.

**Чего не делать:** не засчитывать этот прогон как доказательство моата и не
удалять `synthesize()` — выбор из двух ответов всё ещё нужен для устойчивости к
падению узла, просто он не даёт качества.

---

## 7. Дефекты, найденные в самом стенде

Три ошибки были в измерительном инструменте, а не в моделях. Записаны, потому что
инструмент, который врёт в свою пользу, хуже отсутствующего.

| Дефект | Симптом | Исправление |
| :--- | :--- | :--- |
| Оракул чисел брал **первое** число ответа | «17 * 23 + 19 = 410» краснел на верном ответе: первым числом шло 17 | искать **любое** число, равное ожидаемому |
| Оракул да/нет через `\b` | `/\\bнет\\b/` не находил «Нет» — `\b` в JS определён по `[A-Za-z0-9_]`, для кириллицы границы нет | разбор последнего слова + сравнение строк без `\b` |
| Отладка читала `swarm.content` | печаталось `""` там, где стенд считал верно: `pick` — это селектор `first/second`, а не текст | читать `swarm.picks` и `reason` |

Первый дефект **занижал** результат роя (правильные ответы считались неверными),
второй — тоже. Третий дал ложную картину при разборе. После исправления рой вырос
с 17/25 до 19/25, и это честные 19.

## 8. Как воспроизвести

```bash
# полный прогон, 25 задач
node scripts/swarm-validate.js --out /tmp/swarm-validation.json

# быстрый смоук на 3 задачах
node scripts/swarm-validate.js --limit 3

# свои модели и эталон
node scripts/swarm-validate.js \
  --models qwen/qwen3.5-9b,meta-llama/llama-3.1-8b-instruct,mistralai/mistral-small-3.2-24b-instruct \
  --baseline openai/gpt-5.6-terra
```

Флаги: `--models`, `--baseline`, `--limit`, `--out`, `--timeout`.
Требует `OPENROUTER_API_KEY`. Результат — JSON с полем `summary.verdict`
(`MOAT-CANDIDATE` при `winRatePct >= 20`, иначе `NO-MOAT`) и сырыми ответами
всех моделей в `rows[].models[].content` для разбора.

---

## 9. Итог одной строкой

Три слабые модели **вместе знают** ответ не хуже сильной (24/25 против 24/25), но
рой отдаёт 19/25, потому что **выбор ломается на правиле длины**, а выиграть у
сильной при идеальном выборе он может лишь 4% задач при пороге 20%.
**Моат в текущей формулировке не подтверждён; экономику нужно строить на
приватности, стоимости и устойчивости.**
