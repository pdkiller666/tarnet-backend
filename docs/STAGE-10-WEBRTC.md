# Этап 10 — WebRTC между PWA и воркером

**Статус: план. Кода нет.** Это документ решения, а не отчёт о работе.

## Отклонённый вариант

**WS-relay как основной транспорт — отклонён.** Он уже работает и остаётся
аварийным путём, но задачи через него идут через сервер: трафик обязан
проходить хост, который мы обещаем не читать. Шифрование это скрывает, а не
устраняет — остаётся точка, где можно не отдать задачу.

## План

1. **Discovery.** PWA → `GET /p2p/discover?model=…` → список `peerId` +
   `workerAddress`. Адрес воркера берётся из канала задач, а не из DHT-записи:
   диспетчер доставляет по каналу, и объявленный, но не принимающий узел не
   должен попасть в список.
2. **Транспорт.** WebRTC DataChannel. В браузере — нативный `RTCPeerConnection`,
   на воркере — **`werift`** (чистый JS). `wrtc` не берём: сборка C++ на VPS
   роняет установку, а выигрыша нет.
3. **STUN/TURN.** STUN (`stun.l.google.com:19302` или свой) — только чтобы узнать
   внешний адрес. TURN — запасной путь, когда NAT не пробивается. Честно:
   **TURN видит трафик, но расшифровать не может** — ключ сессии едет отдельно.
4. **Подпись `TaskGrant`.** Ed25519-ключ в IndexedDB (недоступен JS-коду страницы
   вне вкладки), JCS-канонизация, проверка на воркере через `peer-auth.js` —
   тот же модуль, что сейчас проверяет `hello`. Второго пути проверки не будет.
5. **Откат.** Только при отказе WebRTC — на WS-relay, с явным логом
   `[transport] WebRTC failed, using WS relay`. Молчаливый откат запрещён:
   иначе «работает по WebRTC» будет утверждением без доказательства.
6. **Риски.** Safari и Firefox расходятся в поддержке DataChannel и ICE;
   тестировать труднее, чем сокет (нужны два NAT); HTTPS обязателен — уже есть.

## Чего этот план не обещает

Прямого соединения при симметричном NAT: там нужен TURN, а TURN — это сервер.
Этап 10 убирает сервер из **типового** пути, а не из всех.
