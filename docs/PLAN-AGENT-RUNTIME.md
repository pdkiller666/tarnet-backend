## 2. Главная проблема: цену нельзя узнать ДО работы

`cwu = tokens × κ × γ` (`economics.js:35`), где `γ` — коэффициент качества, он известен **только после** `verifyQuality`. Значит до генерации неизвестны ни `tokens`, ни `γ`, и «проверить `maxPerTaskTar` перед вызовом» в лоб невозможно: не с чем сравнивать.

**Решение — объявленный бюджет токенов и проверка по худшему случаю.**

Клиент присылает `maxTokens`. Сервер считает худший случай (`γ = 1.0`, `tokens = maxTokens`):

```
projectedGrossTar = maxTokens × κ × 1.0 × 1e-8
```

где `1e-8 = 0.2 / 1e6 / 20` (цена за 1 cwu при κ=1).

Почему это корректная защита, а не отписка: фактический расход **всегда ≤ projected**, потому что `γ ≤ 1` и `tokens ≤ maxTokens`. Лимит, пройденный по `projected`, физически не может быть превышен по факту. Обратное неверно — поэтому проверять надо именно худший случай.

**Если `maxTokens` не задан** — берётся дефолт из конфига (предлагаю 512) и он же становится базой лимита. Брать «контекст модели» нельзя: у `openrouter/qwen3-coder` это 262 144 токена, и лимит превратится в фикцию.

**Отдельно:** `maxTokens` должен уходить воркеру как жёсткий потолок генерации. Иначе воркер сгенерирует больше, и сервер либо превысит лимит, либо спишет больше, чем проверил.

## 3. Вторая проблема: дефолтные лимиты декоративны

При `PRICE_USD_PER_1M_TOKENS = 0.2` и `USD_PER_TAR = 20` один cwu стоит `1e-8` TAR, то есть **1 TAR = 100 000 000 cwu**.

| Лимит | Значение | Потолок в токенах (κ=1, γ=1) |
|---|---|---|
| `maxPerTaskTar` | 1.0 | **100 000 000** |
| `dailyLimitTar` | 10.0 | **1 000 000 000** |
| `humanApprovalThresholdTar` | 5.0 | **500 000 000** |
| Типичный ответ 512 токенов | 5.12e-6 TAR | — |

Вывод, который нельзя смягчать: **при текущих дефолтах ни один лимит не сработает никогда, а HITL не вызовется ни разу.** Если оставить эти числа и назвать их защитой — это ложь того же рода, что «лимиты проверяются», которую мы уже убрали из памяти.

Три варианта, нужно решение владельца:

- **(a) Пересчитать в микро-TAR:** `maxPerTaskTar = 0.0001`, `dailyLimitTar = 0.01`, `humanApprovalThresholdTar = 0.00005`. Быстро, но числа нечитаемы и зависят от курса.
- **(b) Задавать лимиты в токенах** (`maxTokensPerTask`, `dailyTokens`), а TAR считать производной. **Рекомендую это.** Лимит в токенах нельзя просочить сменой κ или курса `USD_PER_TAR`; он совпадает с единицей, в которой реально меряется работа.
- **(c) Оставить TAR + относительный множитель** к оценке типовой задачи. Гибко, но непрозрачно для пользователя.

## 4. Третья проблема: цены инструментов не согласованы с ценой токена

| Инструмент | `costPerCallTar` | В токенах инференса | В долларах при `USD_PER_TAR=20` |
|---|---|---|---|
| `web_search` | 0.01 | **1 000 000** | $0.20 |
| `python_executor` | 0.005 | **500 000** | $0.10 |
| `calculator` | 0 | 0 | $0.00 |
| Типичная задача (512 токенов) | 5.12e-6 | 512 | $0.0001 |

Один `web_search` = **~2000 типовых задач инференса**. Рыночная цена веб-поиска — $0.003–0.01 за запрос, то есть заложено в 20–60 раз дороже.

Похоже, цены писались из расчёта `$1 за TAR`; при `USD_PER_TAR = 20` они в 20 раз дороже замысла. Решение нужно до внедрения: либо понизить до `1e-6…1e-5` TAR, либо сознательно оставить и записать, что инструмент — премиальная операция.

## 5. Поток задачи: PWA → сервер → воркер → обратно

Сейчас `POST /inference` синхронный: держит HTTP-соединение, пока воркер считает (до 30 с). Для агента это ломается на трёх вещах: цепочка вызовов, HITL-пауза и таймаут прокси.

Предлагаемый поток для агентского вызова (`agentId` присутствует):

1. **PWA → `POST /inference`** с `agentId`, `maxTokens`, `prompt`, `tier`, `actionId`.
2. **Сервер валидирует** (до всякой работы): агент существует, `status = 'active'`; `agentId` принадлежит `clientAddress`; `maxTokens > 0`.
3. **Считает `projectedGrossTar`** по §2.
4. **Проверяет лимиты** по §6. Отказ — `402` с точной причиной и числами, задача не создаётся.
5. **HITL** по §8. Дороже порога — `202` + `approvalId`, ничего не списано.
6. **Резерв** (`reservedTar += projected`), запись `worker_tasks` с `agentId` и `projectedTar`.
7. **Воркер забирает** через `GET /worker/poll` — как сейчас, без изменений. Задача уже содержит `maxTokens`.
8. **PWA опрашивает `GET /inference/:taskId`** вместо держания соединения. Новый эндпоинт: текущий `runInference` умеет только синхронный ответ.
9. **`POST /worker/submit`** приносит ответ и, если были, `toolCalls`.
10. **`recordWork`** начисляет как сейчас; в точке `server.js:1308` резерв превращается в фактическое списание, разница возвращается в `reservedTar = 0`.

Для старых клиентов без `agentId` ничего не меняется: п. 2–6 пропускаются, `debit` работает как сейчас.

## 6. Лимиты: резерв на входе, списание на выходе

**Почему не считать по `balances`.** `debit()` вызывается только при выпуске чека (`server.js:1308`), а чек выпускается при переходе накопления через порог (`receiptThreshold`, `server.js:1009`: `nano` ≈ 1000 токенов, `base` ≈ 100, `expert` ≈ 50). То есть мелкие вызовы копятся в `pending_work` и не списываются вообще. Проверка «хватит ли баланса» по фактическому остатку увидит деньги, которые ещё не списаны, и пропустит перерасход.

**Почему не считать по `ledger_txs`.** В таблице (`server.js:329`) есть `actionId`, но нет `agentId`. Атрибутировать расход агенту через `actionId` нельзя: это клиентский ключ дедупликации, и клиент волен прислать любой. Плюс запись появляется только на флаше — то есть с тем же запаздыванием.

**Схема:**

```sql
-- ensureColumn, безопасный ALTER
worker_tasks: agentId TEXT, projectedTar REAL, reservedTar REAL

-- новый счётчик, чтобы не сканировать леджер
CREATE TABLE agent_spend (
  agentId TEXT NOT NULL,
  day     TEXT NOT NULL,          -- YYYY-MM-DD UTC
  spentTar REAL NOT NULL DEFAULT 0 CHECK (spentTar >= 0),
  calls   INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (agentId, day)
);

-- ключ резерва: повтор actionId не резервирует дважды
CREATE TABLE agent_reservations (
  reservationId TEXT PRIMARY KEY,
  agentId TEXT NOT NULL,
  actionId TEXT NOT NULL,
  reservedTar REAL NOT NULL,
  state TEXT NOT NULL CHECK (state IN ('held','settled','released')),
  createdAt TEXT NOT NULL,
  UNIQUE (agentId, actionId)
);
```

**Порядок проверки при enqueue:**

1. `projected > maxPerTaskTar` → `402 per_task_limit_exceeded` (вернуть `projected`, `limit`).
2. `agent_spend.spentTar(сегодня) + reserved(held) + projected > dailyLimitTar` → `402 daily_limit_exceeded`.
3. Всё прошло → `INSERT` резерва, `reservedTar += projected` в `balances`.

**На выходе (в `recordWork`, рядом с `server.js:1308`):** фактический `gross` списывается `debit()`, в `agent_spend` добавляется строка, резерв переводится в `settled`. Если `γ = 0` (работы не было) — `released`, деньги не двигаются.

`balances.reservedTar` уже существует (`server.js:316`) — наконец используется по назначению. Раньше колонка была мёртвой, и это стоит записать.

## 7. Инструменты и оплата

Воркер сейчас не умеет инструменты вообще (`grep tool\|python_executor\|web_search` по `worker-demo.js` → 0). Значит исполнение живёт в клиенте, и сервер не может его проверить.

**Минимальный честный вариант:**

1. Воркер присылает в `/worker/submit` массив `toolCalls: [{toolId, ok, ms}]`.
2. Сервер проверяет **до** начисления: каждый `toolId` есть в `tool_registry`; `isAvailable = 1`; входит в `allowedTools` агента; количество ≤ разумного потолка (предлагаю 8 на задачу).
3. Начисление: `Σ costPerCallTar` по успешным вызовам, строки в `agent_spend` с `kind = 'tool'`.
4. Неизвестный или запрещённый `toolId` → `400` **до** любой записи в леджер.

**Что это НЕ защищает, и это надо писать прямо:** сервер не может доказать, что инструмент действительно вызывался. Воркер может прислать `toolCalls: []` и всё равно получить оплату за инференс; или заявить вызов, который не делал (тогда заплатит лишнее). Это оплата по декларации.

Частичное закрытие: `calculator` детерминирован — его можно пересечь серверным пересчётом в рамках уже существующего spot-check (`SPOT_CHECK_SAMPLE_PCT = 5`, `economics.js:44`). `python_executor` и `web_search` так проверить нельзя.

## 8. HITL (человек в контуре)

**Триггер:** `projectedGrossTar > humanApprovalThresholdTar`.

Сейчас порог 5 TAR (см. §3) — не сработает никогда. Это первое, что надо исправить, иначе раздел мёртв с рождения.

**Почему нельзя держать HTTP-соединение.** `/inference` ждёт воркера до 30 с, а человек может думать минуты. Значит:

1. `POST /inference` возвращает **`202 Accepted`**: `{approvalId, status: 'pending_approval', projectedTar}`. Задача **не** создана, резерв **не** взят.
2. PWA показывает карточку: агент, промпт-хеш, сумма, лимиты.
3. `POST /approvals/:id/decide` с `{decision: 'approve'|'reject', signature}`.
4. Approve → резерв, enqueue, дальше обычный поток. Reject → `403`, ничего не списано.
5. TTL одобрения (предлагаю 5 мин) → `410`, ничего не списано.

```sql
CREATE TABLE approvals (
  approvalId TEXT PRIMARY KEY,
  agentId TEXT NOT NULL REFERENCES agent_registry(agentId),
  actionId TEXT NOT NULL,
  projectedTar REAL NOT NULL,
  payloadHash TEXT NOT NULL,       -- sha256 промпта: сумма привязана к содержимому
  status TEXT NOT NULL CHECK (status IN ('pending','approved','rejected','expired')),
  createdAt TEXT NOT NULL,
  expiresAt INTEGER NOT NULL,
  decidedAt TEXT,
  decidedBy TEXT
);
```

**Кто подписывает — только владелец.** Ключ `tar_id` (`POST /id/register`, `server.js:1727`), не ключ агента. Иначе агент одобрит сам себя, и HITL станет формальностью. `payloadHash` обязателен: без него можно одобрить дешёвый промпт, а отправить дорогой.

Отдельно: не забыть внести `/approvals` в `RATE_READ_PATH` (`server.js:1436`) для GET и в `strict` для POST.

Фаза A даёт проверяемый результат сама по себе: лимит либо срабатывает, либо нет — видно по ответу и по базе.
