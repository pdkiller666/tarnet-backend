## Статья 1 — Эмиссия и активация

### 1.1. Формула эмиссии

```text
Эмиссия только за верифицированный труд:
  Block_Share_i = E_era_actual × W_i / ΣW_k
  E_era_actual  = E_era × demand_factor
  demand_factor ∈ (0, 1] — параметр Genesis Ceremony (НЕ governance).

Эмиссионно-допустимая работа = верифицированный инференс + его верификация (Spot-Check),
  узлы Tier 1–3. Relay и проверки доступности эмиссию НЕ получают (защита от Sybil).
  Формула W для верификаторов — [OPEN GENESIS PARAMETER] Stage 11.
Tier 5 и Tier 6: 0% Block_Reward.
self_reported после генезиса = 0 эмиссии.
Стейк и репутация НИКОГДА не умножают эмиссию.
```

### 1.2. `demand_factor` — DEFERRED (правка П.1)

`demand_factor` **не фиксируется сейчас**. Числа `50` и `10` не вписываются: это были бы
два угаданных параметра вместо одного, то есть та же болезнь в другой форме.

```text
Параметр demand_factor явно DEFERRED до церемонии Genesis.
Он калибруется на фактических метриках спроса (fee_revenue vs E_era),
полученных в ходе Stage 10–14, ДО запуска Genesis Block #0.

До калибровки действует строгое правило:
  E_era — АБСОЛЮТНЫЙ ВЕРХНИЙ ПРЕДЕЛ (Max Cap).
  Любая невыбранная суточная эмиссия НИКОГДА не печатается и не переносится (never-mint).
  Фактический supply никогда не превысит расчётный кап, даже при нулевом спросе.
```

Почему DEFERRED работает, а не откладывает решение навсегда: Genesis идёт **после**
Stage 14 (платящий спрос), поэтому калибровка происходит **до** Genesis, а не после.
См. раздел «Отношение к канону».

### 1.3. Максимум и остаток

```text
MAX_WORKER_EPOCH_SHARE = 0.10 на один workerAddress; <= 0.20 на один /24 или ASN.
Превышение капа не перераспределяется; соответствующая доля не эмитируется.
Невыбранный остаток НЕ эмитируется и НЕ переносится (never-mint).
```

Два предупреждения, которые должны попасть в код и в UI, а не только в этот документ:

1. **Кап `/24` ниже суммы двух воркерных капов.** `2 × 10% = 20%` — ровно потолок `/24`.
   Третья машина в одном доме уже превышает кап и не получает эмиссии. Это не ошибка
   арифметики, это политика; интерфейс обязан объяснить её до запуска, а не после.
2. **Пер-воркерный кап — не константа, а новая логика в горячем пути леджера.** Он
   требует накопления `ΣW_k` по эпохе до распределения, то есть меняет порядок вычислений
   относительно текущего `RewardEngine.blockStream()` (см. `economics.js`).

### 1.4. Правило активации и разрыв петли (правка П.3)

```text
constitution_v2 разблокируется только при ОДНОВРЕМЕННОМ выполнении:
  spot_check_enabled === true AND независимых активных верификаторов >= 3.
До выполнения условия — CONSTITUTION_LOCK_ERR.
Активация только через новую цепь с Genesis Block #0.

Разрыв петли активации:
  При Genesis Block #0 первые верификаторы (минимум 3) получают стартовый
  Validator Bond напрямую из генезис-аллокации (пул верифицированных тестеров,
  <= 0.5% капа).
```

Без последнего пункта условие активации невыполнимо: верификатору нужен бонд → бонд
появляется после генезиса → генезис требует активации. Пул тестеров из Статьи 4 и есть
источник первых трёх бондов.

## Статья 2 — Стейк

```text
Стейк = страховой залог под слэшинг + порог допуска к тиру/валидатору.
НЕ множитель очереди. Внутри тира выбор по: затухающая quality-репутация,
  latency, tps, ask в TAR.
Репутация — затухающая по качеству, без выслуги лет.
Бонд строго индивидуален: 1 PeerId = 1 Bond.
Делегирование и ликвидный стейкинг бонда запрещены.
```

**Что это отменяет в текущем коде.** Сейчас `economics.js:114` считает
`omega = √stake × reputation`, и `Block_Reward` умножает долю на `omega`, а не на `W_i/ΣW_k`.
Это замаскированный proof-of-stake: доля в эмиссии растёт от капитала. Конституция это
запрещает (Статья 1: «Стейк и репутация НИКОГДА не умножают эмиссию»). Удаление `omega`
из `Block_Reward` — правка П.6, **не входящая в этот коммит** (см. «Что не меняется»).

## Статья 3 — Целочисленные деньги, кап, халвинг, строка чека

### 3.1. Единицы и расписание

```text
1 TAR = 100_000_000 base units. Только целые, никакого float.
E_0 = 719_178_082_192 units/эпоху (округление вверх от 525000/73 × 10^8).
Эпоха = ровно 86_400 с от genesis_timestamp.
Халвинг дискретный каждые 1_460 эпох (~4 года):
  E_era = floor(E_0 / 2^era) = BigInt(719178082192) / (BigInt(2) ** BigInt(era)).
Запрещены `>>` на Number и float для денег. Эр до нуля = 40.
Канонический кап = 20_999_999.99971440 TAR = 2_099_999_999_971_440 base units.
Витрина: «Hard Cap 21M».
```

Проверка капа (воспроизводима, дельта `0`):

```text
Σ(era=0..39) floor(719178082192 / 2^era) × 1460 = 2_099_999_999_971_440 units
эра 0  = 1_050_000_000_000_320 units (ровно половина капа)
эра 39 = 1 unit ; эра 40 = 0
```

### 3.2. Единый триггер

```text
Одно событие — Mainnet Genesis Block #0, epoch=0, genesis_timestamp.
```

### 3.3. Строка чека `payloadVersion:3` (16 атомарных полей)

```text
Кодировка: UTF-8, ASCII, разделитель '|', без пробелов/переносов.
Деньги: целые неотрицательные, десятичная строка без точки/экспоненты.
Работа: целые microCWU, 1 CWU = 1_000_000 microCWU.

v3|workerSeq|workerAddress|clientAddress|epoch|prevReceiptHash|contextHash|
   outputHash|modelId|tier|assuranceLevel|deltaMicroCwu|feeRewardUnits|
   blockRewardUnits|burnUnits|treasuryUnits|timestampMs

cumulativeMicroCwu и cumulativeTarUnits — НЕ в подписи (производные колонки).
Граница генезиса: первый чек воркера имеет prevReceiptHash = "0".repeat(64).
```

**Почему `deltaMicroCwu`, а не абсолютный `cwu`** (правка П.4 — отклонение моего
предложения): чек подписывает **приращение** работы за эпоху, а не накопленный итог.
Кумулятивные величины — производные колонки, они не входят в подпись и не могут
«разъехаться» с историей. Это согласованное решение 16-полевой схемы; менять его ради
пересчёта одной проверки — означает выпустить 17-е поле, которое сломает подписанный
формат на генезисе.

**`assuranceLevel` — поле есть, значения нет.** В коде `assuranceLevel` встречается **0 раз**
(проверено `grep -rn assuranceLevel --include=*.js`). Поле в спецификации есть, источник
значения появится на Stage 12 (Spot-Check). До этого момента оно не может быть подписано
осмысленно — это `[SPEC]`, и в Статье 4 фильтр снапшота по нему тоже пока `[SPEC]`.

## Статья 5 — Клиентская оплата, тариф, LoRA и лимиты

### 5.1. Оплата клиента

```text
STANDARD (налог протокола φ = 500 bps):
  burnUnits      = floor(clientPaymentUnits * 250 / 10000)   // 250 bps (2.5%)
  treasuryUnits  = floor(clientPaymentUnits * 250 / 10000)   // 250 bps (2.5%)
  workerFeeUnits = clientPaymentUnits - burnUnits - treasuryUnits  // 9500 bps (95.0%)

TAR_UTILITY (налог протокола φ = 200 bps):
  burnUnits      = floor(clientPaymentUnits * 100 / 10000)   // 100 bps (1.0%)
  treasuryUnits  = floor(clientPaymentUnits * 100 / 10000)   // 100 bps (1.0%)
  workerFeeUnits = clientPaymentUnits - burnUnits - treasuryUnits  // 9800 bps (98.0%)

Инвариант: сумма частей === clientPaymentUnits.
floor на burn/treasury даёт остаток воркеру.
```

### 5.2. LoRA-роялти — в units от gross (правка П.5)

```text
При использовании верифицированного LoRA-адаптера:
  royalty_bps = floor(φ / 20)                      // φ=500 → 25 bps; φ=200 → 10 bps
  royalty     = floor(clientPaymentUnits * royalty_bps / 10000)
  royaltyBurn     = floor(royalty / 2)
  royaltyTreasury = royalty - royaltyBurn
  workerFeeUnits  = clientPaymentUnits - burnUnits - treasuryUnits - royalty  (remainder)

Роялти вычитается из остатка воркера (worker = remainder), а не из комиссии φ:
из 500 bps налога 250 + 250 уже заняты, взять 25 неоткуда, кроме доли воркера.

Пол 90% действует при φ <= 953. При φ > 953 фактический минимум =
10000 - φ - floor(φ/20) bps (φ=1000 -> 8950 bps = 89.50%).
Коридор DAO: [200, 950] — на всём коридоре пол истинен (φ=950 -> 9003 bps = 90.03%).
```

**Почему `worker = remainder`, а не `burn = floor((φ - royalty_bps)/2)`** (отклонено, п. 3
раздела «Отклонено»): второй вариант требует пересчитывать `burn` и `treasury` от
уменьшенного налога, то есть менять уже согласованные 250/250 и заводить новую математику
там, где нужна одна строка.

**Расхождение с формулировкой `rc1`, зафиксированное честно.** В `rc1` стояло: «роялти
вычитается из комиссии протокола φ, не из доли воркера». Это несовместимо с
`burn = 250` + `treasury = 250` = `φ = 500`: из 500 уже занято всё, и 25 bps роялти взять
неоткуда, кроме остатка воркера. При принятом правиле `worker = remainder` роялти
**неизбежно** вычитается из доли воркера, а суммарные удержания составляют
`250 + 250 + 25 = 525 bps`:

```text
burn 250 + treasury 250 + royalty 25 = 525 bps удержано
worker = 10000 − 525 = 9475 bps (94.75%)
```

Пол 90% соблюдён с запасом `475 bps`. Инвариант держится **тождественно**, потому что
воркер — это remainder, а не вычисленная доля: `worker = clientPaymentUnits − burn −
treasury − royalty`, и сумма частей равна `clientPaymentUnits` по построению, без ветки
«а если не сходится». Именно это и означает «инвариант держится тождественно» в п. 6
принятых правок; альтернативное прочтение (`royalty` из φ при неизменных 250/250) даёт
`525` удержаний из `500` налога, то есть деньги из воздуха — ровно тот дефект, который
правка и устраняет.

### 5.3. Коридор DAO (Stage 14)

```text
φ ∈ [200, 950] bps; воркер >= 90% от gross на всём коридоре;
Burn/Treasury делят налог 50/50; изменение с 30-дневным timelock.
```

**Почему верхняя граница 950, а не 1000** (правка 19.11.2026). При `worker = remainder`
доля воркера равна `10000 - φ - floor(φ/20)`; при `φ = 1000` это `8950 bps = 89.50%`, то есть
пол 90% **ложен** на верхней границе. Граница, где пол ещё выполняется точно, — `φ = 953`
(`9000 bps`); на `954` уже `8999` (`89.99%`). Коридор `[200, 950]` держит пол с запасом
`3 bps` на всём диапазоне и оставляет DAO поле для манёвра в `750 bps`.

### 5.4. Соотношение CWU и TAR

```text
CWU — физическая мера труда: W_i = N_tokens × κ_tier × γ_verify.
TAR — монетарная единица леджера.
В эмиссии паритета нет: доля = W_i / ΣW_k (плавающая, аналог difficulty).
В оплате: 1 CWU = 1 base unit TAR — СПРАВОЧНЫЙ дефолт, не фиксация цены.
```

### 5.5. Клиентская цена и отмена `USD_PER_TAR` (правка П.4)

```text
В constitution_v2: released ≡ minted.
releasedTar — legacy-метрика testnet, не используется в emission accounting после Genesis.
delta === 0 относится к minted-суммам, не к releasedTar.
E_era — немонетарный верхний потолок.

При переходе на constitution_v2 константа USD_PER_TAR = 20 отменяется.
clientPaymentUnits считается напрямую из CWU × worker_ask_units.
```

Что это значит по факту: сегодня `USD_PER_TAR = 20` встречается в коде **16 раз** (включая
`server.js:1538`, `server.js:2647`, `agent-runtime.js:25`) и фактически **фиксирует цену**:
сумма в USD делится на 20. Пока константа жива, «рыночный ask» — декорация. Символы
`clientPaymentUnits`, `worker_ask_units`, `assuranceLevel` в коде **отсутствуют** (0 вхождений
каждый, проверено 15.11.2026) — то есть Статья 5.5 целиком `[SPEC]`.

## Отношение к канону `MASTER-PLAN.md` (правка П.2)

**Genesis Block #0 идёт ПОСЛЕ минимального платящего спроса и верификации**, а не вслепую
до них. Это и есть ответ на вопрос «когда калибровать `demand_factor`»: калибровка
происходит на Stage 14, Genesis — после неё.

Каноническая нумерация этапов **не меняется** (сверено с `MASTER-PLAN.md:60–263`, 16 этапов):

| Этап | Содержание | Статус в `MASTER-PLAN` |
|---|---|---|
| `Stage 10` | WebRTC — живой браузер PWA↔воркер + reboot-тест | 🟡 **В РАБОТЕ** |
| `Stage 11` | Второй seed у другого оператора | ⏳ впереди |
| `Stage 12` | Верификация работы (Spot-Check) | ⏳ впереди |
| `Stage 13` | On-chain settlement (L2) | ⏳ впереди |
| `Stage 14` | Платящий спрос → **калибровка `demand_factor`** | ⏳ впереди |
| **→ Genesis** | **Genesis Block #0, `constitution_v2`** | ⏳ после Stage 14 |
| `Stage 15` | DAO и планетарный масштаб | ⏳ впереди |

> ⚠️ **Расхождение с брифингом `rc1`, зафиксированное честно.** В брифинге (§6 «Порядок
> стройки») Stage 11 назван «Spot-Check», Stage 12 — «On-chain», а Genesis стоял на 11.5.
> В директиве §1.2 названо иначе: Stage 11 = второй seed, 12 = Spot-Check, 13 = on-chain.
> **Канон — `MASTER-PLAN.md`**, и он совпадает с директивой: 11 = второй seed, 12 =
> Spot-Check, 13 = on-chain. Брифинг `rc1` в этой части устарел, и перенумерация в нём
> молча выбрасывала второй seed из пути. Здесь используется канон.

## Числовое обоснование DEFERRED (почему `demand_factor` нельзя вписать сейчас)

Все числа воспроизводимы; метод — `curl /summary` + арифметика ниже.

```text
Номинальная эмиссия при df = 1 : 7_191.78 TAR/эпоху × 365 = 2_625_000 TAR/год
Эмиссия сегодня               : 50 TAR/эпоху × 365       =    18_250 TAR/год
Отношение                                                  =     143.8 ×

Выручка сети (fee) на 15.11.2026: 7.152497 TAR за ~24 дня ≈ 108.8 TAR/год
Эмиссия / выручка сегодня                                  =     168 : 1
Эмиссия / выручка при df = 1                               =  24_132 : 1
df для паритета эмиссии и выручки                          ≈   4.14e-5
```

**Вывод.** Чтобы эмиссия сравнялась с выручкой, `demand_factor` должен быть ≈ `4·10⁻⁵` —
одна двадцатипятитысячная. При `df = 1` проект печатает `2.6 млн TAR/год` при выручке
`≈109 TAR/год`. При рабочем `df` канонический кап недостижим: при `df = 1` — за 124 года,
при `4.14e-5` — в 21 000 раз дольше.

Это и есть причина, по которой число **не вписывается в Genesis вслепую**: на пустой сети
`demand_factor` неоткалибруем, и любое значение будет угадано. DEFERRED + never-mint
превращает проблему из «выбери правильное число» в «не печатай больше, чем потолок», а
калибровка переходит на Stage 14, где появляется факт.

Формула `min(E_era, max(bootstrap_floor, k × verified_fee_revenue))` с числами `50` и `10`
**отклонена** для этого релиза и отложена в `docs/ECONOMY-DESIGN-NOTES.md`: это новая
экономическая модель, требующая отдельного цикла проектирования, а её initial-значения
угаданы, а не выведены.
