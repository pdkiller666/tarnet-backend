# BYOK-PRICING — экономика Tier 6 (внешние API по ключу пользователя)

**Версия документа:** 2.17.8 · **Ставка:** B′ · **Дата:** 2026-11-01

Документ отвечает на один вопрос: **сколько стоит вызов Tier 6, куда уходит
комиссия и что остаётся каждой стороне.** Все числа взяты из `config.js` и
проверяются тестами `29.9`, `29.13`, `34.1`, `36.2`, `43.10b`.

---

## 1. Формула

```
fee = cashback + burn + treasury
```

Тождество обязано держаться на каждом вызове: `conservation.delta === 0`.
Если оно ломается, деньги появляются или исчезают — это не косметика, а
дефект леджера.

**Как это реализовано (Code-First):** `fee` и `cashback` — две независимые
константы в `config.js` (`TIER6.ORCHESTRATION_FEE_TAR`, `TIER6.CASHBACK_TAR`).
`burn` и `treasury` **не заданы вовсе** — они выводятся в `server.js`
(`/inference`, ветка Tier 6):

```js
const fee       = round(TIER6.ORCHESTRATION_FEE_TAR);
const cashback  = round(TIER6.CASHBACK_TAR);
const rest      = round(fee - cashback);
const burnTar   = round(rest / 2);
const treasuryTar = round(rest - burnTar);   // остаток, а не rest/2
```

`treasuryTar` берётся как **остаток**, а не вторым делением: при нечётном
`rest` округление не может развести сумму. Поэтому правка одного числа
(`ORCHESTRATION_FEE_TAR`) физически не способна сломать тождество.

## 2. Выбранный вариант — B′

| | fee | cashback | burn | treasury | Нетто для пользователя | Казна/вызов |
|---|---|---|---|---|---|---|
| **A** (было, 2.12.0–2.17.7) | 0.0005 | 0.0001 | 0.0002 | 0.0002 | **−0.0004** | 0.0002 |
| **B** | 0.0001 | 0.0001 | 0 | 0 | **0** | 0 |
| **B′** ← выбрано | **0.0002** | **0.0001** | **0.00005** | **0.00005** | **−0.0001** | **0.00005** |
| **B″** | 0.0001 | 0.00005 | 0.000025 | 0.000025 | **−0.00005** | 0.000025 |

**Почему B′, а не крайности:**

- **B (бесплатно)** убирает казну целиком. Комиссия перестаёт быть источником
  дохода протокола, а `burn` исчезает — дефляция заканчивается. Формулировка
  «протокол берёт комиссию» становится ложью.
- **B″ (дешёвый)** даёт казне те же 50% комиссии, но кэшбэк падает до
  `0.00005`. Обещание «кэшбэк `+0.0001 TAR`» перестаёт быть правдой по
  абсолютной величине — а это то, что видит пользователь в квитанции.
- **B′** оставляет кэшбэк ровно `0.0001` (обещание не меняется), сохраняет
  дефляцию и отдаёт казне 50% комиссии. Нетто падает вчетверо: `−0.0004` →
  `−0.0001`.

## 3. Что теряет казна

Честно, без смягчения:

| | при A | при B′ | Изменение |
|---|---|---|---|
| Доход казны с вызова | `0.0002 TAR` | `0.00005 TAR` | **−75%** |
| Вызовов на 1 TAR дохода | 5 000 | 20 000 | нужно вчетверо больше трафика |
| При 12 вызовах (текущий стенд) | `0.0024 TAR` | `0.0006 TAR` | `−0.0018 TAR` |

При балансе казны `0.1978 TAR` и OPEX `$517/мес` (`reserveStatus: critical`)
это **уменьшение дохода, а не рост**. Ставка B′ выбрана не ради казны: она
покупает конверсию — вызов становится дешевле вчетверо, и вероятность, что
клиент вообще начнёт платить, выше, чем доход с одного вызова. Если трафик не
вырастет вчетверо, казна получит меньше, чем при A. Это риск, а не выгода, и
в питче он должен звучать именно так.

## 4. Что получает пользователь

| | при A | при B′ |
|---|---|---|
| Списано за вызов | `0.0005 TAR` | `0.0002 TAR` |
| Вернулось кэшбэком | `0.0001 TAR` | `0.0001 TAR` |
| **Нетто** | **`−0.0004 TAR`** | **`−0.0001 TAR`** |

Кэшбэк абсолютной величиной **не изменился**. Изменилось только то, сколько
списывается. Формулировка «кэшбэк `+0.0001 TAR`» остаётся правдой.

## 5. `TAR_UTILITY_FEE` vs `ORCHESTRATION_FEE_TAR` — механизмы не пересекаются

`TAR_UTILITY_FEE_BPS = 200` (2%) — это ставка для **обычного инференса**
(`/work`, `/inference` на локальных тирах), когда клиент платит из своего
баланса TAR. Она живёт в `economics.js` и заменяет пару `BURN_RATE`/
`TREASURY_RATE` (5%) на `TAR_UTILITY_BURN_RATE`/`TAR_UTILITY_TREASURY_RATE`
(1% + 1%).

**Tier 6 к ней не относится.** Ветка Tier 6 в `server.js` не читает
`paymentMode` вообще: сплит считается от `TIER6.*` напрямую.

Проверено живым запросом (2026-11-01, изолированный сервер, фейковый
провайдер, `fee` уже `0.0002`):

```json
### tier 6, без paymentMode (HTTP 200)
{ "fee_gross_tar": 0.0002, "cashback_tar": 0.0001,
  "burn_tar": 0.00005, "treasury_tar": 0.00005, "delta": 0, "paymentMode": null }

### tier 6 + paymentMode TAR_UTILITY (HTTP 200)
{ "fee_gross_tar": 0.0002, "cashback_tar": 0.0001,
  "burn_tar": 0.00005, "treasury_tar": 0.00005, "delta": 0, "paymentMode": null }

fee одинаков (TAR_UTILITY не применяется к Tier 6): true
```

**Ограничение зафиксировано:** при `fee ≤ 0.0002` скидка `TAR_UTILITY` на
Tier 6 **не применима** — механизм к этому пути не подключён. Это не
ограничение округления: гипотеза «2% от `0.0002` округлится до нуля»
**опровергнута** — `0.0002 × 0.02 = 0.000004`, и при `DECIMALS = 6` это
представимо (проверено: `round(0.000004, 6) = 0.000004`, не `0`). То есть
если бы механизм был подключён, он работал бы, но обнулил бы `burn` и
`treasury` до `0.000002` каждый — и тождество всё равно держалось бы.

## 6. Связь с `PITCH-DECK`

Формулировка «кэшбэк `+0.0001 TAR`» **не меняется** — она верна по абсолютной
величине.

Меняется то, что нужно говорить рядом с ней: **нетто `−0.0001 TAR`, а не
`−0.0004`.** Восприятие цены строится по нетто, и именно оно улучшилось
вчетверо. Скрывать это незачем: цифра проверяется на первом же вызове.

Отдельно: **историческая сверка казны (`0.006962 TAR`)** в `PITCH-DECK`
относится к 29.10 при ставке A. Её цифры не пересчитаны под B′ намеренно —
это снимок фактического баланса, и подмена слагаемого сломала бы сумму.
Сверка проверяется тестом 41 на чистой БД, а не на этом снимке.

## 7. Чем это проверяется

| Проверка | Тест | Ожидание |
|---|---|---|
| Тождество `cashback + burn + treasury === fee` | `29.9` | `delta 0` |
| `fee = 0.0002`, `burn = treasury = 0.00005` | `29.9` | зелёный |
| С клиента списано `0.0001` нетто | `29.13` | `0.01 − balance = 0.0001` |
| `burn + treasury = 0.0001` в ответе | `29.13` | `1e-12` |
| Списание у фактического плательщика | `34.1` | `−0.0001` |
| Burn Tier 6 = `0.00005` | `36.2` | `1e-12` |
| `TAR_UTILITY` не меняет Tier 6 | ручная проба §5 | `fee` одинаков |
