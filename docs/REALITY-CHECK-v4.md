## 1. Главное: Discovery перестал быть «зелёным в тесте»

Это тот самый пункт, ради которого писался документ.

В v3 Discovery был механикой, проверенной на loopback. К `2.26.1` он **готов к
runtime** — и вот в каком смысле это утверждение защищено:

| Что значит «готов к runtime» | Чем подтверждено |
| :--- | :--- |
| Воркер объявляет себя в DHT и **переобъявляется** до истечения TTL | `test-reannounce-e2e.js`, **9/9** |
| Клиент находит провайдера **по CID** и открывает поток | `test-discovery-e2e.js`, **12/12** |
| Найденный провайдер — **именно ожидаемый** узел, а не «какой-то» | там же, проверка 4.3 с `--expect-peer` |
| Запись воркера подписана Ed25519 и **подделка отвергается** | там же, 5.4 и 5.5 |
| Мост на проде поднимает оба seed и видит связь | `Seed : 1/1` у seed1 и seed2 |
| HTTP-вход для клиента | `GET /p2p/discover` + `discovery-client.js` |
| Задача уходит на конкретный узел по `targetPeerId` | `bridge.js`, блок 4 |

**Чего это не значит.** «Готов к runtime» здесь = «механика доведена до состояния,
в котором её имеет смысл запускать на живой машине». Это **не** «работает у
пользователя за роутером» — см. §4.

## 2. Тихий дефект, который был найден при закрытии

Отдельный раздел, потому что он важнее любой закрытой галочки.

**Гейт запускал `test-discovery-e2e.js` без `--expect-peer`.** Из-за этого проверка
4.3 («найденный провайдер совпал с ожидаемым») уходила в `SKIP`, и набор показывал
**11/11**, ни разу не выполнив сверку адресата.

Это ровно тот класс отказа, с которого началась вся история с Discovery: проверка
существует, выглядит зелёной и не стоит на пути релиза. Набор из 11 зелёных
проверок создавал впечатление, что «нашёл того, кого искал» доказано, — хотя
доказывалось лишь «нашёл кого-то».

**Исправлено в `scripts/verify.sh`:** `peerId` теперь **вычисляется** из seed
(`peerIdFromPublicKey(publicKeyFromSeed(...))`) и передаётся флагами
`--worker-seed` и `--expect-peer`. Вычисляется, а не вписано константой: вписанный
`peerId` разошёлся бы с seed при первой же правке фикстуры, и проверка снова стала
бы самосогласованной.

После правки набор даёт **12/12** — 4.3 выполняется, а не пропускается.

## 4. NAT не проверен — и это следующий шаг, а не мелочь

**Уровень C пуст.** Ни один прогон не проходил через домашний роутер.

Все доказательства P2P — это либо процессы на loopback (уровень A), либо запросы с
самого VPS к самому себе (уровень B). Узел без NAT — не то, ради чего писался relay.

Три вещи, которые ломают код, работающий на loopback, и не видны в тестах:

1. **Внешний адрес меняется** (CGNAT, смена IP) — объявленный multiaddr протухает.
2. **UDP режется** — QUIC не поднимется, останется TCP.
3. **Пакеты теряются** — handshake удлиняется, таймауты могут не хватить.

### Что именно имеется в виду под словом «адрес»

Важное уточнение, чтобы не искать не то. Воркер слушает
`/ip4/127.0.0.1/tcp/0` и `/p2p-circuit`: **входящего публичного адреса у него за NAT
не будет и не должно быть.** Он дозванивается до моста сам.

`bridge.worker_addresses` — это **TAR-кошельки `0x…`** каналов задач, а не сетевые
адреса. Пустой список при `connections: 1` означает «пир подключён, канала задач
нет», и это диагностический факт, а не косметика.

Поэтому критерий успеха NAT-теста — `connections` **и** `channels`, а не «публичный
адрес в реестре».

### Живое состояние на момент среза

```
bridge.ok:        true
connections:      1
worker_addresses: []
channels:         0
active_workers:   0   (llm_mode: deterministic_fallback)
```

Это **честный ноль**: мост жив, но воркеров нет. Именно это состояние NAT-тест
должен изменить первым. Пока `active_workers: 0`, сети нет — и называть её сетью
нельзя.

### Как закрывать

`worker-demo.js --test-p2p` на машине владельца за домашним роутером. Флаг
принудительно выключает WS, поэтому успешная задача доказывает **именно libp2p**,
а не «что-то из двух путей». Пошаговая инструкция — `docs/NAT-TEST.md`, включая
таблицу «как отличить "NAT не пробит" от "воркер не стартовал"».

## 5. Что найдено при подготовке этого документа

Две поправки к формулировкам, которые иначе ушли бы в материалы как факты.

**1. Лога `peer-auth` не существует.** В `p2p-node/peer-auth.js` нет ни одного
`console.log`: модуль возвращает вердикт `{ok, address}` вызывающему, а печатают
мост (`[bridge]`) и воркер (`[p2p-worker]`). Инструкция «проверьте peer-auth лог»
отправила бы владельца искать несуществующий файл. Диагностика ведётся по
`[p2p-worker]` и журналу `p2p-bridge.service`.

**2. `worker_addresses` — не сетевой адрес.** Подробно в §4. Это то поле, которое
легче всего прочитать неправильно: оно выглядит как «адреса воркеров», а содержит
кошельки.

## 6. Хрупкое — то, что нельзя подавать как боевое

| Хрупкое место | Факт | Почему важно |
| :--- | :--- | :--- |
| NAT не проверен | уровень C пуст | «P2P работает у пользователя» — не доказано |
| Оба seed на одном VPS | общий диск, провайдер, systemd | падение машины уносит оба |
| 256 резерваций relay | расчётный предел | 256 живых воркеров не поднимались |
| Миграция legacy JSONL | на реальных данных не гонялась | путь миграции проверен только на фикстурах |
| Датасет обучения открыт | `distill-*.jsonl`, `mode 0o600` | шифрование at-rest верно для БД, **не** для JSONL |
| Локальный контейнер | 528 МБ свободно (95%) | следующий `npm ci` может упасть; VPS здоров (17%) |

### Как это формулировать

| Нельзя | Можно |
| :--- | :--- |
| «P2P работает» | «P2P проверен на loopback и через боевой мост; **NAT — нет**» |
| «Discovery работает у пользователей» | «Discovery готов к runtime; прогон за NAT — следующий шаг» |
| «Децентрализованная сеть» | «механика мульти-seed проверена; второй оператор — в плане» |
| «Relay решает NAT» | «relay отвечает на проде; за домашним NAT не проверен» |
| «Всё зашифровано» | «БД зашифрована; датасет обучения лежит открытым» |
| «1324 теста — продукт готов» | «1324 проверки механики; уровень C пуст» |

## 7. Что делать дальше

1. **NAT-тест** (`docs/NAT-TEST.md`) — единственное, что переводит Discovery из
   «готов к runtime» в «работает у человека». Блокер — нужен ПК владельца.
2. **Резервный SSH-ключ** (`scripts/generate-backup-key.md`) — процедура готова,
   ждёт машины владельца.
3. **Второй seed у другого оператора** — снимает «одна машина = вся сеть».
4. **Миграция legacy JSONL на копии боевых данных** — до того, как обещать
   «шифрование датасета».
5. **Чистка локального контейнера** — иначе следующий `npm ci` упадёт на 95%.

Зелёный уровень B не отменяет пустой уровень C. Пока C пуст, `v2.27.0` с тегом не
ставится: тег — это утверждение, что продукт работает у пользователя, а не что
механика согласована сама с собой.
