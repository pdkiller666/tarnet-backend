## 1. Идея: что это за проект и зачем

### 1.1. Проблема, которую решаем

Прогон больших языковых моделей (70B–405B) требует GPU-фермы. Попытка «разрезать» одну
модель по слоям между домашними ПК (**pipeline parallelism**) упирается в **«Стену
задержки»**: авторегрессия требует синхронной пересылки тензоров активаций на каждом
токене. При пинге 20–50 мс ответ замедляется до секунд на слово. Это не вопрос
инженерии — это физика: задержка умножается на число слоёв на каждом шаге генерации.

### 1.2. Ответ проекта

Вместо распиливания монолита — **роевая оркестрация автономных малых моделей**
(SLM 0.5B–7B+, квантование INT4 / Q4_K_M / BitNet) с доменными LoRA-адаптерами.
Каждый узел держит модель **целиком** в своей памяти и решает узкую подзадачу со
скоростью своего чипа. Сеть не ускоряет одну задачу — она **масштабирует пропускную
способность** для независимых задач.

$$\text{Throughput}_{\text{Swarm}} \approx \sum_{i=1}^{N} (\text{TPS}_i \times \text{Uptime}_i \times \text{Reliability}_i) - \text{Overhead}_{\text{routing + crypto}}$$

### 1.3. Два вектора роста

1. **Compute Scaling** — больше узлов = линейно больше пропускной способности; задержка
   падает за счёт ликвидации очередей и точного сопоставления «профиль задачи ↔ профиль узла».
2. **Knowledge Scaling** — умнее не от «слепого обучения», а через воронку селекции:
   `Experience Buffer` → `Preference Dataset (DPO)` → ночное дообучение (`Micro-LoRA / MeZO`)
   → сжатие адаптера (Trim 80%, INT8, CSR) → **Benchmark Gate / Ratchet Rule** с авто-откатом.
   TIES-Merging — Фаза 2.5, в коде его нет; реализовано только сжатие.

### 1.4. Экономический смысл

Участник отдаёт простаивающий compute и получает `$TAR` за полезную работу. Плательщик
покупает инференс дешевле облака, потому что нет наценки за дата-центр. Токен должен
иметь **внутреннюю утилизацию** (инвариант ≥50%): заработанное тратится внутри сети,
а не только выводится в фиат.

### 1.5. Приватность

Три изолированных контура, смешивать трафик между ними запрещено:

| Контур | Узлы | Правила |
| :--- | :--- | :--- |
| **Synapse Private** | Tier 1–3 | Onion Routing + TEE + шифрование обратного пути. PII разрешены, данные не покидают рой |
| **Synapse Extended** | Tier 1–3 + Tier 6 (BYOK) | Внешний API только если structured-PII гейт не нашёл совпадений и есть согласие в UI |
| **Synapse Enterprise** | Tier 1–3 + Tier 5 Cloud | SLA 99.99%, облачные TEE, аудит, маркировка `Processed by Cloud Anchor` |

### 1.6. Двойная идентичность бренда

| Контур | Инфраструктура | ИИ-ядро | Тикер | Где |
| :--- | :--- | :--- | :--- | :--- |

## 3. Экономика: формулы и константы

### 3.1. Единица работы (CWU)

$$W_i = N_{\text{tokens}} \times \kappa_{\text{tier}} \times \gamma_{\text{verify}}, \qquad \gamma \in \{0,1\}$$

### 3.2. Двухпоточная награда

$$\text{Reward}_i = \text{Fee\_Reward}_i + \text{Block\_Reward}_i$$

$$\text{Fee\_Gross}_i = \frac{W_i \times \text{PRICE\_USD\_PER\_1M}}{10^6 \times \text{USD\_PER\_TAR}}, \qquad \text{Fee\_Reward}_i = \text{Fee\_Gross}_i \times (1-\phi)$$

$$E_{\text{epoch}}(t) = E_0 \cdot 2^{-t/T_{\text{halving}}}, \qquad \omega_i = \sqrt{\text{Stake}_i} \times \text{Reputation}_i$$

$$\text{Block\_Reward}_i = \min\left(E \cdot \frac{W_i\omega_i}{\sum_k W_k\omega_k},\; E \cdot \text{MAX\_RECEIPT\_SHARE\_OF\_EPOCH}\right)$$

### 3.3. Константы (`config.js`, 271 строка)

| Константа | Значение | Смысл |
| :--- | :--- | :--- |
| `PRICE_USD_PER_1M_TOKENS` | `0.20` | базовая ставка = Protocol Price Floor (отдельной константы floor нет) |
| `USD_PER_TAR` | `20` | 1 TAR = $20; сумма в USD **делится** на 20 |
| `TIER_WEIGHTS` | `{nano:0.1, base:1.0, expert:4.0}` | `$0.02 / $0.20 / $0.80` за 1M |
| `PROTOCOL_FEE_RATE` (φ) | `0.05` | = `BURN_RATE 0.025` + `TREASURY_RATE 0.025` |
| `LORA_ROYALTY_RATE` | `0.05` | 5% **от Fee_Reward** (не от gross), автору адаптера |
| `INITIAL_BLOCK_REWARD` (E₀) | `50` TAR/эпоха | **непрерывное затухание** `2^(-epoch/365)`, не ступенчатый халвинг |
| `MAX_RECEIPT_SHARE_OF_EPOCH` | `0.25` | потолок одного чека |
| `DECIMALS` | `6` | гарантирует `delta === 0` |
| `MIN_RECEIPT_TOKENS` | `50` | нижняя граница порога батчинга |
| `TAR_UTILITY_BURN_RATE` / `TREASURY_RATE` | `0.01` / `0.01` | ставка утилизации 2%, единственное место — `economics.js:115-116` |
| `FAUCET.AMOUNT_TAR` / `IP_LIMIT` | `0.01` / `3` | разовая выдача на адрес, потолок на HMAC-хеш IP |

**Батчинг:** порог генерации чека — `max(50, tokens_for_nonzero_payout(tier))`:
`base` = 50, `nano` = 500, `expert` = 13. Ключ накопления — воркер + тир + адаптер,
потому что `W = tokens × κ`: смешивать тиры нельзя, это занизило бы выплату в κ раз.

**Замкнутый цикл:** при `POST /inference` с `clientAddress` списывается 100% Fee_Gross:
исполнителю 95% (или 90.25% с роялти), протоколу 5%. Полный круг самопотребления стоит ровно 5%.

### 4.1. Три дороги к воркеру (не дублирование, а доступность)

1. **Входящий WebSocket** (`/p2p/worker`, `ws-inbound.js`, 601 стр.) — воркер держит
   **исходящее** соединение, сервер шлёт кадр `TASK`. Портов воркер не открывает.
   Ed25519-хендшейк с nonce, TOFU по адресу (`ADDRESS_KEY_MISMATCH` при подмене ключа).
2. **P2P через мост** (`p2p-bridge.service` + `p2p-channel-pick.js`) — задача уходит по
   libp2p тому адресату, который назван. Первый кадр потока — `hello` с Ed25519-подписью,
   allowlist `authorized-peers.json` пишет backend-api из `ws_worker_auth`.
3. **HTTP-опрос** (`GET /worker/poll`) — фолбэк для воркера без WS и без P2P.

Порядок не настраивается флагом, а следует из состояния строки задачи (`server.js:7215`):
WS первым, P2P только пока строка `pending`. Это защита от двойной генерации.
Переключателя «только P2P» **не существует** (`grep P2P_ONLY|FORCE_P2P|disableWs|WS_DISABLED` → пусто).

## 7. Честная оценка

**Работающий протокол с доказанным P2P-транспортом, ожидающий сети исполнителей.**
Не «работающая сеть роевого ИИ».

Три вещи, которые вышли лучше плана:

1. **Детерминированный леджер вместо лотерей.** Лотерея давала «может повезёт»; леджер
   даёт `delta === 0`, проверяемый одной командой. Любая недостача видна сразу — в v1.0
   её нельзя было увидеть в принципе.
2. **Безопасность стала архитектурной.** Была дыра: `GET /worker/poll` отдавал первую
   pending-задачу любому спросившему вместе с `sessionKey` в открытом виде — шифротекст
   и ключ в одном ответе. Теперь Ed25519 на `/worker/submit`, TOFU по адресу в WS.
3. **P2P и рой доказаны в бою, а не только собраны.** Две задачи через мост 07.11,
   рой с живым обрывом запроса 18:07.

Главные разрывы:

- **Сеть не планетарная.** 154 адреса — все, кто когда-либо регистрировался; онлайн 0.
- **«Децентрализация» ограничена.** Узлы выполняют работу независимо, но координатор один.
- **Экономика платит сама себе.** 95.16% выплат — эмиссия по формуле, не выручка.
- **Внутренняя утилизация — ноль** (`0.000012 TAR` против инварианта ≥50%).
- **TAR оплачивает заявленное, а не сделанное** — верификации работы нет.

Экономический тупик в одной строке: эмиссия затухает (`24.2` TAR/сутки на эпохе 382
против 50 в начале), платящего спроса нет, потому что нет пользователей, а пользователей
нет, потому что `active_workers: 0`. P2P этот круг разрывает не сам по себе, а только
если приведёт реальных исполнителей с реальными моделями.

## 11. Сводка для внешнего читателя (без округлений)

> TarNet — протокол распределённого инференса малых языковых моделей. Узлы держат
> модель целиком и решают независимые задачи; сеть масштабирует пропускную способность,
> а не ускоряет одну задачу. Работа учитывается детерминированно (`delta === 0`),
> чеки подписаны Ed25519 и связаны хеш-цепочкой, приватность промпта обеспечивается
> Onion Routing. Транспорт до исполнителя — WebSocket, libp2p или HTTP-опрос.
>
> Состояние на 07.11.2026: протокол работает и проверен 1229 автотестами и боевыми
> прогонами через P2P и рой. Сети исполнителей нет: 0 узлов онлайн, ответы отдаёт
> заглушка. Координатор централизован (один сервер), верификация факта выполнения
> работы не реализована, смарт-контрактов нет, обучение адаптеров не запускается.
> 95% выплат — эмиссия, не выручка; внутренняя утилизация токена близка к нулю.
