# NAT-TEST — проверка воркера за домашним роутером

> **Проверено на `2.26.6` (коммит `bf5b38d` + правки `2.26.6`).** Если на проде другая
> версия — NAT-тест не запускать, сначала докатить. Проверить одной командой:
> `curl -s https://v1107336.hosted-by-vdsina.com/health | grep -o '"buildVersion":"[^"]*"'`.
> Причина простая: разделы ниже описывают поля и пути, которые менялись между
> сборками, и отчёт со старой версии не отличим от отчёта о дефекте новой.

**Кому.** Владельцу проекта. Один раз, когда появится домашний ПК.
**Зачем.** Все нынешние доказательства P2P сняты на loopback и на боевом мосту
в одном контейнере. Они не отвечают на вопрос, который решает сеть: **доходит ли
воркер за NAT до моста, и остаётся ли он виден после этого.**

**Что это доказывает, а что нет.** Тест доказывает достижимость: воркер стартовал
на машине за роутером, поднял исходящее соединение, открыл поток задач и объявил
себя. Он **не** доказывает, что воркер получил входящий публичный адрес — за NAT
его и не будет, и это нормально (см. §7).

**Чего этот документ не покрывает.** Bitcoin-совместимый файрвол на стороне
провайдера, двойной NAT у CGNAT, VPN. Если роутер выдаёт «серый» адрес вида
`100.64.x.x` — это CGNAT, и тест может пройти по relay-пути. Такой результат
записывайте отдельно, не выдавайте за прямой.

---

## 1. Поставить свежий воркер

Воркер — **не один файл**. `worker.js` умеет только WebSocket; P2P-транспорт
живёт в отдельном пакете `p2p-node`, который приезжает своим архивом и ставит
зависимости через `npm ci` (105 МБ libp2p). Скачать только `worker.js` и ждать
P2P — самая частая ошибка.

**Правильный путь — установщик с сайта.** Он делает четыре шага сам:

| Шаг | Что происходит |
| :--- | :--- |
| 1 | `GET /download/worker.js` → воркер |
| 2 | `GET /download/p2p-node.zip` → `p2p-node/` |
| 3 | `npm ci --omit=dev` внутри `p2p-node/` — ставит libp2p |
| 4 | Создаёт `start.sh` / `start.cmd` с `cd` в папку установки |

**Куда ставится:**

- macOS / Linux: `~/.tarnet`
- Windows: `%LOCALAPPDATA%\TarNet`

Установщик скачивается на странице `/app/` с сервера
(`https://v1107336.hosted-by-vdsina.com/app/`).

### 1.1. Убедиться, что транспорт реально встал

Установщик печатает строку о Discovery. Ищите её в выводе:

```
Discovery: модели=... устройство=...
```

Если вместо этого:

```
Discovery: capabilities не определены — воркер не объявится в DHT
```

— воркер поднимется, но в DHT его не будет, и тест ниже провалится **не по
вине NAT**. Причина — не найдены модели (Ollama не запущена) либо `npm ci`
не прошёл. Чинить здесь, до всякого NAT-теста:

```bash
cd ~/.tarnet/p2p-node && npm ci --omit=dev
```

Признак успеха — `node -e "import('libp2p').then(()=>console.log('libp2p ok'))"`
печатает `libp2p ok` из папки `p2p-node`.

## 2. Запустить с `--test-p2p`

### Почему именно этот флаг

`--p2p` поднимает транспорт, но **WebSocket остаётся приоритетным**: если WS жив,
задача уйдёт по WS. Успех тогда ничего не значит — вы проверите WS и назовёте это
P2P.

`--test-p2p` выключает WS **принудительно**. Значит выполненная задача
доказывает P2P, а не «что-то из двух».

Исторически для этого требовался флаг самого Node
(`node --no-experimental-websocket tarnet-worker.js --p2p`). Он длинный, его
легко спутать с `--p2p`, и ошибка не даёт понятного отказа — воркер молча уходит
на WS. Поэтому флаг перенесён в воркер (`worker-demo.js`, `TEST_P2P`).

### macOS / Linux

```bash
cd ~/.tarnet
./start.sh --test-p2p
```

`start.sh` уже делает `cd` в папку установки и выставляет `TARNET_API_URL`,
`P2P_MODEL_FAMILIES`, `P2P_DEVICE_CLASS`. Аргументы он передаёт воркеру как есть
(`"$@"`), поэтому флаг доходит.

### Windows

```cmd
cd /d "%LOCALAPPDATA%\TarNet"
start.cmd --test-p2p
```

Либо из PowerShell:

```powershell
Set-Location "$env:LOCALAPPDATA\TarNet"
.\start.cmd --test-p2p
```

### Почему `cd` обязателен

Воркер ищет `p2p-node/` **относительно текущей папки**. Запуск ярлыком,
из автозапуска или из чужой папки терял транспорт молча — воркер поднимался,
WS работал, и всё выглядело исправным. Это исправлено в шаблонах `start.*`
(в них вписан `cd`), но ручной запуск `node worker.js` из другой папки снова
сломает поиск.

## 3. Что должно появиться в логе

Воркер печатает строки с префиксом `[p2p-worker]`. По ним и идёт диагностика —
**другого журнала нет**.

Порядок при исправном старте:

```
[p2p-worker] bootstrap: https://v1107336.hosted-by-vdsina.com/p2p/bootstrap
[p2p-worker] мой peerId: 12D3KooW…
[p2p-worker] адрес из bootstrap: /dns4/…/tcp/4001/p2p/12D3KooW…
[p2p-worker] подключено: 12D3KooW…
[p2p-worker] поток задач открыт: /tarnet/task/1.0.0
[p2p-worker] hello отправлен от 0x…
[p2p-worker] запись объявлена: seq 3, до 2026-…
```

**Ключевая строка — `hello отправлен от 0x…`.** Она означает, что мост принял
воркера как авторизованного (иначе поток закрылся бы с отказом).

Где смотреть лог:

- macOS/Linux: `~/.tarnet/worker.log` (установщик запускает воркер туда через `nohup`)
- Windows: окно `TarNet Worker`; при запуске из `start.cmd` вывод идёт на экран

## 4. Проверить, что мост видит ЭТОТ воркер

### 4.1. Главная проверка — `check-autostart.js`

Он сверяет **адрес вашего ПК** из `~/.tarnet/worker.json` со списком каналов на
сервере. Это отвечает на нужный вопрос: «в сети мой узел», а не «в сети
кто-нибудь».

```bash
node scripts/check-autostart.js --window 60 --interval 5
```

Ожидаемо: адрес найден, `active_workers >= 1`, `bridge.connections >= 1`.
Коды возврата: `0` — узел в сети; `1` — не дождались; `3` — сервер старой сборки.

### 4.2. Поправка по `worker_addresses` — читать внимательно

В директиве сказано «проверить, что `worker_addresses` содержит адрес». Уточнение
по коду (`p2p-node/bridge.js`, `worker_addresses`):

`worker_addresses` — это **TAR-кошельки `0x…`** авторизованных каналов, а **не
сетевой адрес**. Там не будет ни `IP:порт`, ни `/ip4/…/tcp/…`. Поэтому:

- `worker_addresses: ["0x7d4e…"]` — воркер **есть**, канал авторизован;
- `worker_addresses: []` при `connections: 1` — кто-то подключён, но **канала
  задач нет**: либо `--test-p2p` не дошёл, либо воркер не авторизован.

Сетевые адреса смотрите в `connected_peers` и в `[p2p-worker] адрес соединения:`,
а не в `worker_addresses`.

### 4.3. Сырой ответ сервера

```bash
curl -s https://v1107336.hosted-by-vdsina.com/p2p/status
```

Поля, которые важны:

| Поле | Что значит |
| :--- | :--- |
| `bridge.connections` | живых libp2p-соединений у моста |
| `bridge.worker_addresses` | `0x…` кошельки с открытым каналом задач |
| `bridge.tasks.channels` | сколько каналов задач открыто |
| `bridge.connected_peers` | peerId подключённых узлов |

`connections: 1` при `channels: 0` — это «пир подключён», а не «сеть работает».
Нужны оба: соединение **и** канал.

## 5. Если адрес не появился

Директива предлагает «проверить `peer-auth` лог». **Такого лога нет:** в
`p2p-node/peer-auth.js` нет ни одного `console.log` — модуль возвращает вердикт
`{ok, address}` вызывающему, а печатает уже мост и воркер. Искать файл
`peer-auth.log` бессмысленно.

Проверяйте по этим следам, сверху вниз:

| Что видно | Где смотреть | Что значит |
| :--- | :--- | :--- |
| Нет строк `[p2p-worker]` вообще | `worker.log` | P2P не стартовал: нет `p2p-node/`, не `--test-p2p`, не тот `cwd` |
| `рядом нет p2p-node/p2p-worker.js` | вывод воркера | не распакован архив — переустановить |
| `нет: …/node_modules/libp2p` | вывод воркера | не выполнен `npm ci` в `p2p-node` |
| `bootstrap вернул ok, но без адресов` | `[p2p-worker]` | мост не отдал multiaddr — смотреть мост на VPS |
| `поток задач не открылся: …` | `[p2p-worker]` | мост закрыл поток: не авторизован, смотреть `[bridge]` на VPS |
| `поток задач не открываю: NO_WORKER_KEY` | `[p2p-worker]` | нет ключа воркера: не выполнен вход/привязка |
| `hello отправлен`, но `worker_addresses: []` | `/p2p/status` | канал открылся и закрылся — смотреть `[bridge]` на VPS |
| Всё зелёное локально, сервер пуст | `/p2p/status` | разные серверы: `TARNET_API_URL` указывает не туда |

На VPS встречная сторона видна в журнале моста:

```bash
ssh root@195.63.131.172 "journalctl -u p2p-bridge.service -n 50 --no-pager | grep -E '\[bridge\]|worker'"
```

## 6. Как отличить «NAT не пробит» от «воркер не стартовал»

Это главный вопрос теста, и он решается первой строкой лога.

| Наблюдение | Вердикт |
| :--- | :--- |
| Строк `[p2p-worker]` нет совсем | **Воркер не стартовал.** NAT ни при чём |
| Есть `bootstrap: …`, нет `подключено:` | **Проблема исходящего пути.** Файрвол/прокси/сеть |
| Есть `подключено:`, нет `поток задач открыт` | **Дошёл, но не авторизован.** Не NAT |
| Есть `поток задач открыт` и `hello отправлен` | **P2P работает.** NAT пробит по исходящему пути |
| Локально всё есть, `/p2p/status` пуст | **Разные серверы** либо мост не тот |

Правило: **если в логе нет ни одной строки `[p2p-worker]` — вы проверяете не NAT,
а запуск.** Не начинайте с роутера.

## 7. Чего ждать от адресов за NAT

Воркер слушает `/ip4/127.0.0.1/tcp/0` и `/p2p-circuit`. Публичного адреса у него
**не будет и не должно быть** — он дозванивается до моста сам, а не ждёт входящих.

Поэтому:

- отсутствие входящего публичного адреса — **норма**, а не отказ;
- третий адрес `/p2p-circuit` — резервация у relay, а не замена прямому TCP;
- критерий успеха в `/p2p/status` — `connections` **и** `channels`, а не
  «публичный адрес в реестре».

Сервер намеренно **не** требует публичного адреса: иначе домашний воркер за NAT
всегда считался бы «неготовым», хотя работает.

## 8. Что записать в отчёт

Четыре факта, без которых тест недоказуем:

1. строки `[p2p-worker]` от `bootstrap:` до `hello отправлен` (копией);
2. вывод `check-autostart.js` (или `--json`);
3. `bridge.connections` и `bridge.tasks.channels` из `/p2p/status`;
4. тип подключения к интернету: прямой / CGNAT (`100.64.x.x`) / VPN.

Пункт 4 обязателен: результат за CGNAT и за прямым NAT — разные факты, и
смешивать их в отчёте нельзя.

**Если тест зелёный** — `v2.27.0` с тегом и записью в `PROJECT-HISTORY.md`.
**Если красный** — раздел 5 говорит, какой именно след смотреть, и это уже не
«P2P не работает», а конкретная строка.
