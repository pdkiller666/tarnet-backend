# Этап 10 — чеклист готовности

**Этап 10 `MASTER-PLAN` — это транспорт WebRTC PWA↔воркер.** Второй seed у другого
оператора — этап 11, не этот. До 11.11.2026 `MASTER-PLAN` держал на номере 10
второй seed, а этот чеклист и `ROADMAP` — WebRTC; номер читался двояко, теперь — нет.

**Составлен:** 2026-11-11, по коду `2.28.4` (прод `buildVersion: 2.28.4`).
**Статус:** 2 из 5 пунктов закрыт (A3 — 11.11 20:0x; WebRTC-прототип — `2.28.4`).

Порядок обязателен: каждый следующий пункт опирается на доказательство
предыдущего. Пропуск даёт «работает» без проверки — именно так `found: 0`
читался как «discovery сломан», когда на самом деле не было воркера.

---

## 1. A3 — воркер в сети, `found ≥ 1` — **ЗАКРЫТ 11.11.2026 20:0x MSK**

**Что доказывает.** Клиент находит воркера через DHT без участия сервера:
воркер объявил провайдер-запись, клиент по `model` вычислил CID того же
бакета и получил того же узла.

**Как проверить обе стороны.**

```bash
curl -s "https://v1107336.hosted-by-vdsina.com/p2p/discover?model=qwen2.5-coder:1.5b"
# ожидание: "found": 1, "rejected": []
curl -s https://v1107336.hosted-by-vdsina.com/health
# ожидание: active_p2p_workers: 1, p2p_model_families: ["qwen2.5-coder"], llm_mode: "worker"
```

**Если `found: 0`** — смотреть `rejected[]` (там причина отказа записи:
подпись, TTL, sequence, адрес) и лог моста, а не код разбора. Пустой
`rejected` при `found: 0` означает «записи не было вообще», то есть воркер
не объявился.

**Состояние на 11.11.2026 20:0x MSK — ЗАКРЫТ.** Владелец запустил воркер, обе
стороны сошлись на живом проде:

```json
GET /p2p/discover?model=qwen2.5-coder:1.5b
{"found":1,"providers":1,"rejected":[],"elapsed_ms":166,
 "workers":[{"peerId":"12D3KooWLBV8uzCxa7Nz…",
             "multiaddrs":["/ip4/45.144.49.113/tcp/37628/p2p/12D3KooWLBV8uzCxa7Nz…"]}]}

GET /health
{"active_workers":1,"active_p2p_workers":1,"llm_mode":"worker",
 "p2p_model_families":["qwen2.5-coder"]}
```

Прежнее состояние 17:0x (`found: 0`, `active_p2p_workers: 0`, `llm_mode:
deterministic_fallback`, `reason: no_workers`) было честным нулём: воркер не
запущен, объявлять нечего.

**Оговорка, которая не даёт считать пункт шире, чем он есть.**
`45.144.49.113` — публичный адрес **VPN** на ПК владельца, а не домашнего
роутера. Значит доказан сценарий «публичный IP»; без VPN провайдер, скорее
всего, спрятал бы ПК за CGNAT. Работа за домашним NAT/CGNAT остаётся
непроверенной и требует TURN либо relay-моста — это отдельная проверка, а не
следствие закрытия A3.

**Что нужно от владельца** (PowerShell, папка воркера):

```powershell
cd "$env:LOCALAPPDATA\TarNet"
$env:TARNET_API_URL="https://v1107336.hosted-by-vdsina.com"
$env:TARNET_PUBLIC_URL="https://v1107336.hosted-by-vdsina.com"
$env:P2P_MODEL_FAMILIES="qwen2.5-coder"
$env:P2P_DEVICE_CLASS="cpu"
$env:P2P_RUNTIMES="ollama"
node tarnet-worker.js --test-p2p
```

Строки, которые должны появиться (точные, из `p2p-node/p2p-worker.js`):

```
[p2p-worker] адрес из bootstrap: /dns4/v1107336.hosted-by-vdsina.com/tcp/4001/p2p/12D3KooW…
[p2p-worker] подключено: 12D3KooW…
[p2p-worker] hello отправлен от 0x…
[p2p-worker] поток задач открыт: …
[p2p-worker] объявлен провайдер: bafkreifkuzjpr65n7jpgrfdpebe3dhioqnyzzo66ojguqqmmm46euzi3mi
[p2p-worker] запись объявлена: seq 1, до <ISO>
```

`--test-p2p` намеренно выключает WS и опрос — задачи идут только по libp2p.
Поэтому `active_workers` (WS-реестр) останется `0`, а считать надо
`active_p2p_workers`.

**Предусловия, проверенные 11.11.2026:** порты `4001` и `4002` открыты
снаружи (`/dev/tcp` → открыт), `/p2p/bootstrap` отдаёт публичный multiaddr,
allowlist содержит `0x3b7928c88de427c5b27d78ca63dde8c80823267f`. Если папка
`p2p-node\` рядом с воркером отсутствует — транспорт не поднимется, будет
строка `рядом нет p2p-node/p2p-worker.js`.

**Чего это НЕ доказывает.** Что узел поднимется сам после перезагрузки —
это пункт 2. И что за симметричным NAT соединение установится — тут только
STUN/host-кандидаты, нужен TURN.

## 2. P1.2 — автономность после ребута — **ОТКРЫТ, блокирован пунктом 1**

**Что доказывает.** Узел живёт без ручного запуска: после перезагрузки ПК
воркер встаёт сам, регистрируется и держит канал.

**Порядок.** Только после `found ≥ 1`. Иначе тест неотличим: код `1` будет
означать и «автозапуск сломан», и «P2P не настроен».

```bash
node scripts/check-autostart.js --p2p --address 0x3b7928c88de427c5b27d78ca63dde8c80823267f --window 600
```

**Ожидание:** код `0`, `active_p2p_workers ≥ 1`, `bridge.connections ≥ 1`,
адрес `0x3b79…` в `bridge.worker_addresses`.

**Коды:** `0` готово, `1` тайм-аут, `2` плохие аргументы, `3` сборка старше
`2.24.0` без `worker_addresses`. `--p2p` обязателен: воркер с `--test-p2p`
не виден в WS-реестре, и без флага исправная машина получила бы «провал».

**Если код `1`** — смотреть лог `peer-auth` (где рвётся проверка) и
`journalctl -u tarnet` на VPS. Не перезапускать вручную до разбора: ручной
запуск маскирует дефект автозапуска.

## 3. WebRTC-прототип — **ЗАКРЫТ** (`2.28.4`)

**Доказано живьём.** `p2p-node/webrtc-peer.js` на `werift` (чистый JS),
DataChannel открыт, ответ `pong:` пришёл по каналу. `scripts/webrtc-test.js`
— 5/5 проверок, код `0`. Сигналинг идёт каналом `task`: отдельного
сигнального сервера нет, и заводить его ради прототипа значило бы построить
ту самую центральную точку, которую Этап 10 убирает.

**Три дефекта нашёл прогон, а не чтение:** кадр без `taskId` — сирота (мост
сопоставляет только по нему); `onMessage` в werift — объект-событие,
присваивание функции ломает библиотеку; `onOpen`/`onClose` не существуют —
`undefined` без ошибки, неотличимый от «канал не открылся».

**Перепроверено 11.11.2026 20:0x MSK:** `node scripts/webrtc-test.js` → код `0`,
5/5 проверок. Важно, что именно это доказывает: тест поднимает **свой** мост на
свободном порту `127.0.0.1`, **свой** воркер и **свою** bootstrap-заглушку,
`HOME` подменяет временным каталогом. К живому воркеру владельца и к его VPN он
не подключается — значит доказан транспорт `werift`↔`werift`, а не путь через
внешний NAT.

## 4. WebRTC в PWA — **НЕ НАЧАТ**

**Что нужно.** `RTCPeerConnection` в браузере, `TaskGrant` с подписью
Ed25519 (ключ в IndexedDB), проверка на воркере через `peer-auth.js` — тот
же модуль, что проверяет `hello`, второго пути проверки не заводить.

**Риск, который надо принять заранее.** Safari и Firefox расходятся в
поддержке DataChannel и ICE. Тестировать труднее, чем сокет: нужны два NAT.

---

## 5. Замена `POST /inference` на `GET /p2p/discover` + WebRTC — **НЕ НАЧАТ**

**Что нужно.** Клиент сам находит воркера и говорит с ним напрямую; сервер
перестаёт быть путём трафика. WS-relay остаётся аварийным путём с явным
логом `[transport] WebRTC failed, using WS relay` — молчаливый откат
запрещён, иначе «работает по WebRTC» будет утверждением без доказательства.

**Чего это не обещает.** Прямого соединения при симметричном NAT: там нужен
TURN, а TURN — это сервер. Этап 10 убирает сервер из **типового** пути, а не
из всех.
