# NETWORK-CONTRACT v1

Контракт между **сервером TarNet** и **воркером**, который берёт задачи `/inference`.

Документ описывает только то, что работает в коде на момент `2.17.15-work-sig-attest`.
Каждое утверждение привязано к файлу и функции. Если документ расходится с кодом — прав код,
документ правится в тот же день (Code-First Rule).

Обозначения: **[КОД]** — реализовано и покрыто тестом; **[SPEC / ROADMAP]** — заявлено, но
в репозитории этого нет.

---

## 1. Кто кому доверяет

Три стороны и три разных доверия. Их нельзя смешивать: подпись воркера защищает очередь,
TLS защищает канал, а ключ сессии защищает промпт.

| Сторона | Что доказывает | Чем |
|---|---|---|
| Сервер → воркер | «это твоя задача» | `intendedWorker` в `worker_tasks` |
| Воркер → сервер | «это я, мой адрес» | Ed25519-подпись опроса над `TARNET_WORKER_POLL:<address>:<ts>` |
| Сервер → только воркер | «промпт читает лишь тот, кому он адресован» | `sessionKey` запечатан на ключ воркера (`box:v1`) |

Без первой строки задачу забирал бы любой; без второй — любой мог бы назваться чужим адресом;
без третьей — перехваченный ответ `poll` давал бы и замок, и ключ.

## 2. Регистрация и привязка ключа

### 2.1. `POST /node` — объявить себя

```json
{ "address": "0x<40 hex>", "model": "...", "installedModels": ["..."] }
```

Сервер **игнорирует** `stake`, `reputation` и `tier` из тела запроса. Это не послабление,
а закрытие дыры: раньше `POST /node` принимал `stake: 50000` и `reputation: 0.9` из тела, то есть
любой мог одним запросом получить максимальный вес маршрутизации.

- новый узел получает `BOOTSTRAP_STAKE = 10` и `BOOTSTRAP_REPUTATION = 0.5` **[КОД]**
- существующие ненулевые значения сохраняются (перезапись запрещена)
- ноль трактуется как «ещё не назначено» и заменяется на bootstrap

`BOOTSTRAP_REPUTATION = 0.5` **ниже** `MIN_VALIDATOR_REPUTATION = 0.8` намеренно: bootstrap-узел
получает вес маршрутизации, но не место в комитете валидаторов.

Вес маршрутизации: `routingWeight = sqrt(stake) × reputation` (`economics.js:91`). Узел с
`routingWeight = 0` не выбирается никогда; если таких нет вообще — `/inference` отдаёт `503`.

### 2.2. `POST /worker/handshake` — привязать ключ к адресу

```json
{
  "pubkey": "<64 hex — сырой Ed25519>",
  "timestamp": 1793630354294,
  "signature": "base64(sign('TARNET_WORKER_POLL:<address>:<timestamp>'))",
  "claimedAddress": "0x<40 hex>"
}
```

Ответ: `{ ok: true, address, boundAt }`.

Правила **[КОД]** (`server.js`, `app.post('/worker/handshake')`):

| Условие | Ответ |
|---|---|
| `pubkey` не 64 hex | `400 BAD_PUBKEY` |
| нет подписи | `400 SIGNATURE_REQUIRED` |
| `|now − timestamp| > 300000` | `401 TIMESTAMP_OUT_OF_WINDOW` |
| подпись не сходится | `401 BAD_SIGNATURE` |
| к адресу уже привязан **другой** ключ | `409 ADDRESS_KEY_MISMATCH` |
| иначе | `200 { ok: true }`, TOFU-привязка в `ws_worker_auth` |

`claimedAddress` необязателен. Если его нет — адрес **выводится из ключа**.

Почему заявка разрешена, хотя строгий вывод адреса из ключа безопаснее. Замерено на проде:
у живого воркера адрес `0xe56c…`, а из его же ключа выводится `0xb31f…` — демо-воркер исторически
брал адрес случайными байтами. Строгий вывод означал бы, что **единственный работающий узел не
может привязаться**, а его история начислений пропадает.

Что при этом не теряется: заявить чужой адрес нельзя, если к нему уже привязан ключ
(`ADDRESS_KEY_MISMATCH`). Захват свободного адреса не даёт работы — задача выдаётся только по
`intendedWorker`, а у неиспользованного адреса задач нет.

## 3. `GET /worker/poll` — получить задачу

```
GET /worker/poll?workerAddress=0x…&ts=<ms>&sig=<base64>&model=<имя>
```

Коды отказа **[КОД]** — порядок важен, это и есть контракт:

| Когда | Ответ | Что делать воркеру |
|---|---|---|
| ключ к адресу не привязан | `403 HANDSHAKE_REQUIRED` | `POST /worker/handshake`, затем повторить |
| ключ есть, нет `ts`/`sig` | `401 SIGNATURE_REQUIRED` | подписать `TARNET_WORKER_POLL:<address>:<ts>` |
| окно времени нарушено | `401 TIMESTAMP_OUT_OF_WINDOW` | проверить часы |
| подпись неверна | `401 BAD_SIGNATURE` | проверить, тем ли ключом подписано |
| лимит 240/мин с IP исчерпан | `429 too_many_requests` | ждать `retryAfterSec` |

`403`, а не `401`, в первой строке — намеренно. `401` значит «секрет не указан или не принят»;
здесь секрета **ещё не существует**, воркер не проходил handshake. Разные коды нужны, чтобы клиент
не чинил подпись там, где нужно сначала привязать ключ.

Лимит считается **до** проверки подписи. Иначе перебор подписей обходил бы ограничение: тысячи
`401` в секунду бесплатно.

Успешный ответ при пустой очереди: `{ "task": null }`. При задаче:

```json
{
  "task": {
    "taskId": "wt_…",
    "encryptedPayload": "enc:v1:…",
    "sessionKey": "box:v1:…",
    "keyEncryption": "box:v1",
    "encryption": "aes-256-gcm",
    "model": "qwen2.5-coder:1.5b",
    "tier": "base",
    "deadlineMs": 30000
  }
}
```

### 3.1. Два слоя шифрования

**Слой 1 — промпт: `enc:v1`, AES-256-GCM** **[КОД]**. Ключ сессии — 32 случайных байта на задачу,
живёт только в памяти сервера (`workerTaskKeys`). Промпт не попадает на диск открытым текстом:
владелец машины не читает промпты, и это не обещание, а свойство хранилища.

**Слой 2 — ключ сессии: `box:v1`** **[КОД]** (`worker-box.js`). Ключ шифруется на **публичный
ключ воркера**, привязанный при handshake.

Почему отдельным слоем. Раньше `sessionKey` ехал в том же ответе, что и шифротекст, открытым
base64. Один перехваченный `poll` — и у посредника и замок, и ключ. Шифрование задачи защищало от
дампа базы, но не от перехвата канала. С `box:v1` перехваченный ответ бесполезен без приватного
ключа воркера.

Схема: Ed25519 → X25519 (`u = (1+y)/(1−y)`), эфемерный ECDH, HKDF-SHA256 с обоими публичными
ключами в соли, AES-256-GCM. Формат: `box:v1:<ephPub>:<iv>:<tag>:<ct>` (все поля base64).

Почему X25519, а не RSA: у воркера в привязке лежит Ed25519 (64 hex). RSA есть лишь у 3 узлов из
147 — опираться на него нельзя. Ed25519 и X25519 — одна кривая, конверсия формулой, без новых
зависимостей.

Если печать не удалась, сервер отдаёт открытый base64 с **явным** `keyEncryption: "none"`.
Молча подсунуть нечитаемое хуже, чем честно назвать формат.

### 3.2. `maxTokens` — потолок генерации

Предел едет **внутри зашифрованной части** задачи, а не отдельным полем кадра **[КОД]**. Иначе
потолок, названный сервером, лежал бы открытым текстом и мог быть подменён на любом посреднике —
а смысл потолка в том, чтобы ограничить именно воркер.

- сервер: `CONFIG.MAX_TOKENS_PER_TASK` = **8192** (`config.js`, env `MAX_TOKENS_PER_TASK`)
- воркер обязан применить его: Ollama — `options.num_predict`, OpenAI-совместимые — `max_tokens`

Воркер, игнорирующий `maxTokens`, — нарушение контракта: он может генерировать неограниченно
долго и держать задачу до `WORKER_TASK_TTL_MS`.

## 4. `POST /worker/submit` — вернуть результат

```json
{
  "taskId": "wt_…",
  "workerAddress": "0x…",
  "response": "текст ответа",
  "source": "live_llm",
  "model": "qwen2.5-coder:1.5b",
  "usage": { "completion_tokens": 128 }
}
```

`source` — **обязательное поле честности** **[КОД]**:

| `source` | Значение |
|---|---|
| `live_llm` | ответ дала модель на этом узле |
| `deterministic_fallback` | модель недоступна, вернулся шаблон |

Сервер пробрасывает это в ответ `/inference` и в `fallback_reason`. Воркер, который отвечает
шаблоном и ставит `live_llm`, ломает учёт начислений: шаблон не должен оплачиваться как работа
модели.

Порядок падения при недоступной модели: `worker → external_api → deterministic_fallback`
(`server.js:7255`). Каждое звено называет свою причину: `model_unavailable`, `worker_timeout`,
`no_workers`, `model_unverified`, `ollama_offline`.

---

### 4.1. `POST /work` — сдать работу напрямую (подпись обязательна)

Отдельный от `/worker/submit` путь: здесь работу сдаёт тот, кто сам назвал объём токенов. Им
пользуется PWA для nano-тира. С `2.17.15` подпись **обязательна**.

```json
{
  "workerAddress": "0x…",
  "tokens": 4000,
  "tier": "base",
  "response": "текст ответа",
  "actionId": "…",
  "worker_ts": 1793729564795,
  "worker_signature": "base64…"
}
```

Подписывается **не только адрес**:

```
TARNET_WORK_SUBMIT:<workerAddress>:<tokens>:<tier>:<actionId>:<timestampMs>
```

`tokens`, `tier` и `actionId` входят в payload намеренно: подпись от работы на 1 токен не должна
подходить к заявке на 8192. Подписывать надо то, за что платят.

**Откуда берётся ключ — два источника [КОД]:**

| Источник | Кто это |
|---|---|
| `ws_worker_auth` | воркер, прошедший handshake |
| `tar_id` | устройство/PWA, зарегистрировавшее TarNet ID через `POST /id/register` |

Смотреть только в первую таблицу нельзя: PWA nano-тира зовёт `/work` своим адресом, и её ключа в
`ws_worker_auth` нет. Закрытие `/work` «в одном месте» отрезало бы работающий путь вместе с дырой.

| Ответ | Значение |
|---|---|
| `403 HANDSHAKE_REQUIRED` | ключа нет вовсе — сначала привязка |
| `403 SIGNATURE_REQUIRED` | ключ есть, подписи нет — чинится на клиенте |
| `401 BAD_SIGNATURE` | подпись есть, но не сходится |
| `401 TIMESTAMP_OUT_OF_WINDOW` | `ts` вне 300 с |
| `400 client_signature rejected` | не сошлась подпись *клиента* (если передана) |

`worker_ts` ограничивает переигровку во времени, но **не** делает запрос идемпотентным: повтор с
тем же `actionId` вернёт тот же чек — за это отвечает `actionId`, а не подпись.

### 4.2. `POST /node/attest` — заявка на `expert` (без выдачи)

```json
{ "workerAddress": "0x…", "tier": "expert", "method": "tpm2-quote", "evidence": { } }
```

Ответ — **`202`, `status: "pending"`, `approved: false`, `tierChanged: false`**.

Это заглушка по делу, а не по недоделке. Чего она **не** делает:

- **не проверяет TPM/SGX/SEV** — аппаратной аттестации в проекте нет;
- **не ставит `tier = 'expert'`**. Выдать `expert` за один POST значило бы вернуть дыру
  `2.17.13`, где клиент сам себе выставлял тир и попадал в пул валидаторов.

`method` обязателен и обязан быть назван: заявка «attest: ok» без указания, *чем* замеряли, через
месяц неотличима от вымысла. `status = 'approved'` в таблице `node_attestations` не выставляется
никогда — это признак того, что кто-то выдал `expert` без проверки.

Настоящая проверка железа — `[SPEC / ROADMAP]`, и ей нужна доверенная сторона, которая замерит
железо, а не эндпоинт.

### 4.3. `GET /receipt/:worker` — публичен **намеренно**

Эндпоинт `/receipt/:worker` **публичен намеренно**. Он не содержит промптов, PII или приватных
ключей. Только подписанные чеки и публичные метрики узла, чтобы клиенты могли проверить историю
воркера.

Что реально отдаётся (`server.js:6090`):

| Поле | Источник | Почему публично |
|---|---|---|
| `workerAddress` | ключ запроса | адрес и так виден в `/nodes` |
| `seq`, `workerSeq` | `work_receipts` | порядковый номер чека, не содержание |
| `cumulativeCwu`, `cumulativeTar` | `work_receipts` | сколько узел наработал — это и есть proof of work |
| `receiptHash`, `prevReceiptHash`, `signature` | Ed25519 шлюза | без них чек нельзя проверить |
| `stake`, `reputation` | `nodes` | входные данные маршрутизации |
| `verified` | `ledger.verify` | результат проверки подписи |

Чего здесь **нет и не должно быть**: текста промпта, текста ответа, `sessionKey`, приватного
ключа воркера, IP-адреса. Тексты не хранятся в `work_receipts` вовсе — в лог `/inference` пишется
`sha256` ответа и его длина, а не содержание.

**Почему это не утечка, хотя эндпоинт без авторизации.** Аудит без возможности проверить —
это не аудит. Если бы историю воркера видел только её владелец, клиент не смог бы убедиться, что
узел, которому он платит, действительно наработал заявленное, а не нарисовал цифру в ответе.
Публичность здесь — условие доверия, а не побочный эффект.

**Граница.** Публичность относится ровно к чекам и агрегатам. Список привязанных устройств
(`GET /devices/links/:owner`) остаётся **не** публичным по смыслу: он связывает владельца с его
ПК и показывает баланс, то есть это уже про человека, а не про узел.

## 5. Тайминги и лимиты

| Константа | Значение | Где |
|---|---|---|
| `WORKER_TASK_TTL_MS` | 30000 | `server.js` |
| `WORKER_ACTIVE_WINDOW_MS` | 60000 | `server.js` |
| `POLL_AUTH_SKEW_MS` | 300000 | `server.js` |
| `POLL_AUTH_PREFIX` | `TARNET_WORKER_POLL` | `server.js` |
| `TARNET_WORK_SUBMIT` (payload `/work`) | префикс | `server.js` |
| `MAX_TOKENS_PER_TASK` | 8192 | `config.js` |
| `RATE_LIMIT_WORKER_MAX` | 240 / 60 с | `server.js` |
| `RATE_LIMIT_READ_MAX` | 300 / 60 с | `server.js` |
| `RATE_LIMIT_MAX` (strict) | 10 / 60 с | `server.js` |
| `RATE_LIMIT_CHAT_MAX` | 120 / 60 с | `server.js` |

Воркер живёт в окне 60 с: опрос раз в секунду его продлевает. Молчащий сокет **без** задачи
рвётся по прежнему порогу; сокет **с** задачей в работе держится до её дедлайна — иначе спящий ПК
терял бы задачу, которую ещё считает.

Потеря сокета с задачей возвращает её в очередь (`status = 'pending'`, `intendedWorker = NULL`).
Привязка снимается вместе с `workerAddress`: иначе строка осталась бы нацеленной на сокет,
которого нет, и `poll` её не отдал бы никому.

## 6. Что воркер обязан и чего не должен

### 6.1 `CANCEL` — кадр «результат больше не нужен»

Приходит по WebSocket, а не через HTTP. Появляется, когда задача отправлена двум воркерам
(swarm) и один из них уже дал ответ, который признан лучшим.

```json
{ "type": "CANCEL", "taskId": "<id задачи>", "reason": "swarm_loser", "at": 1762345678901 }
```

`reason` сейчас единственный: `swarm_loser`. Появится другой — появится и новое значение;
воркер обязан не падать на незнакомом `reason`, а трактовать его как «отменить».

**Что воркер обязан:** прервать работу, если может. `worker-demo.js` для этого держит `AbortController`
по `taskId` (`taskAborts`) и зовёт `abort()`. Оборванный запрос **не** отправляется в `submit` — это не
ошибка воркера, и `failed` в статистике не растёт.

**Кадр может прийти раньше задачи.** Сервер отправляет `CANCEL` после снятия строки задачи, но при
переупорядочивании каналов воркер может получить его до `TASK`. Такие «ранние» отмены запоминаются
в `taskCancelledBefore` (предел `MAX_EARLY_CANCELS = 200`, вытеснение FIFO — самый старый уходит
первым), чтобы долгоживущий воркер не рос в памяти. Пришедшая позже задача с этим `taskId`
отменяется сразу, не начинаясь.

**Чего `CANCEL` не делает.** Он не отменяет деньги и не гарантирует остановку: воркер может быть
в середине HTTP-запроса к Ollama, и кадр ляжет в очередь. Это сигнал, а не приказ с подтверждением.
Поэтому строка задачи снимается на сервере **до** отправки кадра: даже если воркер его не увидит,
результат не будет оплачен второй раз.

### 6.2 `swarm` — два воркера на одну задачу

Включается полем `swarmMode: "synthesis"` в `POST /inference`. Любое другое значение (и отсутствие
поля) — режим `race`.

**Пара должна быть настоящей:** два разных адреса. Один воркер, получивший две задачи, — это не
параллель, а очередь на одном ПК, поэтому второй вызов идёт с явным исключением первого адреса.

Режимы:

- `race` — берётся первый пришедший ответ, второй не сравнивается.
- `synthesis` — сравниваются оба. `DEFAULT_AGREEMENT_THRESHOLD = 0.8` по коэффициенту Dice:
  при ≥80% общих слов два ответа пересказывают одно и то же, и второй информации не добавляет.

Порядок правил в `swarm-synthesis.js` важнее самой метрики, потому что похожесть слов не равна
правильности:

1. **Проверка синтаксиса кода до согласия.** Битый код совпадает с рабочим по словам на ~95%,
   и наивная схема объявила бы это согласием. Не прошедший синтаксис ответ не может быть выбран.
2. Согласие ≥ порога → берётся первый.
3. Длина — если ответы разошлись.
4. Пустой ответ — отдельная ветка: ноль против нуля иначе дал бы «длиннее» на пустоте.

**Оплата уходит выбранному воркеру, не первому ответившему.** Проигравшая задача при этом
**не снимается**: её ответ прочитан, работа выполнена, и списывать её как невыполненную нельзя.
Снимается только то, что ещё не начато или уже не нужно, — и тогда уходит `CANCEL` (§6.1).

**Когда рой не состоялся**, ответ несёт `swarm.enabled = false` и `reason`:

- `need_two_workers` — подключён меньше двух воркеров;
- `both_answers_empty` — пара была, оба ответа пусты;
- `no_workers` — нет ни одного воркера, задача ушла в облачный fallback.

`reason` в `/inference` и `swarm.reason` — **разные поля разных уровней**, не дубликат:
первое объясняет, почему работа копится до минимального чека (`MIN_RECEIPT_TOKENS = 50`),
второе — почему не сложился рой.

**Потолок токенов.** `maxTokens` на задачу не может превысить `CONFIG.MAX_TOKENS_PER_TASK = 8192`;
превышение не обрезается молча — на входе это 400 с `maxAllowedTokens`, а в выдаче задачи
ставится флаг `tokens_clamped: true`.

**Обязан:**
1. Пройти handshake до первого опроса — иначе `403`.
2. Подписывать каждый опрос; `ts` в пределах 300 с.
3. Подписывать каждую сдачу в `/work`; `ts` в пределах 300 с.
4. Применять `maxTokens`.
5. Честно ставить `source`.
6. Расшифровывать `sessionKey` своим приватным ключом, если `keyEncryption: "box:v1"`.

**Не должен:**
1. Считать `403 HANDSHAKE_REQUIRED` поводом бросить сеть — это шаг, который надо выполнить.
2. Перегенерировать ключ при `409 ADDRESS_KEY_MISMATCH`. Так выглядел бы захват чужого адреса;
   восстановление — отдельная процедура у оператора.
3. Полагаться на `stake`/`reputation` из тела `POST /node` — они игнорируются.
4. Заявлять `live_llm`, если ответил шаблоном.

## 8. `SignedAuthorizationV1` — подпись запроса по JCS, `[SPEC / ROADMAP]`

> **Статус: НЕ РЕАЛИЗОВАНО.** В коде этого раздела нет. Сейчас `/inference` и `/work`
> подписываются строкой с разделителем `:` (см. §4.1), и проверяется она только если
> подпись прислана. `SignedAuthorizationV1` — это описание того, что должно заменить
> строковую склейку, а не описание работающего механизма.

### 8.1. Зачем это нужно, конкретно

Сегодняшний payload — строка, собранная через `:`:

```
TARNET_WORK_SUBMIT:<address>:<tokens>:<tier>:<actionId>:<ts>
```

`actionId` — **свободная строка без экранирования**. Если она содержит `:`, границы полей
размываются. Проверено прямым прогоном: пары `(tokens=100, tier="base", actionId="x:y")` и
`(tokens=100, tier="base:x", actionId="y")` дают **байт-в-байт одинаковый payload** — одна
подпись подходит к двум разным запросам.

Практически это не взрывается только по совпадению:

- `base:x` не проходит валидацию `TIERS`, атака отсеивается раньше;
- пустой `ts` не проходит `Number.isFinite`, поэтому `actionId="a:999", ts=""` не схлопывается
  с `actionId="a", ts=999`.

**Защита держится на побочных проверках, а не на формате.** Это и есть причина переходить на
структурную подпись: с JSON-объектом размыть границы полей невозможно, потому что границы
— это кавычки, а не разделитель внутри данных.

### 8.2. Почему JCS (RFC 8785), а не «просто JSON.stringify»

`JSON.stringify` даёт разный байтовый результат при разном порядке ключей, при `2e-3` вставленном
вместо `0.002`, и при разных локалях в сортировке. Подпись, проверяемая по такому представлению,
падала бы на ровном месте.

JCS задаёт один результат для одних данных. Три правила, которые нужны практически
(проверены на примере из §3.2.3 RFC):

| Правило | Что требует |
|---|---|
| Пробелы | Не выводить пробелы между токенами |
| Числа | Сериализовать по ECMAScript, включая `1e+30`, `4.5`, `0.002`, `1e-27` |
| Ключи | Сортировать **рекурсивно**, по UTF-16 code units, без учёта локали. Порядок массива **не меняется** |

Ловушка, проверенная живьём: `Object.keys(o).sort((a,b)=>a.localeCompare(b))` на
`{"b","a","Z","aa",""}` даёт `["", "a", "aa", "b", "Z"]`, а JCS требует
`["", "Z", "a", "aa", "b"]`. **Локаль-зависимая сортировка ломает подпись** — нужен
голый `.sort()` без компаратора.

### 8.3. Поля, которые подписываются

Объект целиком, канонизированный по JCS и подписанный Ed25519:

```json
{
  "v": 1,
  "type": "inference",
  "clientAddress": "0x…40hex",
  "workerAddress": "0x…40hex",
  "tier": "base",
  "promptHash": "sha256-хеш промпта, hex",
  "maxTokens": 512,
  "maxFeeAtomic": "1500000000000000",
  "nonce": "случайная строка, ≥16 байт",
  "issuedAt": 1793730000000,
  "expiresAt": 1793730300000
}
```

Четыре поля, которых нет в нынешней строковой подписи, и зачем каждое:

- **`nonce`** — без него одинаковый запрос, отправленный дважды, имеет одинаковую подпись, и
  перехваченный запрос можно проиграть. Сейчас роль ограничителя играет только `ts` в окне
  300 с; `nonce` делает повтор невозможным внутри окна.
- **`expiresAt`** — подпись, действительная навсегда, превращается в бессрочный доступ к чужому
  балансу после утечки. Явный срок гасит это на уровне формата, а не политики.
- **`maxFeeAtomic`** — потолок списания, подписанный **клиентом**, а не вычисленный сервером.
  Без него клиент подписывает «сделай что-нибудь», а сколько списать — решает другая сторона.
- **`v` и `type`** — разделение доменов. Без них подпись запроса на `inference` могла бы быть
  предъявлена как подпись запроса на `work`: payload одного типа неотличим от другого.

`maxFeeAtomic` — **строка**, не число. Причина из RFC 8785 §3.1: JSON-числа обязаны быть
выразимы как IEEE 754 double. `9007199254740993` (2^53+1) при записи числом превращается в
`9007199254740992` — проверено: два разных значения дают одинаковый байт. Для денег это
недопустимо; атомарные суммы идут строкой, как рекомендует Appendix D.

`promptHash`, а не `prompt`: сам текст в подпись не попадает, иначе подпись требовала бы
передачи промпта на проверяющую сторону — прямое нарушение privacy by default.

### 8.4. Что ломается и как это ловить

| Случай | Обязательное поведение |
|---|---|
| `expiresAt` в прошлом | Отказ, не предупреждение |
| `nonce` уже видели | Отказ; хранилище nonce — с TTL не меньше `expiresAt` |
| `maxFeeAtomic` < реальной цены | Отказ, а не списание по факту |
| `v` не поддерживается | Отказ, не «попробуем как v1» |
| Одиночный суррогат в строке | Отказ: RFC 8785 §3.2.2.2 требует аварийного завершения |

`nonce`, проверенный без атомарности, бесполезен: две параллельные копии одного запроса обе
увидят «не видели» и обе пройдут. Проверка и запись `nonce` — в одной транзакции, так же как
лимит faucet по `ipHash` (§7 манифеста).

### 8.5. Граница с тем, что есть сегодня

Сейчас `/inference` проверяет `client_signature` **если он прислан**, а по-настоящему
обязательным не делает. `SignedAuthorizationV1` изменит три вещи: объект вместо строки,
обязательность вместо необязательности, и потолок цены внутри подписи. Это отдельная работа,
и смешивать её с текущей приёмкой нельзя: подмена формата без клиентов, умеющих его собрать,
даст 401 у всех сразу.

## 9. Границы этого документа

Здесь **нет** и не должно быть, пока не появится в репозитории:

- **Onion routing** — `[SPEC / ROADMAP]`. AES-256-GCM используется только для ключей в состоянии
  покоя и для задач; многослойной маршрутизации нет.
- **TEE attestation** — `[SPEC / ROADMAP]`. `isTeeAttested` — флаг в БД, аппаратной аттестации
  нет. `POST /node/attest` принимает заявку, но `tier: expert` по-прежнему выдаётся **только**
  backfill'ом по `work_receipts`. Заглушка, названная заглушкой (§4.2).
- **Cartel detection, децентрализация до DAO** — Фаза 3.
- **libp2p / P2P-транспорт** — `[SPEC / ROADMAP]` в части **работ**. Уточнение на 2026-11-05:
  `server.js` теперь **импортирует** `p2p-bridge-client` (строка 38) и отдаёт `GET /p2p/bootstrap`
  с адресом узла из живого `status.listen`; `p2p-node/p2p-worker.js` по этому адресу делает
  `dial` и держит соединение (приёмка: `connections: 1` с обеих сторон). **Транспорт и discovery
  работают.** Чего по-прежнему нет: **задачи и чеки по P2P не ходят** — `/worker/poll` и
  `/worker/submit` остаются HTTP, узел ничего не знает о `work_receipts`. Считать «P2P готов»
  по факту соединения нельзя: соединение — канал, а не протокол работ.
- **`SignedAuthorizationV1`** — `[SPEC / ROADMAP]`, §8. В коде подпись по-прежнему строковая.
