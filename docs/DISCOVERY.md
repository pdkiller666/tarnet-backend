# DISCOVERY — как сеть TarNet находит узлы

**Назначение.** Как устроено обнаружение в `2.25.4-two-seed`: DHT, relay, протоколы,
что проверено и чем именно. Всё ниже — из кода и прогонов; значения, которых нет в
репозитории, здесь отсутствуют.

**Правило.** Пункт без ссылки на файл/тест — не описание, а пересказ.

---

## 1. Три уровня, которые нельзя путать

| Уровень | Вопрос, на который отвечает | Механизм |
| :--- | :--- | :--- |
| **Bootstrap** | «с чего начать, если я никого не знаю» | `GET /p2p/bootstrap` у backend-api |
| **Discovery (DHT)** | «кто умеет X и по какому адресу» | `kad-dht`, протокол `/tarnet/kad/1.0.0` |
| **Достижимость** | «как достучаться, если у узла нет входящего порта» | `circuit-relay-v2`, адрес `/p2p-circuit` |

Это три разных отказа, и лечатся они по-разному. DHT-сервер **не** делает узел
достижимым: он честно отдаёт адрес, по которому нельзя подключиться. Именно поэтому
relay — отдельный механизм, а не «настройка DHT».

---

## 2. Bootstrap: адрес сети берётся у того, кто реально слушает

`server.js` → `GET /p2p/bootstrap`.

Ответ собирается из ответа моста (`action: 'status'`), а **не** из `P2P_PUBLIC_URL`.
Переменная — это желание, а не факт: она может быть задана при выключенном libp2p
(`P2P_BRIDGE_LIBP2P≠1`), и тогда выданный адрес ведёт в пустоту. Источник — `listen`
живого узла: нет узла — нет адреса.

Коды ответа различают два разных отказа:

| Ответ | Значение |
| :--- | :--- |
| `200` + `multiaddrs[]` | сеть найдена, есть куда подключаться |
| `503 P2P_BRIDGE_UNAVAILABLE` | мост не отвечает по сокету |
| `503 P2P_NODE_NOT_LISTENING` | мост отвечает, но libp2p не слушает ни на одном адресе |

Пустой список с кодом `200` был бы ложью: клиент понял бы его как «сеть есть, пиров
нет» и ждал бы вечно.

**С `2.25.4`** ответ содержит оба seed: `multiaddrs` объединён и дедуплицирован, а
`seeds[]` говорит, откуда взялся каждый адрес и почему второго нет. Отсутствие второго
seed — **не** 503: хост может его не иметь. Ошибка видна в `seeds[1].error`.

## 3. DHT: что именно объявляется

| Параметр | Значение | Где |
| :--- | :--- | :--- |
| Протокол DHT | `/tarnet/kad/1.0.0` | `p2p-node/bridge.js:64`, `p2p-worker.js:69` |
| Сеть (бакеты/темы) | `tarnet-testnet-1` (`TARNET_NETWORK_ID`) | `bridge.js:64` |
| Схема записи | `tarnet.worker-record.v1` | `p2p-node/worker-record.js:37` |
| TTL записи | 90 000 мс | `worker-record.js:46` |
| Переиздание | каждые 30 000 мс (⅓ TTL) | `worker-record.js:50` |

**Ключ бакета** — от `networkId`, `modelFamily`, `deviceClass` (`bucketCid`). Провайдер
объявляется через `dht.provide(CID)`, ищется через `dht.findProviders(CID)`. Оба
возвращают AsyncIterable: **без дренажа запрос не выполняется** и выглядит как «пусто».

**Запись подписывается** Ed25519; `peerIdFromPublicKey` обязан совпадать с объявленным
`peerId`, иначе `buildRecord` отказывает `PEER_ID_MISMATCH`. Подпись покрывает
JCS-строку записи без поля `signature`. Проверено `test-discovery-e2e.js` 5.4 и
`test-seed-failover.js` 4.4 — включая отказ на подделанной записи (`BAD_SIGNATURE`).

**Что по DHT НЕ передаётся.** GossipSub-тема
`/tarnet/<networkId>/workers/1.0.0` несёт только метаданные присутствия. Промпты и
результаты по ней не идут.

## 4. Relay: путь туда, где входящий TCP невозможен

`circuitRelayServer()` — на мосту (`bridge.js`), `circuitRelayTransport()` +
`listen: ['/p2p-circuit']` — на воркере (`p2p-worker.js`). **Оба нужны вместе:**
транспорт без `/p2p-circuit` в `listen` не запрашивает резервацию, а listen-адрес без
транспорта не обслуживается.

Relay — **третий** адрес, а не замена TCP. Узел без NAT соединяется напрямую и
дополнительно держит слот.

| Параметр | Значение | Почему |
| :--- | :--- | :--- |
| `P2P_RELAY=0` | выключает | штатное действие, обязано быть видно в логе |
| `maxReservations` | 256 | дефолт 15: 16-й воркер молча не получал слот |
| `defaultDataLimit` | 2 МБ/соединение | relay пропускает чужой трафик |
| `reservationTtl` | 7 200 000 мс | брошенные резервации освобождают место |

## 5. Два seed: что проверено и что нет

`tarnet-seed2.service` — `P2P_PORT=4002`, свой `P2P_DATA_DIR`, свой сокет.
Общий data-dir дал бы **тот же peerId**, то есть один узел, раздвоенный в отчёте.

`P2P_SEED_PEERS` — список соседей, симметричный в обоих юнитах. Без него два seed на
разных портах — **два острова**: `bridge.js` до `2.25.4` никогда не звонил другому seed.
Повтор dial: 18 × 10 с в фоне, потому что systemd стартует юниты одновременно.

**Доказано** (`test-seed-failover.js`, 12/0):
- воркер объявляется через seed1, клиент знает **только** seed2 — находит воркера;
- обратное направление — тоже;
- изолированный seed не находит провайдера из чужой сети (отрицательный контроль).

Доказательство строится на **разнице двух замеров** соединений по обе стороны от
`provide()`: после него сам DHT звонит ближним узлам, поэтому «воркер знал только
seed1» проверить нельзя.

**НЕ доказано:**
- два seed у **разных операторов** (сейчас оба на одном VPS — общий диск, провайдер);
- настоящий NAT между машинами с потерей пакетов;
- живой прогон с гашением первого seed на проде.

## 6. Границы честности

| Утверждение | Статус |
| :--- | :--- |
| Discovery работает на loopback (3–5 узлов) | ✅ доказано |
| Relay даёт резервацию через боевой мост | ✅ 1101 мс, `direct addrs: 0` |
| Discovery работает через любой из двух seed | ✅ 12/0 |
| Работает через реальный NAT | ❌ не проверено (нужен ПК владельца) |
| Сеть децентрализована | ❌ один хост — писать нельзя |

## 7. Диагностика: что смотреть первым

| Симптом | Первое, что смотреть |
| :--- | :--- |
| `503 P2P_BRIDGE_UNAVAILABLE` | `systemctl status p2p-bridge`, сокет `/tmp/tarnet-p2p-bridge.sock` |
| `503 P2P_NODE_NOT_LISTENING` | `P2P_BRIDGE_LIBP2P=1` в юните; строка `libp2p поднят` в логе |
| Воркер не находит провайдера | `routingTable.size`; `routingTable.add()` вызывается явно? |
| Узел за NAT недостижим | строка `Relay` в логе моста; `P2P_RELAY=0` не выставлен? |
| Seed2 не связан | `seeds_linked` в `status()`; `P2P_SEED_PEERS` в обоих юнитах |
| `ERR_MODULE_NOT_FOUND` у воркера | `npm ci` в `p2p-node`; список `P2P_REQUIRED_PACKAGES` |
