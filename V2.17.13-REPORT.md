**Дата:** 2026-11-03
**Приёмка:** `1019 ✅ / 0 ❌`, `EXIT=0` (было `1009`; добавлено 10 проверок)

## 1. Главное: утечка промпта через `/worker/poll`

### Что было

`GET /worker/poll` отдавал первую pending-задачу **любому спросившему**. Вместе с задачей уезжал `sessionKey` — ключ расшифровки AES-256-GCM. То есть шифрование не защищало ничего: шифротекст и ключ к нему ехали в одном ответе.

### Доказательство, а не предположение

Эксплойт воспроизведён на изолированной копии БД (`/tmp/proof.db`, порт 3301; боевая `tarnet.db` не тронута):

```
A) POST /node без аутентификации      → 200, routingWeight = 297
B) присутствие записано
D) ЗАДАЧА УКРАДЕНА. taskId = wt_a307e1822f50e586bd2e4bc7
   sessionKey в открытом виде: rH9FejA5RA7JTwxlgwQI…
E) РАСШИФРОВАНО: СЕКРЕТ: пароль от VPS и приватная стратегия TarNet…
   СОВПАЛО С ОРИГИНАЛОМ: true
F) честный воркер теперь получает: {"task":null,"note":"Очередь пуста."}
```

Последняя строка — не косметика: атака не просто читала промпт, она **отбирала работу** у настоящего воркера.

### Исправление, шаг 1 — привязка задачи к адресу

- `worker_tasks.intendedWorker TEXT` — новая колонка.
- `enqueueWorkerTask({ prompt, model, tier, workerAddress })` пишет адрес в нижнем регистре.
- `/worker/poll` отдаёт строку только при совпадении адреса.
- При возврате задачи в очередь (воркер потерян, сокет упал) привязка снимается: иначе задача истечёт за мёртвым узлом.

### Исправление, шаг 2 — подпись опроса

Одной привязки оказалось **мало**. Проверено тем же способом:

```
✅ ПЕРЕХВАТ ЗАКРЫТ: чужой адрес задачу не получил
❌ ПОДМЕНА АДРЕСА РАБОТАЕТ. промпт: ВТОРОЙ СЕКРЕТ… | совпало: true
```

Адрес виден в `/nodes` — злоумышленник просто называет себя чужим. Поэтому добавлена подпись Ed25519 тем же ключом, который воркер уже предъявляет в WS-handshake:

- `POLL_AUTH_PREFIX` = `TARNET_WORKER_POLL`, подписывается `${PREFIX}:${address}:${ts}`;
- `POLL_AUTH_SKEW_MS` — окно свежести `ts`;
- ключ берётся из `ws_worker_auth` (TOFU-привязка при первом рукопожатии);
- отказы: `401 SIGNATURE_REQUIRED`, `401 TIMESTAMP_OUT_OF_WINDOW`, `401 BAD_SIGNATURE`.

Канал защиты: подпись доказывает владение ключом, привязанным к адресу. Сменить ключ для занятого адреса нельзя — `ADDRESS_KEY_MISMATCH`.

### Совместимость — сломано намеренно

`worker-demo.js` подписывает poll. Без этой правки собственный воркер получил бы `401` после первого же WS-подключения. **Сторонний воркер, который уже проходил handshake, обязан обновить клиент** — это breaking change, и он записан здесь, а не обнаружен на демо.

## 2. Директива `stake = 0` была математически неверной

**Исходная директива:** игнорировать `stake` и `reputation` из тела `/node`, новому узлу ставить `stake = 0`.

**Почему это отрезало бы сеть целиком.** `routingWeight = ω = √stake × reputation`, `pickWorker` фильтрует `routingWeight > 0`:

```
stake=0, rep=0   → 0.0000  МЁРТВЫЙ
stake=10, rep=0  → 0.0000  МЁРТВЫЙ
stake=0, rep=0.5 → 0.0000  МЁРТВЫЙ
stake=10, rep=0.5→ 1.5811  живой
```

Ноль в **любом** множителе обнуляет вес. Директива предлагала одну константу (`BOOTSTRAP_STAKE`), но `reputation` по умолчанию `0` — сеть осталась бы отрезанной ровно так же. Отсюда **две** константы.

**Третья ловушка — буквальное «сохранять текущий stake».** Проверка живой БД 2026-11-03:

```
всего узлов: 3
routingWeight<=0: 3 | stake<=0: 3 | reputation<=0: 3
```

Все три узла уже были с нулями. «Сохранять как есть» законсервировало бы мёртвую сеть навсегда. Поэтому ноль трактуется как «ещё не назначено» и заменяется на bootstrap.

**Итоговая реализация:**

| Константа | Значение | Смысл |
|---|---|---|
| `CONFIG.BOOTSTRAP_STAKE` | `10` | даёт `routingWeight > 0` |
| `CONFIG.BOOTSTRAP_REPUTATION` | `0.5` | второй множитель, без него вес = 0 |

Обе переопределяются из окружения. `reputation = 0.5`, а не `1.0`: репутация должна быть заслужена, иначе регистрация снова давала бы максимальный вес бесплатно — та же дыра в мягкой форме.

**Правило логики:** существующий узел сохраняет прежнее значение; ноль (или отсутствие) заменяется на bootstrap; значение из тела игнорируется **всегда**.

## 3. `tier` из тела больше не записывается

Присланный `tier` проверяется на допустимость (`nano/base/expert/heavy`, иначе `400`), но **не сохраняется**. Иначе клиент сам себе выставлял `expert` и попадал в пул валидаторов без проверки железа.

### Ограничение, которое это создаёт

Единственный путь получить `expert` сейчас — backfill по `work_receipts` при старте сервера. Эндпоинта аттестации нет. Это **пробел**, а не решение: нужен отдельный механизм подтверждения железа.

Тестовая фикстура сидинга валидаторов переведена на прямую запись в БД — через API роль валидатора больше не назначается. Тест это не «обошёл», а зафиксировал: раньше валидаторов можно было наделать одним POST.

---

## 4. Порог валидатора не поднят

`MIN_VALIDATOR_REPUTATION = 0.8`, а bootstrap даёт `0.5`. Это сделано намеренно: bootstrap возвращает **маршрутизацию** (`routingWeight > 0`), но **не голос**.

Поднять `BOOTSTRAP_REPUTATION` до `0.9`, чтобы тест зеленел без фикстуры, означало бы вернуть дыру: новый узел сразу стал бы валидатором без истории и без подтверждения железа.

---

## 5. Остаточная дыра — названа прямо

Воркер, который **никогда** не подключался по WS, опрашивается без подписи: ключа в `ws_worker_auth` ещё нет.

Привязать ключ из самого poll нельзя. Злоумышленник, заняв чужой адрес первым, навсегда выпер бы владельца (`ADDRESS_KEY_MISMATCH` — это отказ, не перезапись).

Закрывается только обязательным WS-handshake при регистрации ключа — архитектурное решение, зафиксировано в хронике.

---

## 6. Что осталось

- **Стадия 2:** обернуть `sessionKey` публичным ключом воркера. После подписи это уже не P0 — ключ уходит только тому, кто доказал владение адресом, — но обёртка убирает доверие к каналу.
- **Эндпоинт аттестации** — иначе `tier: expert` недостижим, кроме backfill.
- **`/work` без подписи** — закрывается отдельным коммитом.
