## Шаг 1. Открыть `/app/` на телефоне

```
https://v1107336.hosted-by-vdsina.com/app/
```

Телефон подключается к тому же узлу, что и ПК: это PWA, ставится на домашний
экран через «Поделиться → На экран Домой». Открывается без установки из стора.

**Смысл:** вход один — TarNet ID, кошелёк создаётся на устройстве, приватный
ключ не уходит на сервер. Это не «ещё одно приложение», это тот же аккаунт.

**Если не открылось:** проверить `curl -o /dev/null -w "%{http_code}" <URL>/app/`
— должно быть `200`. Туннель мог умереть; тогда поднимать заново
`scripts/tarnet-tunnel.sh` на VPS.

## Шаг 2. Нажать **Nano-Node**

Кнопка `Nano-Node` на главном экране (`id="nanoBtn"`). Узел регистрируется, в
`/nodes` появляется новая запись с `tier`.

**Смысл:** порог входа — обычный телефон. Тир `nano` даёт κ = 0.1 (коэффициент
работы), но участвовать можно с нуля. Это ответ на «зачем мне ваш токен, если
у меня нет фермы».

**Что сказать про тиры прямо:** `nano` — телефон, `base` — ноутбук,
`expert` — машина с GPU, `heavy` — сервер. В **комитет валидаторов** входят
только `expert` и `heavy`: узел на телефоне не может проверять чужие LoRA.
Сейчас в комитете 22 узла из 133.

## Шаг 3. Открыть `/health` в браузере — показать `delta: 0`

```
https://v1107336.hosted-by-vdsina.com/health
```

Смотреть три поля:

```json
"conservation": { "delta": 0, "holds": true },
"buildVersion": "2.4.1-tier-fix",
"llm_mode": "deterministic_fallback"
```

**Смысл:** `delta: 0` — баланс сети сходится. Сколько токенов выпущено, столько
и распределено: `gross = distributed`, расхождение ноль. Это главная защита от
«а вы просто рисуете цифры в базе» — инвариант проверяется на каждом запросе.

**Честная оговорка:** `llm_mode: deterministic_fallback` означает, что модель
сейчас отвечает шаблоном. Это состояние **до** шага 5. Не прятать: сказать, что
настоящий инференс включается живым воркером, и показать это следующим.

## Шаг 4. Открыть `/p2p/status` — показать 3 узла

```
https://v1107336.hosted-by-vdsina.com/p2p/status
```

```json
"transport": "websocket",
"routeNodes": [ "0x2491ab72…", "0xabe139a7…", "0x3281abaf…" ]
```

**Смысл:** это не «сервер и клиент», а три relay-узла, через которые идёт
луковичный маршрут. Каждый слой шифруется RSA-ключом своего узла — relay видит
только следующий адрес, но не промпт.

**Проверка, которую стоит показать живьём** (она убедительнее экрана):

```bash
curl -s -X POST https://v1107336.hosted-by-vdsina.com/inference/onion \
  -H 'Content-Type: application/json' \
  -d '{"routeNodes":["0x2491ab72f3cdfa132059df7e5cf08a0ea4c9fe25","0xabe139a759a3e77649eabc45fa5319e7085b2610","0x3281abaf01c3d746d09934b8e3a64344c0de3640"],"prompt":"demo"}'
```

Ответ: `"delivered": true`, `"hops": 3`, `"packetBytes"` ≈ 2.4 КБ
(число зависит от длины промпта — не называть точное значение вслух,
если оно изменится). Доставка реальная, не заглушка.

## Шаг 5. Запустить `worker.js` на ПК — показать `llm_mode: worker`

```bash
curl -O https://v1107336.hosted-by-vdsina.com/download/worker.js
TARNET_API_URL=https://v1107336.hosted-by-vdsina.com node worker.js
```

Файл качать **заново перед каждым показом**, не переиспользовать скачанный
раньше: версии до `v2.5.1-prep` не шлют heartbeat и мигают в баннере.

Зависимостей нет, нужен Node 18+. Затем обновить `/health`:

```json
"llm_mode": "worker",
"active_workers": 1
```

**Смысл:** тот самый ПК стал вычислительным узлом сети. Промпт ушёл на него,
там посчитан настоящей моделью (Ollama / Groq / OpenRouter), вернулся с чеком.
Сервер не считал — сервер только свёл баланс.

**Окно жизни:** воркер считается живым **15 секунд** после последнего опроса
(`WORKER_ACTIVE_WINDOW_MS`, видно в `/health`). Закрыли терминал — через 15 секунд
`llm_mode` вернётся в `deterministic_fallback`. Это норма, не поломка.

**Почему окно короткое и почему воркер не гаснет во время ответа:** воркер
опрашивает сервер раз в секунду, поэтому 15 с — запас 15x. Но пока он считает,
цикл занят генерацией и опроса нет: 7B на CPU думает дольше 15 с. Поэтому воркер
шлёт пульс `GET /worker/poll?workerAddress=…&model=…&heartbeat=1` вдвое чаще
окна (раз в 7 с), и присутствие не истекает посреди работы. Пульс задачу не
забирает — «украсть» работу у другого опроса он не может.

> ⚠️ **Старые воркеры мигают в баннере.** Файл `worker.js`, скачанный **до
> `v2.5.1-prep`**, пульс `heartbeat=1` не шлёт: пока он считает, присутствие
> истекает через 15 с, и баннер показывает «⚠️ Ваш ПК не в сети», хотя ПК жив.
> Ответ при этом всё равно приходит — врёт только индикатор. **Лечение: перекачать
> `worker.js` и перезапустить воркер** (команда в шаге 5). Проверить, что файл
> свежий: `grep -c heartbeat worker.js` → больше нуля.

**Дублирующий экран:** `GET /worker/status` отдаёт то же в поле `mode`, плюс
`pending_tasks` и список воркеров — удобно, если `/health` уже открыт.

## Demo Flush — чек ниже порога, показать сейчас

Обычный путь: работа копится в `pending_work`, и чек выпускается только при
переходе порога (`receiptThreshold()` = `max(MIN_RECEIPT_TOKENS, формула)`,
`MIN_RECEIPT_TOKENS = 50`): nano — 500, base — 50, expert — 50. У expert
формула даёт 13, но низкий пол в 50 токенов поднимает порог до 50 — цифру
13 в демо не называть.
На демо ждать порога нельзя: показать выплату нужно в первую минуту.

`POST /demo/flush-work` выпускает чек **ровно на накопленное**, минуя порог.
Экономика та же: идёт через `recordWork()` — fee, block, burn, treasury и
`conservation: delta 0` считаются общим кодом, а не отдельной веткой.
Принудительный чек помечается `demo: true` **в базе**, не только в ответе:
иначе после перезагрузки страницы он выглядел бы обычным.

### DEMO_MODE — флаг, который нельзя забыть выключить

`POST /demo/flush-work` выпускает чек минуя порог 50 токенов. Это нужно на демо
и опасно вне демо: порог перестаёт защищать экономику от чека на одну транзакцию.
Поэтому доступ закрыт флагом окружения и **выключён по умолчанию**.

**Пока флаг выключен — `/demo/flush-work` отдаёт `403`:**

```json
{"error":"demo mode is off"}
```

Это нормальное состояние продакшена, а не поломка. Тот же `403` — если флаг
включён, но сервис не перезапущен: `Environment=` читается только при старте.

Флаг живёт в **окружении сервера**, не в теле запроса — иначе порог обошёл бы
кто угодно.

#### Включить (перед показом)

```bash
ssh root@195.63.131.172
sed -i '/^Environment=PORT=/a Environment=DEMO_MODE=1' /etc/systemd/system/tarnet.service
systemctl daemon-reload && systemctl restart tarnet
systemctl show tarnet -p Environment | tr ' ' '\n' | grep DEMO_MODE   # → DEMO_MODE=1
```

Проверка, что флаг действительно в живом процессе (unit мог не примениться):

```bash
curl -s -X POST https://v1107336.hosted-by-vdsina.com/demo/flush-work \
  -H 'Content-Type: application/json' \
  -d '{"workerAddress":"0x0000000000000000000000000000000000000001"}'
# 403 → флаг не применился; 404 → флаг есть, накопления нет (это успех)
```

Для проверки самого флага `404` лучше `403`: он означает, что защита пропустила
запрос и код дошёл до поиска накопления. Использовать для этого живого боевого
воркера нельзя — он получит чек. Берите заведомо пустой адрес.

#### Выключить — сразу после демо, в тот же день

```bash
sed -i '/^Environment=DEMO_MODE=1$/d' /etc/systemd/system/tarnet.service
systemctl daemon-reload && systemctl restart tarnet
systemctl show tarnet -p Environment | tr ' ' '\n' | grep -c DEMO_MODE   # → 0
```

**Проверка после выключения — обязательна.** Отсутствие строки в unit не значит,
что процесс её забыл; `restart` мог не пройти. Единственное доказательство —
`403` снаружи:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://v1107336.hosted-by-vdsina.com/demo/flush-work \
  -H 'Content-Type: application/json' \
  -d '{"workerAddress":"0x0000000000000000000000000000000000000001"}'
# ожидаем 403
```

Демо-чеки остаются в базе с `demo: true` и после выключения флага — это правильно:
они были настоящими начислениями, но помечены, чтобы не смешиваться со статистикой.
Удалять их не нужно.

#### Как не забыть

Единственный реальный риск — оставить флаг включённым на неделю. Поэтому ставьте
выключение не «потом», а сразу при включении:

```bash
echo "DEMO_RUNBOOK: выключить DEMO_MODE на tarnet после показа" | at now + 3 hours
```

Если `at` не установлен — записать напоминание в календарь тем же действием,
которым включали флаг.

### Как вызвать

```bash
curl -s -X POST https://v1107336.hosted-by-vdsina.com/demo/flush-work \
  -H 'Content-Type: application/json' \
  -d '{"workerAddress":"0x..."}' | python3 -m json.tool
```

`workerAddress` обязателен. Необязательные: `tier` (`base`/`expert`/`nano`),
`adapterId`, `clientAddress`, `response`.

Успех — `201`:

```json
{
  "demo": true, "flushed": true,
  "pending_work_before": 6,
  "threshold": 50,
  "threshold_bypassed": true,
  "remaining_pending_rows": 0,
  "receipt": { "seq": 1, "rewardTar": 4.83, "demo": true },
  "conservation": { "delta": 0, "holds": true }
}
```

| Ответ | Когда |
|---|---|
| `403` | `DEMO_MODE` не равен `1` |
| `400` | нет `workerAddress` |
| `404` | `pending_work` пуст либо фильтр `tier`/`adapterId` не совпал |
| `409` | накопление нулевое или чек не выпущен (нулевая эмиссия эпохи) |
| `201` | чек выпущен |

### Одна строка, а не все сразу

Ключ накопления — `(workerAddress, tier, adapterId)`, поэтому у воркера может
быть несколько строк. Без явного `tier`/`adapterId` берётся **самая крупная**
строка: суммировать тиры нельзя, потому что CWU = `tokens × κ`, и общий чек на
45 nano + 5 expert занизил бы выплату в κ раз. Выбор детерминирован и виден в
ответе; остальные строки **не удаляются**, их число — в
`remaining_pending_rows`. Режим «слить всё» (`all: true`) не реализован.

> **Не показывать инвестору сумму чека с пустой БД.** На чистой базе доля пула
> эмиссии огромна: блок-награда — доля пула, а не объём работы, поэтому flush
> на 6 токенов со свежей базы даёт ≈ `4.83 TAR`. На боевой БД (CWU ~5×10⁸) та
> же работа даст микродоли. Сумму с пустой базы нельзя подавать как «доход
> воркера» — только как «механика начисления работает».

## Если что-то упало во время демо

| Симптом | Что делать |
|---|---|
| `/app/` не открывается | туннель умер → `scripts/tarnet-tunnel.sh` на VPS |
| `delta` ≠ 0 | **остановить демо**, это дефект экономики, не «глюк» |
| `/p2p/status` без узлов | `systemctl restart tarnet`, проверить порты 4001/4002 |
| `llm_mode` не стал `worker` | воркер не опрашивает: проверить `TARNET_API_URL` и что процесс жив |
| `/inference/onion` даёт `delivered: false` | смотреть `deliveryError`; пакет валиден, сеть — нет |

## Что нельзя обещать инвестору

Эти вещи в коде есть как **спецификация**, не как работа:

- **Benchmark Gate** (`verifyAdapter`) — возвращает `implemented: false`. Комитет
  валидаторов **выбирается**, но проверки адаптеров нет: ни бенчмарка, ни
  подписей валидаторов.
- **ECVRF** — жребий комитета сейчас детерминированный sha256-поток. Он
  пересчитывается любым участником, но предсказуем заранее. Настоящий VRF —
  Фаза 3.
- **Onion Routing** — работает для демо-сети из 3 узлов. Продовый маршрут по
  произвольным узлам из БД не доставляется: у записей нет транспортного адреса.
- **ONNX-классификатор PII** — выключен на этом VPS: модель держит 532 МБ RSS
  из 1642 МБ. Сейчас работает только regex-ветка (телефон, email, карта, IBAN).
  Имена ловит модель — она включится на сервере с 4+ ГБ RAM.

Формулировка для инвестора: «ядро экономики работает и сходится; валидация
адаптеров и VRF — следующие два спринта, спека готова, кода нет».
