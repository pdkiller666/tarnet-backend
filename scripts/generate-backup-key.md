# Как создать резервный SSH-ключ для VPS TarNet

**Кому.** Владельцу проекта. Делается **один раз** на его машине, когда она появится.
Агент этого сделать не может: ключ должен родиться на машине владельца, иначе
резервный доступ будет у агента, а не у человека.

**Зачем.** Сейчас SSH на VPS завязан на один ключ (`openclaw-tarnet-deploy`), который
лежит на постоянном томе контейнера. Если контейнер пересобирают и том теряется —
доступ к VPS пропадает вместе с ним. Резервный ключ с машины владельца — единственная
независимая точка входа.

**Важно.** Резервный ключ — **только для входа**. Он не даёт агенту прав на VPS сам по
себе; чтобы агент им пользовался, файл придётся положить туда, где агент его видит.

---

## 0. Текущее состояние: ПК владельца ещё нет

На 09.11.2026 ключ **не создан**, и это не недоделка, а следствие: ключ обязан родиться
на машине владельца, а машины пока нет. Ни один шаг ниже нельзя выполнить за него —
и нельзя заменить «создам у себя»: тогда резервный доступ будет у агента, а не у человека,
и весь смысл теряется.

**Пока ПК нет, риск не закрыт.** Держите в голове две вещи:

1. **Доступ сейчас держится на одном ключе** (`~/.ssh/tarnet_vps` на постоянном томе
   контейнера). Пока резервного нет, потеря тома = потеря VPS.
2. **Не пересобирайте контейнер без нужды.** Каждая пересборка — это шанс потерять том,
   и этот шанс ничем не подстрахован.

**Что сделать, когда ПК появится.** Не начинайте с шага 1 «на всякий случай». Сначала
убедитесь, что доступ ещё есть:

```bash
ssh -i ~/.ssh/tarnet_vps -o IdentitiesOnly=yes -o ConnectTimeout=10 \
  root@195.63.131.172 "echo OK; hostname"
```

`OK` и имя хоста — можно идти по шагам 1–5. Ошибка `Permission denied` — ключ уже потерян,
и резервный создавать поздно: нужен доступ через панель провайдера VDSina
(восстановление по консоли), а не по этой инструкции.

**Порядок имеет значение.** Резервный ключ создаётся **до** первой пересборки контейнера
после появления ПК, а не после. Ключ, добавленный «на следующий день», не спасает от
потери, случившейся вчера.

### Если ПК не появится в обозримом будущем

Есть более слабая, но реальная замена — **не ключ, а второй путь входа**:

| Вариант | Что даёт | Чего не даёт |
| :--- | :--- | :--- |
| Ключ на телефоне (Termius и аналоги) | вход без ПК | зависит от одного телефона |
| Ключ на флешке + парольная фраза | офлайн-носитель | флешку можно потерять |
| TOTP-подтверждение у провайдера | сброс пароля через панель | не заменяет SSH-ключ |

Любой из них лучше, чем ничего, но **ни один не равен** ключу на машине владельца:
он должен быть там, где владелец, а не там, где удобно агенту.

---

## Шаг 1. Создать ключ (на машине владельца)

### macOS / Linux

```bash
ssh-keygen -t ed25519 -C "tarnet-owner-backup-$(date +%Y-%m)" -f ~/.ssh/tarnet_owner
```

### Windows (PowerShell)

```powershell
ssh-keygen -t ed25519 -C "tarnet-owner-backup" -f $env:USERPROFILE\.ssh\tarnet_owner
```

**Почему `ed25519`, а не RSA.** VPS-ключ уже `ssh-ed25519`; ed25519 короче, быстрее и
не требует выбора длины. Смешивать типы на одном хосте незачем.

**Парольную фразу — ставить.** Это второй фактор: файл ключа без пароля означает, что
любой, кто прочитал диск, входит на VPS.

**Что появится:**
- `tarnet_owner` — **приватный**. Никому не отправлять, никуда не копировать.
- `tarnet_owner.pub` — публичный. Его и передаём.

---

## Шаг 2. Показать публичную часть

```bash
cat ~/.ssh/tarnet_owner.pub
```

Строка начинается с `ssh-ed25519 AAAA...` и заканчивается комментарием. Это
**публичный** ключ: его не страшно отправить даже в чат.

⚠️ **Не отправляйте файл `tarnet_owner`** (без `.pub`). Проверка: публичный — одна
строка, приватный — многострочный блок `-----BEGIN OPENSSH PRIVATE KEY-----`.

---

## Шаг 3. Передать публичный ключ агенту

Отправьте владельцу канала одну строку целиком:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... tarnet-owner-backup-2026-11
```

Агент выполнит:

```bash
bash scripts/ensure.sh "ssh-ed25519 AAAAC3... tarnet-owner-backup-2026-11"
```

Скрипт добавит ключ в `/root/.ssh/authorized_keys` на VPS **с проверкой и откатом**:
сначала проверяет, что ключ в правильном формате, затем дописывает, затем проверяет,
что вход по нему проходит. Не прошло — возвращает файл как было.

---

## Шаг 4. Проверить, что вход работает

```bash
ssh -i ~/.ssh/tarnet_owner root@195.63.131.172 "echo OK; hostname"
```

Ожидаемый вывод: `OK` и имя хоста. Если просит пароль — ключ не встал, вернитесь к шагу 3.

**Проверять нужно с выключенным текущим ключом**, иначе `ssh` может войти по нему и
создать ложное впечатление:

```bash
ssh -i ~/.ssh/tarnet_owner -o IdentitiesOnly=yes root@195.63.131.172 "echo OK"
```

`-o IdentitiesOnly=yes` запрещает ssh подставлять другие ключи. Без него проверка
доказывает не то, что кажется.

---

## Шаг 5. Записать, где лежит

Резервный ключ бесполезен, если через месяц никто не помнит, что он есть. Запишите в
`MEMORY.md` (или в личные заметки) четыре факта:

1. путь к приватному ключу (`~/.ssh/tarnet_owner`);
2. что он добавлен в `authorized_keys` на VPS и когда (дата);
3. что у него есть парольная фраза и где она лежит (менеджер паролей, не файл рядом с ключом);
4. **что шаг 4 реально выполнен** — вход проверен с `-o IdentitiesOnly=yes`, а не «ключ добавлен,
   значит работает». Разница между этими двумя утверждениями — весь смысл резерва.

После записи проверьте, что резерв действительно резерв: временно отключите основной ключ
и войдите резервным. Не получилось — резерва нет, есть только надежда.

---

## Если ключ потерян или скомпрометирован

Отозвать на VPS:

```bash
ssh -i ~/.ssh/tarnet_vps root@195.63.131.172 \
  "sed -i '/tarnet-owner-backup/d' /root/.ssh/authorized_keys && wc -l /root/.ssh/authorized_keys"
```

Затем создать новый по шагам 1–4. Удалять строку по комментарию, а не по номеру
строки: номера сдвигаются, и `sed -i '3d'` однажды удалит чужой ключ.

---

## Чего делать НЕ надо

| Нельзя | Почему |
| :--- | :--- |
| Копировать приватный ключ в чат, почту, облако | это уже утечка, отзыв обязателен |
| Делать ключ без парольной фразы | диск/бэкап = доступ |
| Использовать RSA-1024 | устарел, ed25519 короче и безопаснее |
| Проверять вход без `IdentitiesOnly=yes` | ssh подставит другой ключ, проверка станет ложной |
| Держать резервный ключ только на одном носителе | это не резерв, а второй экземпляр того же риска |
