### 2026-10-28 (продолжение) — установщики, Device Pairing

- **Причина «.bat дал новый кошелёк» — не в подстановке.** Директива предполагала, что `addr` не доходит до `WORKER_ADDRESS`. Проверено на живом сервере: `GET /install/install.bat?addr=0x648f…` → **200, `set "ADDR=0x648f7af570d0c201c87b7cef55dba88c98bf1936"`**; без адреса → **400 `addr required`**. `app.js:1114` строит ссылку как `` `/install/install.bat?addr=${encodeURIComponent(ADDR)}` ``. Подстановка, валидация и клиентская ссылка работают с коммита `7101678` (24.10).
- **Что было на самом деле:** `ADDR` в PWA — это **демо-адрес из `localStorage`** (`tarnet.address`), сгенерированный `crypto.getRandomValues`, без приватного ключа. Он не связан с `tar_id` телефона. Воркер Ильи шёл **без** переменной окружения и взял `~/.tarnet/worker.json` — оттуда `0xaf34…`, который существовал ещё 24.10 (чек `seq 706`). То есть оба адреса «правильные для своих устройств», но между ними нет связи: механизма привязки не было вовсе.
- **Пустой адрес закрыт в шаблонах.** Добавлена проверка в `install.bat.tpl` (длина 42, префикс `0x`, маркер `__TARNET_ADDR__`) и `install.command.tpl` (то же в bash). Обе ветки проверены: пустой адрес → **`exit=2`** с текстом «скачайте установщик из PWA заново». Это второй рубеж к серверному `400`: файл могли сохранить, переслать или открыть из истории.
- **Device Pairing сделана:** таблица `device_links(ownerAddress, deviceAddress, createdAt)`, `POST /devices/link`, `GET /devices/:owner`, `DELETE /devices/link`. Новые маршруты ушли в `read`-класс лимита (иначе вкладка «Мои устройства» упиралась бы в 10/мин).
- **Баннер теперь учитывает привязку.** Без этого Device Pairing был бы мёртвым механизмом: адрес привязан, сервер знает, а PWA продолжает писать «ваш ПК не среди них» — ровно то, от чего его и делали.
- **Честное ограничение привязки (записано и в коде):** вход по подписи не сделан, `ADDR` — демо-адрес без ключа. Значит привязка — **заявка**, а не доказанное владение: кто знает адрес, тот может его привязать. Балансы при этом **не сливаются** — привязка меняет только ответ на вопрос «моё ли это устройство», деньги остаются на адресе ПК.

### 2026-10-28 (продолжение 3) — `install.bat` упал на живой Windows

- **`6a03f5d`** — установщик падал у человека: `'$s.WorkingDirectory' is not recognized` и кракозябры вместо русского текста. Предупреждение «на живой Windows не проверял» подтвердилось буквально. **Урок: файл для Windows нельзя считать проверенным по HTTP-коду и строковым тестам — нужен запуск на Windows.**
- **Диагноз директивы в части PowerShell — неверен.** Утверждалось, что строки `$s.WorkingDirectory` попали в `.bat` без обёртки `powershell -Command`. Проверено: обёртка стояла, `grep '^\s*\$'` давал **0** строк. Причина была другая, и обе настоящие причины хуже названной.
- **Причина 1 — LF вместо CRLF.** Шаблон в git лежит с LF, и сервер отдавал его как есть. CMD разбирает batch-файлы **по CRLF**: при LF он склеивает соседние строки, метки `:` и `goto` съезжают, и куски PowerShell начинают выполняться как команды DOS. Отсюда и `'is not recognized'`, и мусор в выводе. `chcp 65001` тут бессилен — парсер ломается раньше вывода.
- **Причина 2 — 70 строк кириллицы** в UTF-8 при консоли в OEM/CP866.
- **Исправление:** шаблон переписан на **чистый ASCII**, все сообщения по-английски; `server.js` нормализует `.bat` к CRLF **на отдаче** (шаблон в git остаётся LF); base64-трюк с кириллическим именем убран — ярлык теперь `TarNet.lnk`, латиницей, то есть кодировочная проблема снята, а не обойдена.
- **Найден свой дефект, живший в предыдущей версии:** в блоке `:fail_addr` две строки были `rem` вместо `echo`, и предупреждение «воркер создаст НОВЫЙ кошелёк, работа уйдёт в чужой баланс» **никогда не печаталось**. Теперь весь текст ошибки — `echo`, держит тест `31.11`.
- **Тест `31.4` поймал живой баг в самой правке:** условие `/\.bat$/` не совпадало с именем `install.bat.tpl` (суффикс `.tpl`), CRLF не применялся — 227 строк без CR. Исправлено на `/\.bat(\.tpl)?$/`.
- **Приёмка: 706 `test-dpouw` + 25 `test-mesh` = 731, 0 падений.** Секция `31` — 16 проверок, инварианты: ASCII, CRLF, обёртка PowerShell, цель ярлыка, `rem`/`echo`.

### 2026-10-28 (продолжение 8) — комиссию Tier 6 платит владелец аккаунта, если у устройства пусто

- **Симптом:** на свежем ПК платный контур отвечал `402 INSUFFICIENT_FUNDS`, хотя на аккаунте TarNet ID лежало **0.009995 TAR** при комиссии `0.0005`. Устройство имело `0.000163 TAR`.
- **Причина — расхождение с принципом «единый аккаунт».** `app/app.js` (~строка 751) отправляет `clientAddress: ADDR`, где `ADDR = deviceAddress()` — случайный кошелёк из `localStorage['tarnet.address']`. Сервер проверял свободный остаток (`reserveTier6Fee`) **только** по этому адресу. Привязка `device_links` (владелец ↔ устройство) существовала, но в расчёте денег не участвовала вовсе: у неё была роль только для баннера «ваш ПК в сети» и отвязки.
- **Решение:** цепочка плательщиков `tier6PayerChain()` — сначала адрес устройства, затем владельцы из `device_links` (порядок `createdAt ASC, ownerAddress ASC`, чтобы выбор не зависел от порядка строк в индексе). Бронь ставится на **первом**, у кого свободный остаток ≥ комиссии (`balanceTar − reservedTar`), и списание идёт **с него же**, а не с вызвавшего: `settleTier6Reserve()` теперь возвращает `clientAddress` брони, и `debit()` берёт именно этот адрес.
- **Чужой кошелёк не становится плательщиком.** Владелец читается **только** из привязки, а не из тела запроса; непривязанное устройство с нулём по-прежнему получает 402. Проверка `34.5` держит баланс владельца нетронутым при чужом запросе.

### 2026-10-28 (продолжение 9) — сжигание больше не числится списанием с плательщика

- **Симптом — арифметика не сходилась, и это видел любой аудит.** Живая запись `tier6_calls.id = 4f6270d5-23db-4e19-98f3-af7dbf7223f2` (28.10 17:03 MSK, комиссия `0.0005`, кэшбэк `0.0001`, burn `0.0002`, treasury `0.0002`): приход `0.010395`, расход по `SUM(fromAddress)` `0.000706`, расчётный баланс `0.009689` — при фактических **`0.009889`** в `balances`. Расхождение ровно **`−0.0002`**, то есть весь burn-оборот чека. Без burn-строк сходится до нуля.
- **Причина — атрибуция, а не движение денег.** `recordBurn()` писала адрес плательщика (в основном пути — воркера) в `fromAddress` строки `burn`, хотя второго списания не было: `0.0005` уже ушло строкой `spend`. Функция делала только `INSERT INTO ledger_txs` и `credit(CONFIG.BURN_ADDRESS, …)`, никакого `UPDATE balances` по `fromAddress` не существовало. Значит любой расчёт движения по адресу как `SUM(toAddress) − SUM(fromAddress)` завышал расход на всю сумму сжигания.
- **Правка:** `recordBurn(amount, actionId)` больше не принимает `fromAddress` и пишет `NULL`. Сжигание — распределение уже списанной комиссии, а не отдельное движение с чьего-либо баланса. Оба вызова приведены к новой сигнатуре; `toAddress` остался адресом сжигания, поэтому `burnAddressBalanceTar` в `/summary` не изменил смысла — монеты по-прежнему аккумулируются для аудита.
- **Миграция старых строк.** Правка функции чинит только новые записи, а на проде уже лежали burn-строки с адресом плательщика. Добавлена идемпотентная `migrateBurnAttribution()`: `UPDATE ledger_txs SET fromAddress = NULL WHERE kind = 'burn' AND fromAddress IS NOT NULL`. Меняется **только** это поле — суммы, `balances` и история движения денег не переписываются. Повторный запуск находит 0 строк.
- **Приёмка: 759 `test-dpouw`, 0 падений** (было 749). Секция `35` — 9 проверок на изолированном сервере с заглушкой провайдера на loopback: вызов проходит; расход плательщика по леджеру = `fee − cashback` и **не включает** burn; расчётный баланс из леджера сходится с фактическим в `balances`; burn-строка с `fromAddress = NULL` и адресом сжигания в `toAddress`; сумма строки равна сожжённой доле; баланс адреса сжигания вырос на неё; `delta: 0` и `holds: true` в `/summary` и в `/health` (`conservation` и `conservationTier6`).
- **Что НЕ менялось намеренно:** инварианты `/summary` и `/health` считают `distributed` из `work_receipts`/`tier6_calls`, а не из `ledger_txs`, поэтому они и до правки были зелёными — правка лечит расчёт по адресу, а не инвариант. Это и есть причина, по которой дефект жил: метрика его не видела, видел только сверявший балансы человек.

### 2026-10-28 (продолжение 10) — два числа сжигания в `/summary` названы, а не слиты

- **Симптом — два соседних числа в одном ответе описывали разное.** На проде `/summary` отдавал `totalBurnedTar = 0.185113` и `burnAddressBalanceTar = 0.185313` — разрыв ровно **`0.0002`**, то есть ровно одно сжигание единственного вызова Tier 6. `totalBurnedTar` считается из `work_receipts.burnTar` через `ledger.totals()`, а `burnAddressBalanceTar` — просто баланс адреса сжигания, куда пишут **оба** пути. Видимого объяснения разницы в ответе не было: читатель мог решить, что одно из чисел врёт.
- **Воспроизведено на чистой БД до правки.** Сервер на временной БД + заглушка провайдера на loopback + один вызов Tier 6 с балансом плательщика: `totalBurnedTar` `0 → 0` (Δ=0), `burnAddressBalanceTar` `0 → 0.0002` (Δ=0.0002), разрыв ровно burn. `tier6_calls.burnTar = 0.0002`, burn-строка в `ledger_txs` с `fromAddress = NULL`. Инварианты при этом зелёные — дефект отчётности, а не движения денег.
- **Решение — разделить, а не складывать.** Вариант «добавить `tier6_calls.burnTar` внутрь `totalBurnedTar`» отклонён осознанно: это поле стоит в одном ряду с `totalRewardTar`, `totalFeeGrossTar`, `totalTreasuryTar`, и весь ряд считается из `work_receipts`. Сделав из одного поля гибрид, мы получили бы `receiptsByTier`, не складывающийся в итог, и `conservation.distributed`, не сходящийся с суммой `total*` — то есть сломали бы ровно ту согласованность, ради которой ряд существует. Вместо этого разница **названа**: `totalBurnedTar` (только чеки) + новое `totalBurnedTier6Tar` (внешние вызовы). Тот же приём, что `conservation` против `conservationTier6` в `/health`.
- **Сверка вместо надежды — `burnAudit`.** В ответе рядом появился блок `{ workReceiptsTar, tier6Tar, accountedTar, addressBalanceTar, delta, holds }`: сумма двух источников обязана совпасть с балансом адреса сжигания до `1e-6`. Если когда-нибудь появится третий путь сжигания, `holds` станет `false` и это будет видно из ответа, а не после ручного пересчёта `SUM` по таблицам.
- **Витрина не занижает.** `ui/index.html` (лендинг) и `ui/console.html` показывали только `totalBurnedTar`, то есть после разделения отставали бы от баланса адреса на весь объём Tier 6. Оба места теперь складывают `totalBurnedTar + totalBurnedTier6Tar` — цифра «TAR сожжено» осталась той же, что читатель видел раньше, и совпадает с `burnAddressBalanceTar`.
- **Приёмка: 776 `test-dpouw`, 0 падений** (было 759). Секция `36` — 17 проверок на изолированном сервере с заглушкой: burn работает и увеличивает `totalBurnedTar`, но **не** `totalBurnedTier6Tar`; вызов Tier 6 не двигает `totalBurnedTar`, а двигает `totalBurnedTier6Tar` ровно на `0.0002` и на ту же величину — `burnAddressBalanceTar`; сумма частей равна балансу, `burnAudit.holds` и `delta: 0`; `conservation`, `conservationTier6` в `/health` и `/summary` остаются `delta: 0 / holds: true`; оба файла витрины складывают два поля.
- **Чего эта правка НЕ делает:** не меняет ни одной суммы в `balances` и ни одной burn-строки. Деньги в `balances` были корректны и остаются корректными — исправлена только атрибуция в отчёте, как и в продолжении 9.

## 2. Решения

### Экономика

| Решение | Константа | Почему так |
|---|---|---|
| Отказ от лотерей → **dPoUW** | `REWARD_MODE: 'hybrid'` | Лотерея даёт непредсказуемый доход: воркер не может планировать, UX ломается |
| `W = N_tokens × κ_tier × γ_verify` | `economics.js:6` | CWU — единица полезной работы, а не «сколько заплатили» |
| Одна цена `P`, тир — множитель `κ` | `PRICE_USD_PER_1M_TOKENS: 0.20` | Отдельная цена на тир разъезжается с таблицей весов при первой правке |
| `TIER_WEIGHTS = {nano: 0.1, base: 1, expert: 4}` | `config.js:7` | Даёт `$0.02 / $0.20 / $0.80` за 1M — числа, выводимые из одной константы |
| Курс `USD_PER_TAR = 20` | `config.js` | **Переименовано** из `TAR_PER_USD`: старое имя читалось как «20 TAR за доллар» — ровно наоборот, в 400 раз мимо. Математика была верной, врало название |
| Комиссия `φ = 5%`: 2.5% burn + 2.5% treasury | `PROTOCOL_FEE_RATE: 0.05` | Дефляция без отдельного механизма |
| Роялти LoRA 5% **от Fee_Reward**, не от gross | `LORA_ROYALTY_RATE: 0.05` | Иначе авторы адаптеров получали бы долю эмиссии, которую не заработали |
| Эмиссия: 50 TAR/эпоха, халвинг 365 эпох | `INITIAL_BLOCK_REWARD: 50` | Биткоин-подобная кривая; эпоха = сутки |
| Потолок `MAX_RECEIPT_SHARE_OF_EPOCH = 0.25` | `config.js` | Без него единственный узел в эпохе забирает 100% и получается гонка «кто первый» |
| Порог чека `MIN_RECEIPT_TOKENS = 50` | `config.js` | 50 токенов base = ровно половина шага `DECIMALS:6`. Меньше — округлится в ноль. **13 и 500 — границы округления, а не пороги чека** |

### Tier 6 (внешние API, BYOK)

| Решение | Почему |
|---|---|
| Ключ **только** в `localStorage`, только заголовком `X-Provider-Key` | Принцип «промпты не на сервере». Серверных ключей нет вообще — иначе владелец платил бы за всех |
| `TARNET_TIER6_ENDPOINT` только на loopback | Иначе эндпоинт стал бы способом увести чужой ключ на свой хост. Guard стоит **перед** `fetch` |
| Тип 6 **не в** `TIER_WEIGHTS` | κ задаёт вес полезной работы локального узла; у внешнего API узла нет |
| Комиссия `0.0005` = кэшбэк `0.0001` + burn `0.0002` + treasury `0.0002` | ТЗ просило 50/50 сплит плюс кэшбэк — это давало `0.0006` при выручке `0.0005`, то есть `delta = +0.0001`. Пришлось урезать сплит, главный критерий — `delta 0` |
| `cashbackRate` — **геттер**, не второй литерал | Два независимых числа разъехались бы при первой правке |
| `funded_by` только `client` | `emission` был настоящей инфляцией (см. §3, баг 9) |
| Резерв с TTL 5 мин, сбор на входе | Отдельный таймер в процессе некому закрыть после падения сервера |

| Решение | Почему |
|---|---|
| Отказ от Tier 3 Heavy `κ = 10` и `$2.00/M` | Нет рыночного прайса. `heavy` остался **классом железа** в `nodes.tier`, но κ для heavy-работы нет |

### Баги и фиксы — хронология

1. **TTL 30с** убивал задачу раньше Ollama. Живое значение `150000` задано **в systemd**, не в коде: `/etc/systemd/system/tarnet.service:15: Environment=WORKER_TASK_TTL_MS=150000`. В коде дефолт `30000` (`server.js:4135`). **Переустановка без drop-in вернёт 30с.**
2. **`test-mesh` флаки** — `WORKER_DELAY_MS` не читался.
3. **`[hidden]` проигрывал `.panel { display: flex }`** — вкладки не переключались. Фикс через глобальный `!important`.
4. **`sw.js` уважал HTTP-кэш** — фикс не доходил до клиента. `fetch(url, {cache:'reload'})`.
5. **`expert 13` vs `50`** — 13 это граница округления, порог чека 50. Путаница в документе, не в коде.
6. **`697 vs 699`** — разные моменты чтения, не расхождение.
7. **`/install/` 404** — ложная тревога: GET вместо POST.
8. **`/id/register` 404** — ложная тревога: маршрут только POST (`server.js:2282`).
9. **`funded_by: emission` — настоящая инфляция.** `credit()` поднимал баланс без `debit()`, то есть при каждом вызове без баланса **печаталось** `0.0005` TAR. Тест закреплял это как норму. Исправлено в `2.12.1`: без `clientAddress` → `402 CLIENT_REQUIRED`, без свободного баланса → `402 INSUFFICIENT_FUNDS`, `funded_by` всегда `client`, `fundedByEmission` в `/health` = 0.
10. **`2/3/3 = ~62%`** — арифметическая ошибка. В `VISION-8-COMPONENTS.md` записано `0 ✅ / 5 ⚠️ / 3 ❌ — ~30%`; 37% и 44% — альтернативные методики зачёта, прописаны в примечаниях.

## 6. Глоссарий

| Термин | Значение |
|---|---|
| **dPoUW** | Deterministic Proof-of-Useful-Work. Детерминированное вознаграждение за полезную работу, аналог Bitcoin PPS. Заменил лотереи |
| **CWU** | Cognitive Work Unit = `N_tokens × κ_tier × γ_verify`. Единица учёта работы |
| **κ (kappa)** | Вес тира: nano `0.1`, base `1.0`, expert `4.0`. Множитель к цене, не отдельная цена |
| **γ_verify** | 1 — работа подтверждена, 0 — нет. При 0 начисления нет. Сейчас `1` практически всегда (`reason: 'not sampled'`) |
| **TAR** | Учётная единица. `USD_PER_TAR = 20` (1 TAR = `$20`). `DECIMALS = 6` |
| **Fee_Reward** | Выплата за работу, поток 1. В отличие от Block Reward не создаёт деньги |
| **Block Reward** | Эмиссия, поток 2. 50 TAR/эпоха, халвинг 365 эпох |
| **`delta`** | Инвариант леджера: `вход − (burn + treasury + выплаты)`. Обязан быть `0` |
| **Tier 1–4** | Локальные модели по размеру: nano / base / expert |
| **Tier 5** | Cloud Anchors `[SPEC Фаза 3]`. В коде нет |
| **Tier 6** | BYOK — внешние API по ключу пользователя. Единственный тир без локального узла |
| **BYOK** | Bring Your Own Key. Ключ живёт в браузере, уходит провайдеру напрямую |
| **TarNet ID** | Единый аккаунт: `tar_id`, PK = `address`. Колонки `userId` нет |
| **HITL** | Human-In-The-Loop. Подтверждение человеком траты выше порога (`2000` токенов), подпись Ed25519 |
| **`funded_by`** | Кто оплатил комиссию Tier 6. После `2.12.1` — **только** `client` |
| **`reservedTar`** | Занятая часть баланса под незавершённые операции. Свободный остаток = `balanceTar − reservedTar` |
| **`buildVersion`** | Метка сборки в `/health`. **Не git-тег** и не версия схемы |
| **Схема леджера** | `2.1.0-dpouw`. Поле `version` в `/health`. Не путать с `buildVersion` |
| **`fallback_reason`** | Причина, по которой запрос не дошёл до воркера. В коде **3 значения**: `no_workers`, `model_unavailable`, `external_api_error` |
| **`p2p-demo.js`** | Демо-меш: узлы с адресами `sha256('tarnet-demo:<role>')` на loopback. Не реальная сеть |
| **Anti-replay** | LRU на 10 000 хешей пакетов с TTL. Без него перехваченный конверт проигрывался бесконечно |

## 7. Как обновлять

1. Новая веха → раздел в §1 с датой, коммитом, тегом.
2. Новое отвергнутое утверждение → строка в §3 с доказательством из кода.
3. Изменилась живая цифра → §4 (но там датированный срез, не константа).
4. Термин → §6.
