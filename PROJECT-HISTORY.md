### 2026-10-28 (продолжение) — установщики, Device Pairing

- **Причина «.bat дал новый кошелёк» — не в подстановке.** Директива предполагала, что `addr` не доходит до `WORKER_ADDRESS`. Проверено на живом сервере: `GET /install/install.bat?addr=0x648f…` → **200, `set "ADDR=0x648f7af570d0c201c87b7cef55dba88c98bf1936"`**; без адреса → **400 `addr required`**. `app.js:1114` строит ссылку как `` `/install/install.bat?addr=${encodeURIComponent(ADDR)}` ``. Подстановка, валидация и клиентская ссылка работают с коммита `7101678` (24.10).
- **Что было на самом деле:** `ADDR` в PWA — это **демо-адрес из `localStorage`** (`tarnet.address`), сгенерированный `crypto.getRandomValues`, без приватного ключа. Он не связан с `tar_id` телефона. Воркер Ильи шёл **без** переменной окружения и взял `~/.tarnet/worker.json` — оттуда `0xaf34…`, который существовал ещё 24.10 (чек `seq 706`). То есть оба адреса «правильные для своих устройств», но между ними нет связи: механизма привязки не было вовсе.
- **Пустой адрес закрыт в шаблонах.** Добавлена проверка в `install.bat.tpl` (длина 42, префикс `0x`, маркер `__TARNET_ADDR__`) и `install.command.tpl` (то же в bash). Обе ветки проверены: пустой адрес → **`exit=2`** с текстом «скачайте установщик из PWA заново». Это второй рубеж к серверному `400`: файл могли сохранить, переслать или открыть из истории.
- **Device Pairing сделана:** таблица `device_links(ownerAddress, deviceAddress, createdAt)`, `POST /devices/link`, `GET /devices/:owner`, `DELETE /devices/link`. Новые маршруты ушли в `read`-класс лимита (иначе вкладка «Мои устройства» упиралась бы в 10/мин).
- **Баннер теперь учитывает привязку.** Без этого Device Pairing был бы мёртвым механизмом: адрес привязан, сервер знает, а PWA продолжает писать «ваш ПК не среди них» — ровно то, от чего его и делали.
- **Честное ограничение привязки (записано и в коде):** вход по подписи не сделан, `ADDR` — демо-адрес без ключа. Значит привязка — **заявка**, а не доказанное владение: кто знает адрес, тот может его привязать. Балансы при этом **не сливаются** — привязка меняет только ответ на вопрос «моё ли это устройство», деньги остаются на адресе ПК.
- **Найден и исправлен свой же дефект:** флаг `created` был инвертирован (первый вызов → `false`, повторный → `true`), потому что сравнивал сохранённый `createdAt` со свежим `now`, а они всегда разные. Переписано на проверку «было ли до вставки»; тест `30.7`–`30.8` держит это.
- **Приёмка: 690 `test-dpouw` + 25 `test-mesh` = 715, 0 падений.** Из них 16 новых — секция `30. Device Pairing`.

### 2026-10-28 (продолжение 11) — привязка устройства аутентифицирована подписью Ed25519

- **Дефект, названный в коде честно, но остававшийся дырой.** `POST /devices/link` принимал `ownerAddress` из тела и писал привязку без единой проверки. Комментарий к таблице прямо называл таблицу «заявкой, а не доказанным владением». Практическое следствие: кто знает адрес кошелька, тот привязывает к себе чужое устройство, а `tier6PayerChain` начинает списывать комиссию с чужого кошелька — цепочка плательщика берёт деньги с владельца из `device_links`.
- **Второй блокер, который пришлось снять первым: подписывать было нечем.** `deviceAddress()` в `app/app.js` создавал адрес как 20 случайных байт в `localStorage` — у него не было никакого приватного ключа, and комментарий это признавал. Директива предполагала «ключ из localStorage или демо-ключа», но такого ключа не существовало. Поэтому вместо одной серверной правки сделаны обе части: клиент получил настоящий ключ Ed25519 (WebCrypto `generateKey`), адрес выводится той же формулой `0x + sha256(SPKI-DER)[0..40]`, что в `server.js` и `identity.js`. Сходимость не предположена, а проверена запуском: браузерный ключ даёт тот же адрес и его подпись проходит серверный `verifyPayload`. Приватный ключ в `localStorage` этого браузера и на сервер не уходит — регистрируется только `pubkey` через `POST /id/register`.
- **Каноническая строка и разные scope.** Подписывается `<scope>:<owner>:<device>:<nonce>`, где `scope` = `link` для POST и `unlink` для DELETE. Разные scope не дают переиспользовать подпись от привязки для отвязки: строка совпала бы, а смысл действия — нет. `DELETE /devices/link` был такой же дырой и закрыт той же проверкой.
- **Nonce одноразовый, но гасится ПОСЛЕ проверки подписи.** Таблица `device_link_nonces` с TTL 10 минут, значный «второй раз» — `409 NONCE_REUSED`. Порядок важен: если бы nonce сжигался до проверки, мусорный запрос с чужим nonce блокировал бы честную привязку владельца.
- **Порядок ворот — часть защиты, а не стиль.** Валидация формата → `SAME_ADDRESS` → проверка подписи → поиск устройства в сети. Если бы 404 `DEVICE_UNKNOWN` отвечал раньше подписи, чужой человек по коду ответа узнавал бы, какие адреса вообще существуют. Тест `30.24` фиксирует именно это: неподписанный запрос к незнакомому адресу получает `400`, а не `404`.
- **Владелец без публичного ключа — отказ, а не пропуск.** Иначе обходом проверки стало бы «не регистрировать ключ». Код `403 DEVICE_NOT_OWNED`, тест `30.23`.
- **Чего эта правка НЕ доказывает, и это сказано в коде.** Владение самим устройством. Владелец доказывает, что он владелец аккаунта, и заявляет устройство; проверить, что ПК его, нельзя — у ПК свой кошелёк, и его ключа у аккаунта нет. Это ограничение модели, а не недоделка.
- **Стоимость, которую нельзя замалчивать: адрес PWA меняется.** Старый демо-адрес больше не текущий. Его баланс — демо-начисления, распоряжаться ими было нельзя и раньше (ключа не существовало). Старый адрес сохраняется в `tarnet.address` и пишется в консоль как справка, а не стирается молча. На проде таких адресов с ненулевым балансом много: `0xdemo…demo` 20.50314, `0x…1a16…` 14.628653, `0x7c0ffee…beef` 8.112392 — все `NO-KEY`.
- **Приёмка: 786 `test-dpouw`, 0 падений** (было 776). Секция `30` — 26 проверок; новые `30.16–30.24` покрывают ровно требования директивы: без подписи `400 SIGNATURE_REQUIRED`, без nonce `400`, кривой nonce `400 NONCE_INVALID`, чужой ключ `403 DEVICE_NOT_OWNED`, мусорная подпись `403`, подпись над другим устройством `403`, повтор nonce `409 NONCE_REUSED`, владелец без ключа `403`, порядок ворот `400` вместо `404`. ### 2026-10-28 (продолжение 12) — старые балансы разморожены через подписанный клейм

- **Что было заморожено и почему.** До 2.12.8 адрес в PWA выводился как двадцать случайных байт, и приватного ключа к нему не существовало вообще. Демо-начисления на таких адресах нельзя было ни потратить, ни вывести — не потому что не хватало кода, а потому что не существовало ключа, которым можно подписать распоряжение. На проде таких адресов с ненулевым балансом несколько.
- **Директива не требовала подписи — и это было бы новой дырой того же класса.** Формулировка была «пользователь вводит свой старый адрес → сервер проверяет, что на нём есть баланс». Проверка баланса не проверяет владение: любой, кто впишет чужой старый адрес, увёл бы чужой баланс себе. Поэтому подпись сделана **обязательной**, полностью повторяя приём привязки: `checkLinkSignature` со scope `migrate`, строка `<scope>:<owner>:<device>:<nonce>`, где owner — новый адрес, device — старый.
- **Подпись ставит НОВЫЙ адрес, и это единственный возможный вариант.** Старый ключа не имеет по определению — иначе он не был бы осиротевшим. Значит доказать можно только одно: получатель — реальный аккаунт с ключом. Проверить, что старый кошелёк «его», технически нельзя, и это сказано в коде, а не только в отчёте.
- **Что вместо недоказуемого владения — запреты на живые адреса.** Клейм закрыт для адреса с публичным ключом (`403 OLD_HAS_KEY`), для зарегистрированного в `tar_id` (`403 OLD_IS_ACCOUNT`), для привязанного устройства (`403 OLD_IS_DEVICE`). Смысл: перенос разрешён только с осиротевшего демо-адреса, а не с работающего кошелька. Без этих трёх запретов подпись нового адреса защищала бы только от «клейма в никуда».
- **Перенос — ОДНА строка реестра, а не пара debit+credit.** Пара дала бы две строки на одну сумму, и любой расчёт `SUM(to) − SUM(from)` посчитал бы перенос дважды — ровно тот дефект, что был у `burn` с плательщиком (продолжение 9). Тест `37.16` считает строки `kind='migrate'` и требует ровно одну; `37.15` требует, чтобы сумма по всем балансам не изменилась — перенос не эмиссия.
- **Повторный клейм закрыт на уровне схемы.** `balance_migrations.oldAddress` — PRIMARY KEY. Гонка двух одновременных заявок падает на PK и превращается в `409 ALREADY_MIGRATED`, а не в двойной перенос. Баланс перечитывается ВНУТРИ транзакции: между проверкой и списанием мог пройти другой запрос.
- **Свой баг, поймавший себя до тестов.** В первой версии ветка `ALREADY_MIGRATED` отдавала `amountTar: Number(st.claimedAt)` — то есть число из даты. Замечено чтением собственного диффа до запуска; исправлено добавлением `claimedTar` в `migrationState` и взятием суммы из записи о клейме, а не с баланса (баланс старого адреса после переноса равен нулю, историю по нему не прочитать).
- **Задача 2 директивы оказалась уже сделанной.** `worker.js` в репозитории нет — есть `worker-demo.js`, и он читает `WORKER_ADDRESS` с коммита 24.10 (приоритет: `WORKER_ADDRESS` → `TARNET_ID` → `TARNET_WORKER_ADDRESS`). Проверка «старый адрес воркера есть в `nodes`» тоже уже стоит: `DEVICE_UNKNOWN` отвечает только если адреса нет ни в `worker_presence`, ни в `work_receipts`, ни в `nodes`. Добавлять было нечего, и я не стал имитировать работу — вместо этого расширил уже существующее.
- **Документы правились по живым цифрам, а не по памяти.** Снято с прода: `721` чек (было 716), выплаты `72.117293`, оборот `72.500819`, труд `740 195 944 CWU`. Инвариант пересчитан: `72.117293 + 0.185113 + 0.185113 + 0.013300 = 72.500819`, сходится.

ONE-PAGER утверждал «реальная модель, не заглушка» в таблице состояния. Это было правдой в 16:30 и перестало быть правдой к 19:30. ### 2026-11-01 (18:50) — комиссия Tier 6 снижена до ставки B′: `2.17.8-byok-pricing-b`

- **Правка оказалась одной константы, а не трёх.** Перед правкой проверено, чем являются `burn` и `treasury`: в `config.js` их **нет вовсе**, они выводятся в `server.js` как `(fee − cashback) / 2`, причём `treasuryTar` берётся **остатком** (`rest − burnTar`), а не вторым делением. - **Гипотеза «2% от 0.0002 округлится в 0» — опровергнута живым запросом.** `0.0002 × 0.02 = 0.000004`, и при `DECIMALS = 6` это представимо (`round(0.000004, 6) = 0.000004`, не `0`). Настоящая причина неприменимости другая: ветка Tier 6 в `server.js` **не читает `paymentMode` вовсе**, сплит считается только от `TIER6.*`. Проверено двумя запросами с одинаковым телом на изолированном сервере: `fee_gross_tar` в обоих `0.0002`, `paymentMode: null` в обоих. Разница формулировок важна: «ограничение точности» звучало бы как технический потолок, а реальность — недоделанная связка.
- **`PITCH-DECK` чуть не испорчен подгонкой.** Начал заменять `0.000400` в сверке казны — сумма перестала сходиться: `0.006762 + 0.0001 − 0.0002 = 0.006662 ≠ 0.006962`. Это датированный снимок фактического баланса 29.10, а не формула. Правильный ход — пометить дату и ставку A, а не переписать число; рядом дан расчёт под B′.

При балансе `0.1978 TAR` и OPEX `$517/мес` это падение дохода. Ставка выбрана ради конверсии: если трафик не вырастет вчетверо, казна получит меньше, чем при A.
- **Приёмка:** тесты `988 ✅ / 0 ❌`, `RC=0` (было 987; добавлен ассерт на `burn`/`treasury` по отдельности); `grep -c "0.0005\|0.0002 сожжено\|0.0004" DEMO-SCRIPT.md` → `0`; в `PITCH-DECK` остатки `0.0005`/`0.0004` только в явно помеченных исторических снимках.

### 2026-11-02 (19:20) — тело ошибки Ollama и потеря задачи при разрыве сокета: `2.17.10-ollama-error-surface`

- **Запрос был «починить ошибку», а сломано оказалось три вещи, и две из них — в моём коде.** Владелец прислал `500` с текстом `llama-server binary not found` из Ollama. Сам бинарник — его ПК, но по дороге к этому выводу обнаружилось, что сервер и воркер **выбрасывали именно ту строку**, которая называла причину, и что задача умирала от разрыва сокета, а не от поломки модели. Чинилось всё три, потому что чинить только `Ollama` значило оставить два дефекта, которые проявились бы на любом другом сбое модели.
- **`worker-demo.js` бросал `new Error('ollama HTTP 500')` без тела — а рядом, в `askCloud`, тело сохранялось.** Асимметрия и была багом: для облака причина видна, для локальной Ollama — нет. Тело теперь идёт в `errorDetail` (до `200` символов), код `OLLAMA_HTTP_ERROR` остаётся стабильным, потому что PWA переводит код по словарю. Склейка их в одну строку сломала бы поиск по словарю: человек увидел бы сырое `OLLAMA_HTTP_ERROR: ...` вместо инструкции.
- **Порог молчания сокета не знал, чем занят воркер.** `PONG_DEAD_MS = 35000` рвал соединение через `44 873` мс молчания — ровно когда ПК считал задачу. Модель на CPU (и особенно Ollama, поднимающая отсутствующий `llama-server`) думает минуты; молчание во время генерации — **норма**, а не признак мёртвого узла. Добавлен `INFLIGHT_DEAD_MS = 160000` для сокета с задачей в работе; пустой сокет по-прежнему отпускается за `35` с, иначе мёртвый узел держал бы запись и получал задачи, которые не посчитает.
- **Задача на разорванном сокете оставалась `claimed` до TTL и умирала `expired`, хотя её мог посчитать другой узел.** По логам прода: задача `wt_2e1514…` ушла в `17:44:20`, сокет разорван в `17:45:05`, в `17:46:50` — `expired` при полностью рабочем сервере. Добавлен `onWorkerLost`: возврат в `pending` с проверкой дедлайна и счётчиком `requeues`. **Лимит `WORKER_TASK_MAX_REQUEUES = 1` — не жадность:** без него воркер, который берёт задачу и молча падает каждую попытку, гонял бы её вечно; одна повторная попытка лечит разрыв канала, вторая подряд означает, что дело не в канале.
- **HTTP-пульс продлевает WS-присутствие, и это не дубль ping/pong.** Воркер шлёт `/worker/poll?heartbeat=1` каждые `7` с из того же процесса — то есть доказывает жизнь ровно в тот момент, когда ping/pong молчит из-за занятого цикла. `touchAddress` пишет `lastSeenAt` не чаще раза в `10` с: иначе получили бы лишний `UPDATE` на каждый кадр.
- **`ollamaOnline: true` при полностью неработающей Ollama — ложный зелёный сигнал, и он остался.** `/api/tags` отвечает из метаданных и не проверяет, способен ли демон генерировать. Это записано как известное ограничение, а не починено: честная проверка потребовала бы пробной генерации при каждом рукопожатии, что на слабом ПК стоило бы десятков секунд. Симптом теперь виден в `errorDetail`, а не прячется.
- **Приёмка секции 45 проверяет поведение, а не наличие строк.** Поднимается фейковая Ollama, отдающая ровно тот `500` с телом; отдельный процесс воркера доказывает, что текст доехал до `errorDetail` и обрезан до `200`; затем живой WS-воркер получает кадр `TASK`, сокет убивается **до** ответа, и второй воркер обязан забрать задачу обычным опросом, а его ответ — дойти до клиента. Проверка строк в исходнике прошла бы и на коде, который собирает `errorDetail` и никуда его не передаёт.
- **Два провала в первой редакции тестов были моими, а не кода, и оба поучительны.** `JSON.parse` по всему stdout падал, потому что воркер печатает туда же журнал — теперь результат помечается `@@OUT@@` и парсится только помеченная строка. И `/inference` отвечал `503 No worker nodes available`, потому что WS-рукопожатие даёт присутствие, но `pickWorker` читает таблицу `nodes`: без `POST /node` тест проверял отказ, а не возврат в очередь. Правило: **тест, который «проверил» отказ раньше проверяемого пути, зеленеет по неверной причине.**
- **Что НЕ починено и требует действия владельца:** `llama-server.exe` отсутствует в установке Ollama на его ПК. Правка `2.17.10` делает поломку **видимой** — вместо «модель не настроена» человек увидит `llama-server binary not found` с инструкцией, — но сам бинарник возвращается только переустановкой Ollama. Пока этого не сделано, `/health` будет показывать `active_workers: 1` (воркер жив и опрашивает сервер), а каждая задача — падать в `deterministic_fallback`. **Это не «сеть не работает»: узел на связи, сломана модель на нём.**
- **Приёмка:** `998 ✅ / 0 ❌`, `RC=0` (было `988`; добавлены `10` проверок секции 45); `buildVersion = 2.17.10-ollama-error-surface`.

## 2. Решения

### Экономика

| Решение | Константа | Почему так |
|---|---|---|
| Отказ от лотерей → **dPoUW** | `REWARD_MODE: 'hybrid'` | Лотерея даёт непредсказуемый доход: воркер не может планировать, UX ломается |
| `W = N_tokens × κ_tier × γ_verify` | `economics.js:6` | CWU — единица полезной работы, а не «сколько заплатили» |
| Одна цена `P`, тир — множитель `κ` | `PRICE_USD_PER_1M_TOKENS: 0.20` | Отдельная цена на тир разъезжается с таблицей весов при первой правке |
| `TIER_WEIGHTS = {nano: 0.1, base: 1, expert: 4}` | `config.js:7` | Даёт `$0.02 / $0.20 / $0.80` за 1M — числа, выводимые из одной константы |
| Курс `USD_PER_TAR = 20` | `config.js` | **Переименовано** из `TAR_PER_USD`: старое имя читалось как «20 TAR за доллар» — ровно наоборот, в 400 раз мимо. Математика была верной, врало название |
| Комиссия `φ = 5%`: 2.5% burn + 2.5% treasury | `PROTOCOL_FEE_RATE: 0.05` | Дефляция без отдельного механизма |
| Роялти LoRA 5% **от Fee_Reward**, не от gross | `LORA_ROYALTY_RATE: 0.05` | Иначе авторы адаптеров получали бы долю эмиссии, которую не заработали |
| Эмиссия: 50 TAR/эпоха, затухание `2^(−epoch/365)` | `INITIAL_BLOCK_REWARD: 50` | **Не ступенчатый халвинг:** непрерывная экспонента, значение меняется каждую эпоху. Эпоха = сутки |
| Потолок `MAX_RECEIPT_SHARE_OF_EPOCH = 0.25` | `config.js` | Без него единственный узел в эпохе забирает 100% и получается гонка «кто первый» |
| Порог чека `MIN_RECEIPT_TOKENS = 50` | `config.js` | 50 токенов base = ровно половина шага `DECIMALS:6`. Меньше — округлится в ноль. **13 и 500 — границы округления, а не пороги чека** |

### Tier 6 (внешние API, BYOK)

| Решение | Почему |
|---|---|
| Ключ **только** в `localStorage`, только заголовком `X-Provider-Key` | Принцип «промпты не на сервере». Серверных ключей нет вообще — иначе владелец платил бы за всех |
| `TARNET_TIER6_ENDPOINT` только на loopback | Иначе эндпоинт стал бы способом увести чужой ключ на свой хост. Guard стоит **перед** `fetch` |
| Тип 6 **не в** `TIER_WEIGHTS` | κ задаёт вес полезной работы локального узла; у внешнего API узла нет |
| Комиссия `0.0005` = кэшбэк `0.0001` + burn `0.0002` + treasury `0.0002` | ТЗ просило 50/50 сплит плюс кэшбэк — это давало `0.0006` при выручке `0.0005`, то есть `delta = +0.0001`. Пришлось урезать сплит, главный критерий — `delta 0` |

| `funded_by` только `client` | `emission` был настоящей инфляцией (см. §3, баг 9) |
| Резерв с TTL 5 мин, сбор на входе | Отдельный таймер в процессе некому закрыть после падения сервера |

### Баги и фиксы — хронология

1. **TTL 30с** убивал задачу раньше Ollama. Живое значение `150000` задано **в systemd**, не в коде: `/etc/systemd/system/tarnet.service:15: Environment=WORKER_TASK_TTL_MS=150000`. В коде дефолт `30000` (`server.js:4135`). **Переустановка без drop-in вернёт 30с.**
2. **`test-mesh` флаки** — `WORKER_DELAY_MS` не читался.
3. **`[hidden]` проигрывал `.panel { display: flex }`** — вкладки не переключались. Фикс через глобальный `!important`.
4. **`sw.js` уважал HTTP-кэш** — фикс не доходил до клиента. `fetch(url, {cache:'reload'})`.
5. **`expert 13` vs `50`** — 13 это граница округления, порог чека 50. Путаница в документе, не в коде.
6. **`697 vs 699`** — разные моменты чтения, не расхождение.
7. **`/install/` 404** — ложная тревога: GET вместо POST.
8. **`/id/register` 404** — ложная тревога: маршрут только POST (`server.js:2282`).
9. **`funded_by: emission` — настоящая инфляция.** `credit()` поднимал баланс без `debit()`, то есть при каждом вызове без баланса **печаталось** `0.0005` TAR. Тест закреплял это как норму. Исправлено в `2.12.1`: без `clientAddress` → `402 CLIENT_REQUIRED`, без свободного баланса → `402 INSUFFICIENT_FUNDS`, `funded_by` всегда `client`, `fundedByEmission` в `/health` = 0.
10. **`2/3/3 = ~62%`** — арифметическая ошибка. В `VISION-8-COMPONENTS.md` записано `0 ✅ / 5 ⚠️ / 3 ❌ — ~30%`; 37% и 44% — альтернативные методики зачёта, прописаны в примечаниях.

## 6. Глоссарий

| Термин | Значение |
|---|---|
| **dPoUW** | Deterministic Proof-of-Useful-Work. Детерминированное вознаграждение за полезную работу, аналог Bitcoin PPS. Заменил лотереи |
| **CWU** | Cognitive Work Unit = `N_tokens × κ_tier × γ_verify`. Единица учёта работы |
| **κ (kappa)** | Вес тира: nano `0.1`, base `1.0`, expert `4.0`. Множитель к цене, не отдельная цена |
| **γ_verify** | 1 — работа подтверждена, 0 — нет. При 0 начисления нет. Сейчас `1` практически всегда (`reason: 'not sampled'`) |
| **TAR** | Учётная единица. `USD_PER_TAR = 20` (1 TAR = `$20`). `DECIMALS = 6` |
| **Fee_Reward** | Выплата за работу, поток 1. В отличие от Block Reward не создаёт деньги |
| **Block Reward** | Эмиссия, поток 2. 50 TAR/эпоха, непрерывное затухание `2^(−epoch/365)`; **не ступенчатый халвинг** |
| **`delta`** | Инвариант леджера: `вход − (burn + treasury + выплаты)`. Обязан быть `0` |
| **Tier 1–4** | Локальные модели по размеру: nano / base / expert |
| **Tier 5** | Cloud Anchors `[SPEC Фаза 3]`. В коде нет |
| **Tier 6** | BYOK — внешние API по ключу пользователя. Единственный тир без локального узла |
| **BYOK** | Bring Your Own Key. Ключ живёт в браузере, уходит провайдеру напрямую |
| **TarNet ID** | Единый аккаунт: `tar_id`, PK = `address`. Колонки `userId` нет |
| **HITL** | Human-In-The-Loop. Подтверждение человеком траты выше порога (`2000` токенов), подпись Ed25519 |
| **`funded_by`** | Кто оплатил комиссию Tier 6. После `2.12.1` — **только** `client` |
| **`reservedTar`** | Занятая часть баланса под незавершённые операции. Свободный остаток = `balanceTar − reservedTar` |
| **`buildVersion`** | Метка сборки в `/health`. **Не git-тег** и не версия схемы |
| **Схема леджера** | `2.1.0-dpouw`. Поле `version` в `/health`. Не путать с `buildVersion` |
| **`fallback_reason`** | Причина, по которой запрос не дошёл до воркера. В коде **3 значения**: `no_workers`, `model_unavailable`, `external_api_error` |
| **`p2p-demo.js`** | Демо-меш: узлы с адресами `sha256('tarnet-demo:<role>')` на loopback. Не реальная сеть |
| **Anti-replay** | LRU на 10 000 хешей пакетов с TTL. Без него перехваченный конверт проигрывался бесконечно |
